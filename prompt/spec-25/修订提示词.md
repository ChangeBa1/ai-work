```
你要修订一个 spec-kit 功能的设计文档。仓库根目录是
D:\ai-work\ai-work\ai-visual-testing-research\ai-visual-testing-research
目标目录 specs/025-element-identity-key/

【严格边界】
- 只允许修改 specs/025-element-identity-key/ 下的 .md 文件
- 禁止修改 vnc_agent/ 下的任何代码、配置、测试
- 禁止修改 .specify/memory/constitution.md
- 不要重写整份文档，只做下面列出的定点修改；保持既有的中文措辞风格、MUST/MUST NOT
  用法、表格格式与章节编号

【背景：这次修订要解决的三个跨文档缺陷】

缺陷1（最严重，几何锚点异源）：
  plan.md「### 2. 写入路径（record_success）」步骤2 写的是
    「由 target_region 中心算 geom_cell」
  而 research.md「## R3」查询部分步骤2 写的是
    「收集所有 normalize_visible_text(ocr.text) == L 的 OCR 项 → 各算 geom_cell」
  写入侧用点击区域中心，查询侧用 OCR 文字框中心——两侧算的不是同一个点。
  identity_key 含 geom_cell 分量，因此同一个控件先写后查会得到不同的 key，永远查不中。
  G 默认 16，1024×768 下网格是 64×48 像素；按钮区域中心与其标签文字 bbox 中心相差
  超过一格是常态（按钮大、文字不居中、target_region 是安全点扩展框时）。
  后果正是 User Story 3 明确要防的「第二代零命中」，且不报错、只表现为 SC-001 的
  30% 命中率达不到，极易被误诊成归一化规则问题。

缺陷2（纯图标身份写得进查不出）：
  spec.md FR-005a 末句承诺「无可见文本时文本分量为空，身份 MUST 仍可仅凭画面身份 +
  几何分量建立（纯图标路径）」，research.md R3 写入步骤2 也允许「若无 OCR，文本分量
  = ""（纯几何身份）」。
  但 research.md R3 的查询部分，所有路径都从 normalize_visible_text(target_label)
  出发去匹配 OCR 项。纯图标没有 OCR 文本可匹配，候选集恒为空 → insufficient → 永不
  命中。即：写入侧承诺的能力在查询侧不可达，规格自相矛盾。
  这些永不可命中的记录还会进入 SC-001 的分母，压低命中率。

缺陷3（改 identity_grid_size 会静默错命中）：
  contracts/element-identity.md 第5节把 identity_grid_size: 16 与
  identity_schema_version: "eid-v1" 并列为两个互相独立的运行时配置，无联动约束。
  identity_key = "{schema}|{text}|{cell}" 不含 G。
  purge_legacy_element_memories() 的删除条件是「identity_key 为空或非当前 schema」。
  所以把 G 从 16 改成 32 而不动 schema_version：旧行 schema 匹配、留存、参与命中，
  但 geom_cell 的语义已经变了 → 直接错命中，击穿本 feature「宁可不命中、不可错命中」
  的红线。plan.md §1 有一句「归一化或网格语义变更时递增 schema_version」表达了正确
  意图，但意图不是可验收约束，也没有任何机制强制。

【修订 1（缺陷1）：统一几何锚点为「被选中的那条 OCR 项的 bbox 中心」】

决策依据（写进文档时不必复述，但你要理解）：查询侧的入参只有 target_label 和当前帧
OCR 项，除了 OCR 的 bbox 它拿不到任何几何。所以能让两侧一致的锚点只有一个选择。

1a. research.md「## R3」写入部分，把步骤1、步骤2 改为明确区分「用来选 OCR 项的参考点」
    和「用来算 geom_cell 的锚点」：
    - target_region 中心的用途 MUST 限定为两条：(i) 在 ocr_items 中选出中心距最近的
      候选项；(ii) 存入 ElementMemory.bbox 供模板邻域校验
    - geom_cell MUST 由「上一步被选中的那条 OCR 项的 bbox 中心」计算，MUST NOT 由
      target_region 中心计算
    - 用 MUST 措辞写明：写入侧与查询侧计算 geom_cell 的锚点定义 MUST 同源

1b. plan.md「### 2. 写入路径（record_success）」步骤2，当前原文是
      「2. 由 `target_region` 中心算 `geom_cell`；由邻域 OCR 选可见文本（最近非动态
        token，规则见 research / contracts）。」
    改成先选 OCR 项、再由该 OCR 项中心算 geom_cell 的顺序，并显式写明 target_region
    中心只用于选项与存 bbox。

1c. research.md「## R2. 几何网格参数」补一句：cx/cy 的来源 MUST 是可见文本 OCR 项的
    bbox 中心（两侧同源），并说明 R5 表格里 P1「bbox [840,612,894,642] 中心 (867,627)」
    这类样例指的就是 OCR bbox 中心。

1d. contracts/element-identity.md 第1节 resolve_identity_for_write 的说明里，补一句
    锚点约定（region 仅用于选项与存 bbox，cell 取自被选 OCR 项中心）。

1e. spec.md 的 FR-002 或 FR-006 补一条 MUST：写入路径与查询路径计算几何分量所用的
    锚点 MUST 为同一定义，且验收 MUST 包含一组「同一控件先写后查、两侧 geom_cell
    逐字符相等」的断言（不能只断言最终命中——只断言命中的话，两侧不一致时表现为
    「没命中」，与其他失败原因无法区分）。

【修订 2（缺陷2）：取消纯图标可检索身份的承诺】

2a. spec.md FR-005a 末句，当前原文是
      「无可见文本时文本分量为空，身份 MUST 仍可仅凭画面身份 + 几何分量建立
        （纯图标路径）。」
    改为：无可匹配的可见文本 OCR 项时，身份 MUST 视为不可建立；写入侧 MUST 跳过
    可检索写入。理由（可写进文档）：查询侧无法从 target_label 推导几何，纯文本分量
    为空的身份在查询侧不可达，写入它只会产生永不命中的记录并污染 SC-001 分母。

2b. spec.md Edge Cases 中的这一条，当前原文是
      「- 控件无可见文本（纯图标）→ 身份仍须可建立（至少基于画面身份 + 几何等非文本
         要素）；不得退回「整段 Planner 长描述当主键」。」
    改为：纯图标 → 身份不可建立 → 不写可检索记录、查询未命中；同时保留原有的
    「不得退回整段 Planner 长描述当主键」这半句。

2c. research.md R3 写入步骤2，当前原文是
      「2. 若无 OCR，文本分量 = `""`（纯几何身份）；」
    改为：若选不出符合条件的 OCR 项 → 返回 None（身份不可建立），service 跳过可检索写入。

2d. 全局一致性扫描：在 specs/025-element-identity-key/ 下搜索「纯图标」「纯几何」
    「text=""」「normalized_visible_text = ""」等表述，把所有还在承诺「空文本身份可建立
    / 可检索」的地方一并改掉。至少要检查 plan.md §1 的代码块注释
    （「# 无可见文本时 normalized_visible_text = ""（纯图标：仅页面+几何）」）、
    data-model.md 的 NormalizedVisibleText 与 ElementIdentity 小节、
    research.md R5 结论段（「两条中文长描述在无稳定 OCR 短标签时可能变为 text=""+几何
    或不可检索」——这句要收敛为「不可检索」）。

【修订 3（缺陷3）：把网格粒度编码进身份键】

3a. 身份键格式从
      identity_key = "{schema_version}|{normalized_visible_text}|{geom_cell}"
    改为把 G 并入 schema 段，例如
      identity_key = "{schema_version}:g{G}|{normalized_visible_text}|{geom_cell}"
      （如 "eid-v1:g16|小計|13,13"）
    效果：改 G 会让全部旧键自动失配，且 purge_legacy_element_memories() 现有的
    「非当前 schema 前缀」条件顺带覆盖 G 变更，不再依赖人工记得同步递增 schema_version。
    如果你认为有更好的等价写法（例如把 G 作为独立键分量），可以采用，但 MUST 满足：
    G 变更后旧行既不可能被命中、也会被 purge 条件识别。

3b. 需要同步改的位置（逐个检查，不要漏）：
    - plan.md「### 1. 身份键（逻辑）」代码块及其下方关于 schema_version 递增的说明
    - contracts/element-identity.md 第1节 build_identity_key 的格式说明
    - contracts/element-identity.md 第4节 purge_legacy_element_memories 的条件描述
    - data-model.md 的 ElementIdentity 表（identity_key 行）与「校验」小节
    - research.md R1 的键形态说明
    - data-model.md SQLite 物理模型中 identity_key 列的长度是否仍够用（VARCHAR(640)）

3c. spec.md 补一条 MUST（放在 FR-001 或新增 FR-001a 均可）：身份键 MUST 编码网格粒度，
    使网格粒度变更后既有记录 MUST NOT 被命中；或等价地，网格粒度变更 MUST 强制
    schema_version 递增并触发 purge。二选一，写死一种。

【修订 4（CHK008：归一化顺序两处文档相反）】

spec.md FR-005a 当前列举的顺序是：
  (1) Unicode NFKC；(2) 大小写折叠；(3) 空白折叠；(4) 日文假名脚本级折叠
research.md R4「处理流水线（顺序固定）」的顺序是：
  0 空安全 → 1 NFKC → 2 浊点预合成 → 3 长音统一 → 4 casefold → 5 空白折叠 → 7 ==
两者把假名/长音处理放在了 casefold、空白折叠的相反侧。对结果影响极小（假名无大小写
形态），但两份规范性文档对同一条「顺序固定」规则给出不同顺序，实现者无从判定以谁为准。
把 FR-005a 改为与 R4 完全一致的顺序（或改为显式引用 R4 流水线表，不再自行列举顺序）。

【修订 5（CHK002：写入侧行为二选一未收敛）】

spec.md FR-006 当前写「无法可靠解析身份时 MUST 跳过可检索写入**或**显式标记不可检索」，
US3-AS3 当前写「写入**可**跳过或标记为不可检索」。
而 contracts 第3节 record_success 已经定死为「身份可建则按 identity_key upsert；否则
**不写可检索元素**」，data-model 也定「identity_key=="" 永不进入命中候选」。
把 FR-006 与 US3-AS3 收敛为 contracts 已选定的那一种：MUST 跳过可检索写入（不再用
「或」「可」）。

【修订 6（CHK003：纯符号串未定义）】

纯符号串（仅 ×、／、-、标点等）经 R4 流水线后仍是非空字符串，会作为合法文本分量参与
身份相等，但全部文档没有一处明示这个结论。R4 金样表 12 行没有纯符号样例
（`預/現計` 含汉字，不构成覆盖）；is_dynamic_token 过滤只作用于写入侧且只针对数字形态。
风险：多个纯图标/符号按钮若被 OCR 读成同一符号，会在同一 cell 下误并。

6a. research.md R4「规则表示例（单测金样）」补至少 3 行纯符号样例（如 `×`、`／`、`--`），
    给出期望输出。
6b. spec.md Edge Cases 补一句 MUST，明确纯符号串归一化后是「作为合法文本分量参与相等」
    还是「视为不可检索」——二选一写死，不要留「可」。
    建议选前者（作为合法文本分量），因为几何分量仍在起区分作用，且判定纯符号需要额外
    的字符类规则，属于新增复杂度；但你若选后者，需在 6a 的样例期望值中保持一致。

【顺带修正（不构成缺陷，顺手改掉）】

research.md R4 步骤3 的括号举例「ASCII 连字符 `-` 不改为长音（避免破坏 `預/現計` 等）」
中，`預/現計` 的分隔符是 `/` 而不是 `-`，举例与规则不对应。规则本身表述正确，换一个
真正含 ASCII 连字符的样例，或删掉这个括号举例。

【完成后必须自检并报告】

1. 列出你改动的每个文件和每处改动（文件:小节 → 改了什么）
2. 逐项确认：修订1的锚点定义在 spec/plan/research/contracts 四处表述**一致且互不矛盾**
3. 逐项确认：全仓 specs/025-element-identity-key/ 内已无「空文本身份可检索」的残留表述
4. 逐项确认：identity_key 的格式在 plan / contracts / data-model / research 四处**完全
   一致**（逐字符比对，包括示例值）
5. 明确报告：你是否改动了 vnc_agent/ 下的任何文件（正确答案必须是「否」）
```
