# AI时代的架构师：变化与应对

> 承接 [认知成长学习方案](./README.md)。本篇聚焦：AI（尤其是LLM/生成式AI）浪潮下，架构师这个角色发生了什么变化，需要新增学习哪些内容。

## 一、AI时代架构师角色的核心变化

### 1. 不变的部分（容易被误解为"过时"的能力，其实更重要）
- 系统设计基本功（可用性、一致性、扩展性权衡）依然是地基，AI不会替代这层判断
- 业务理解与需求抽象能力不降反升——AI能帮你快速实现方案，但"该不该做、做成什么样"依然要靠人判断
- 沟通与向上管理能力更重要了，因为AI让"实现"变便宜，"决策对不对"成为团队产出的主要瓶颈

### 2. 新增的部分
- **AI系统本身成为一种新的架构组件**：LLM调用、向量检索、Agent编排，需要像对待数据库/消息队列一样设计其选型、容错、成本模型
- **不确定性成为一等公民**：传统系统追求确定性输出，AI系统的输出本身有概率性/幻觉风险，架构层面要设计兜底和验证机制
- **人机协作流程设计**：哪些环节全自动、哪些环节需要人工审核（Human-in-the-loop），这是新的架构决策维度
- **AI辅助研发流程本身改变了团队协作方式**：Code Review的重点、代码产出速度、初级工程师的培养方式都在变

## 二、架构师需要补的AI技术认知

### 1. LLM基础概念（必须掌握，属于新的"计算机基础"）
- Token、Context Window（上下文窗口）、Prompt、System Prompt 的基本概念
- 模型能力的边界：为什么会"幻觉"（Hallucination）、为什么长上下文会"迷失中间"（Lost in the middle）
- Prompt Engineering 基本方法：Few-shot、Chain-of-thought、结构化输出（如强制JSON schema）
- 主流模型家族的定位差异（不需要记具体参数，需要知道"选型思路"：速度 vs 能力 vs 成本 的取舍逻辑）

### 2. RAG（检索增强生成）架构模式
- 为什么需要RAG：解决模型知识过时、私有数据接入的问题
- 核心组件：Embedding（向量化）、向量数据库、检索策略（相似度检索、混合检索）、重排序（Rerank）
- 架构层面的权衡：检索召回率 vs 响应延迟 vs 存储成本

### 3. Agent 与工具调用架构
- Function Calling / Tool Use 的基本原理：模型如何决定调用哪个工具、如何传参
- 单Agent vs 多Agent协作架构的适用场景（复杂任务拆解 vs 简单任务直接执行）
- MCP（Model Context Protocol）等标准化协议的作用：解决工具接入的碎片化问题，类似于"AI时代的API网关"
- Agent系统的失控风险：无限循环调用、越权操作、成本失控，架构上要设计好熔断和权限边界

### 4. AI应用的系统设计新维度
传统系统设计三要素（可用性、一致性、扩展性）之外，AI系统架构需要额外考虑：
- **成本模型**：按Token计费带来的成本不确定性，需要设计缓存（Prompt Caching）、模型分级路由（简单任务用小模型、复杂任务用大模型）
- **延迟特性**：流式输出（Streaming）成为标配，架构上要考虑前端如何处理渐进式响应
- **可观测性（Evaluation & Tracing）**：AI系统的"对不对"无法像传统系统一样靠单元测试完全覆盖，需要建立评测集（Eval Set）、人工抽检、线上效果监控体系
- **安全新增维度**：Prompt Injection（提示词注入）、数据泄露风险（敏感信息被检索/生成暴露），需要在架构里设计好输入过滤和输出脱敏

## 三、AI时代架构决策的思维变化

### 1. ROI评估维度变了
以前评估"要不要做这个功能"，现在要多问一层："这个环节能不能用AI做、值不值得用AI做"——需要综合考虑准确率要求、出错成本、人工兜底成本。不是所有环节都适合上AI，越是高风险、高确定性要求的环节（如金融交易），越要谨慎评估。

### 2. "非功能性需求"里多了一项：可解释性与可控性
传统架构关注性能、安全、可维护性，AI系统还要额外设计：
- 出错时能不能定位是哪个环节的问题（模型幻觉？检索没召回？还是Prompt写得不好？）
- 能不能让用户/运营人员在必要时介入纠正，而不是完全黑盒自动化

### 3. 团队协作与工程流程的变化
- Code Review 的重点从"有没有bug"部分转向"AI生成的代码是否符合架构意图、是否引入了不必要的复杂度"
- 架构师需要为团队设计"人机协作的研发流程"：什么代码可以完全交给AI生成、什么场景必须人工设计后再让AI实现细节
- 初级工程师的成长路径也在变化——纯"实现"的工作被AI大量替代后，如何还能让新人锻炼出系统设计能力，是架构师需要考虑的团队建设问题

## 四、学习路径建议

| 阶段 | 内容 |
|---|---|
| 第1-2周 | 补齐LLM基础概念（Token、Context Window、Prompt Engineering），亲自动手用API跑通一个最小的LLM调用示例 |
| 第3-4周 | 学习RAG架构模式，动手搭一个简单的检索增强demo（向量库+检索+生成），体会检索质量对最终效果的影响 |
| 第2个月 | 学习Agent/工具调用架构，了解Function Calling原理和MCP协议的定位，跑通一个简单的多工具Agent |
| 第2-3个月 | 在实际工作中，找一个可以用AI辅助的环节（如自动化测试生成、文档生成、代码review辅助），主动设计并落地一版方案，重点练习成本/延迟/准确率的权衡 |
| 持续 | 关注AI应用的评测体系（Evaluation）设计方法，这是目前大部分团队最薄弱、也最容易体现架构师价值的一环 |

## 五、核心心态

- AI没有改变架构师的核心职责（做技术决策、权衡取舍、对齐业务目标），但给架构师的"工具箱"和"决策变量"里加了新的维度（不确定性、成本模型、人机协作边界）
- 越早把AI系统设计当作一门正经的架构能力去系统学习（而不是当作"调个API"的小事），越能在这一波变化里建立差异化优势
- 具体动手实践比看文章更重要——AI应用的很多"坑"（幻觉、成本失控、Prompt脆弱性）只有自己搭过一遍才能真正体会，这和学系统设计的道理是一样的：光看书不动手，永远停留在表面
