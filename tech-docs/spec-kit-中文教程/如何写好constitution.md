# 如何写好 Constitution(尤其是从 0 开始、经验有限时)

> 本文补充 [README.md](./README.md) 第 8.3 节,聚焦一个具体问题:没有架构和业务经验的开发者,如何写出、审查并逐步完善项目宪章(`.specify/memory/constitution.md`)。

## 1. 先破除一个误解

写好 constitution 不需要"架构经验"或"业务经验",需要的是**工程纪律的常识 + 把抽象原则拆成可检验规则的能力**。后者是可以练出来的技能,不依赖年限。很多资深工程师写的 constitution 也很烂——比如"代码要优雅""架构要清晰"——这些是废话,因为没法检验。

## 2. 判断一条原则好不好:五个测试

让 AI 起草候选原则(比如 10-15 条),再用下面五个测试逐条筛选、修改:

1. **可验证性测试**(最关键):这条原则能不能变成以下四种东西之一?
   - 一条 lint/CI 规则
   - 一个必须存在的测试类别
   - 一条 code review checklist 项
   - 一个可以在 `plan`/`analyze` 阶段自动检查的约束

   不能的话就是口号,删掉或重写。例如"代码要优雅"改成"每个函数不超过 50 行,超过需要在 PR 里说明理由"。

2. **反例测试**:能否编出一个具体场景,遵守这条原则反而是错的?容易编出来,说明要么该加例外条款,要么这条不该进宪章(它其实是某个功能的权衡,不是长期规则)。

3. **稳定性测试**:这条原则会不会因为下个功能的需求变化而跟着变?会变的属于 spec 层,不属于 constitution 层。constitution 应该是"不管做什么功能都成立"的东西(如"外部输入必须校验"),而不是具体功能细节(如"任务看板要支持四种状态")。

4. **数量控制**:好的 constitution 通常 5-10 条。超过 15 条基本说明在堆砌套话而不是抓真正重要的红线。

5. **反向压力测试**(专治经验不足):让 AI 起草完后,再单独要求它"针对每一条原则,给出一个真实场景,说明严格执行这条会造成明显的负面后果"。把 AI 当审查者而不是权威,用它来补足自己经验不足带来的盲区。

## 3. 学习判断力:不用先学完架构再动手

判断力是从大量小样本的实践 + 复盘中长出来的,顺序应该是边做边学:

- 精读 [12-Factor App](https://12factor.net/):篇幅短、每条都具体,是"如何把原则写成可检验规则"的最佳范例。
- 《A Philosophy of Software Design》(John Ousterhout):比 Clean Architecture 更适合建立"复杂度"和"好设计长什么样"的判断力。
- 看开源项目的 ADR(Architecture Decision Record)和 `CONTRIBUTING.md`:这些就是别人写的"宪章",看多了会知道好原则和差原则长什么样。
- 把每次被 code review 纠正的地方记下来:被纠正三次以上的同一类问题,就值得写进 constitution——这是最贴合自己项目的原则来源。
- 用 spec-kit 自己的 `analyze`/`checklist` 阶段反哺学习:这两个阶段本质是在替你做"这条规则能不能被检验"的自动化判断,多跑几次能逐渐吸收这套逻辑。

## 4. 从 0 开始时具体怎么写

从 0 开始时,**不要把 constitution 当"最终宪法",当成"v0.1、允许被修订的起点"**。README 命令表里写的是"项目首次采用**或原则变更时**"运行 `/speckit.constitution`——修订本来就是正常用法,不是失败。第一步不是憋出一份完整宪章,而是只写现在就能确定的部分,剩下的留白,等第一轮 `specify → plan` 跑完、真实约束浮现后再回来补。

### 只有一个点子时,能确定的原则来自三类来源

**(1) 通用工程卫生原则**(不需要任何架构/业务知识,放之四海皆准,现在就能写):
- 外部输入必须在系统边界校验
- 密钥、密码、用户隐私内容不进日志和仓库
- 新增依赖必须说明理由,能不加就不加
- 简单直接优先于聪明取巧的方案

**(2) 从"点子本身"推出的原则**(只需回答几个关于点子的问题,不需要架构知识):
- 会不会碰钱/支付? → 需要数据完整性、操作留痕
- 会不会碰个人隐私数据? → 需要隐私边界规则
- 是不是给陌生人/公网用户用? → 需要默认安全假设(如"默认拒绝、显式授权")
- 出错的代价大不大(医疗/金融 vs 个人小工具)? → 决定测试覆盖的强制程度

这些答案取决于"这是个什么系统",不取决于"这个系统怎么实现",所以现在就能回答。

**(3) 针对"自己"这个开发者的补偿性原则**(自知之明,不是架构经验):
- 知道自己容易跳过测试 → "核心逻辑合并前必须有单元测试"
- 知道自己容易忘记当初的设计动机 → "每个模块变更需在 PR/commit 里简要说明动机"
- 没有第二个人 review → "每次 implement 后必须自己过一遍 diff 清单再合并"

### 明确现在不要写的东西

不要为了显得完整而硬编造现在判断不了的条款,比如具体性能指标("响应时间必须 <200ms")、合规标准细节。这时候的"可验证性测试"会直接帮你筛掉——现在没法验证的东西,写了也是空话,不如留白,等第一个功能的 `plan` 阶段暴露真实约束后再补。

### 操作流程

1. 只写 3-5 条确定的原则(上述三类),跑一版 `/speckit.constitution`,不用追求完整。
2. 直接进入第一个功能的 `/speckit.specify → /speckit.clarify → /speckit.plan`。这一步会逼你回答技术栈、数据存储、部署方式——这些答案出来之前,没法写出靠谱的架构类原则,硬写只是猜。
3. 做完第一轮后回头看:哪些决定是在 plan/clarify 阶段反复确认、明显是"以后每个功能都要遵守"的?把这些提炼回 constitution,再跑一次 `/speckit.constitution` 做修订。这时才有第一手真实约束,而不是凭空想象的架构经验。
4. 重复几轮功能后,constitution 会自然收敛成一份真正基于项目实际情况的宪章,而不是照抄网上模板。

## 5. 一句话总结

从 0 开始时,constitution 该写的不是"我预测这个系统会需要什么架构",而是"不管这个系统最后长什么样,我现在就确定要守住的底线是什么"。这个问题的答案不需要架构经验,只需要对点子本身的风险和对自己的弱点诚实。剩下的交给后续修订——修订本来就是 spec-kit 工作流的一部分。
