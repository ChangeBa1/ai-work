24役割アーキテクチャ：Planner · Grounder · Executor · Verifier

本プロジェクトで最も重要なアーキテクチャ契約です。 「何をしたいか / どこをクリックするか / どうイベントを送るか / 本当に成功したか」を分離することで、 ブラックボックス環境でも原因分析・リスク制御・モデル差し替えが可能になります。

Planner

次に何をするか

StructuredScreen とステップ intent を読み、SemanticAction （誰をクリック、どのキー、マイクロアクションか）を出力。
禁止：生座標の出力、最終合否の判定。

Grounder

ターゲットはどこか

MiMo による視覚的位置特定。bbox 候補 + 信頼度 + coordinate_space を返す。
禁止：テストフロー決定。未知/矛盾/範囲外座標は fail-safe。

Executor

VNC でどう実行するか

意味アクションをキー/マウスイベントへ。batch キー、type_text、stale_frame ガード、safe click point を含む。
「送信」のみ担当し、「業務成功か」は判断しない。

Verifier

本当に成功したか

操作後に再キャプチャ。ActionEffect と業務アサーションを独立判定。
禁止：Planner/Grounder の自己申告を信じること。uncertain ≠ 合格。

4二重検証：操作効果 ≠ 業務成功

POS 実機事故が Feature 002 を後押ししました。全画面画素変化が約 0.4% しかないのに、 旧ロジックは「2% screen_changed」で効果なしと誤判定し、「レジ袋追加」を再クリックしていました。 現在は必ず2系統の結果を見ます。

no_effect / expected_effect
unexpected_effect / effect_uncertain"] W --> SV["StepVerificationResult
passed / failed / uncertain"] AE --> RG[RepeatGuard / リトライ戦略] SV --> STEP[ステップ最終状態] AE -.独立.-> LOG[(ActionIteration 監査)] SV -.独立.-> LOG

ActionEffect が答えること

「今回のキー/マウス操作は UI 上で観測可能な反応を起こしたか？」 — 局所 blob・OCR/テンプレ差分を使い、業務目標達成は証明しない。

StepVerification が答えること

「YAML の expected を満たしたか？」— text_appears / visual_question 等。 正式業務ステップには業務アサーション必須。screen_changed だけでは不十分（effect_only を除く）。

非冪等保護：「レジ袋追加 / 金券登録 / 現金確定」などでは、 効果が expected_effect でも業務が uncertain のとき、盲目的な再クリックを禁止し、 まず検証を強化します — POS の二重計上を防ぐ要です。

8成功事例 A：レジ袋 + 現金会計

ケース ID：pos-buy-bag-checkout-001。 最初に通した「縦断成功スライス」の一つであり、002/003 事故回帰の主 fixture でもあります。 以下は設計上の成功パスを解説し、実 run で段階的に合格した証拠パターンを交えます。

① 前提条件：空カート

YAML で precondition.facts.cart_item_count を宣言し、visual_question で 左側「合計」の緑数字が明確に 0 かを問います。コアに “cart” フィールドはありません — Constitution VI の実装です。 人手では --confirm-precondition cart_item_count=0 でも確認できます。

Verifier · visual_question Feature 003 facts

② レジ袋追加（非冪等 · 二重クリックが最も危険）

Planner は click ターゲット「レジ袋」を出力。OCR はしばしば「ジ袋」と読みますが、 同一性は normalized_target で判定し、文字列完全一致を要求しません。 クリック後の ActionEffect は全画面変化 約 0.7% でもよく、 局所 blob + 業務アサーションで成功を証明します：

  • text_appears: 点数 + text_appears: 内税（安定 chrome。「1」「袋」誤一致を回避）
  • visual_question：数量 1 個・金額 5 が明確なときのみ passed
Planner Executor click ActionEffect = expected_effect trusted_pass 実 run 例：座標 約 (337,679)

③ 小計：支払画面への遷移

右下「小計」をクリック。画面は大きく変化（global_diff が 40%+ になることも）。 業務ゲートはシンプルかつ有効：OCR で「不足」が出れば待支払状態とみなします。 多くの場合 1 反復で trusted_pass。

1 iteration が典型 実 run 例：クリック 約 (866,627)

④ 預/現計：現金開始 + 釣銭機の自動入金待ち

本ケースで最も「ブラックボックス」なステップです。Agent は POS ボタンだけを押し、 釣銭機シミュレータウィンドウは操作しません。 成功条件はダイアログに 預り金 10,000・お釣り 9,995（レジ袋 5 円時）、かつ「確定」が押せる状態。 OCR は 10,000 / 10.000 の千分位差を正規化して許容します。

過去の失敗パターン：visual_question は金額一致と見ても OCR が “10,000” を拾えず、 「決定的アサーションが VLM より優先」のため全体 failed（Feature 011 仲裁と関連）。 成功パスでは OCR と視覚結論の整合、または脆弱な OCR を避けるアサーション設計が必要です。

⑤ 確定 → 済

現金ダイアログの「確定」をクリック。最終的に visual_question で商品明細の目立つ赤「済」を確認。 済 が見えて初めて取引が固定完了 — これが業務成功のハード終点です。

visual_question · 済 業務クローズ完了

9成功事例 B：金券 + 現金の混合支払

ケース ID：pos-buy-bag-mixed-kinken-cash-001。 レジ袋登録後、まず金券で 4、残りを現金で補います。 成功の鍵は金額入力がテンキー「4」のクリックであり、type_text や Escape ではないことです。

なぜこれが「成功設計」か

実機では支払画面のキーボードフォーカスが不安定で、type_text が金額枠に入らないことが多い。 成功パスは Grounder が数字キー「4」を位置特定して click。 intent に近傍関係（上 7 / 右 5 / 下 1）を書き、位置特定の安定性を上げます。

レッドライン操作（逸脱＝失敗）

Escape 禁止：「現在の操作を行うには…」が金券ボタンを覆い、 後続が TARGET_NOT_FOUND。クリア/戻る/キャンセルの乱打も禁止（ブロック解除目的を除く）。

実 brief 断片では add-shopping-bag / calc-subtotal / enter-kinken-amount / apply-kinken が passed になり、 混合支払の前半は実機で通っていることが確認できます。現金差額ステップは釣銭文言に敏感で、 アサーションと OCR の協調チューニングが要ります。

成功パス上の「工学的細部」（偶然の当たりではない）

タスクビュー：先に POS エラーダイアログを閉じる

赤い「バーコードが不正です」があると Win+Tab は POS に即座に奪われます。成功策：先に「戻る」→ その後 Win+Tab。

サムネイル click：タイトルはアンカーのみ

Grounder がタイトルバー y≈50 を誤ロックしたことがありました。 成功記述は target.text = null を強制し、タイトルは nearby_texts、クリックはサムネ本体。

バーコード消去：batch_repeat Backspace（Feature 005）

1 回の ActionIteration で連続退格。観察/検証は 1 ラウンドだけにし、20 回分のキャプチャ+計画を避けます。

type_text が本当に動くこと（Feature 006）

vncdotool クライアントに type が無かった欠陥を修正後、数字バーコードが安定入力できます。

検証 ROI を絞り「表に既にあるコード」偽合格を防ぐ

Favorite 表に 45127366 が既に見えると、OCR 領域が広いと pre-check が入力完了と誤認し type_text をスキップします。 成功策：アサーション領域を入力枠の行だけに限定。

性能：OCR で足りるなら visual_question を使わない

日本語かなの OCR は不安定なため、アンカーは ASCII/漢字/数字。VQ は全選択反転、金額枠、済 など真に視覚的な判定に限定。

11POS 成功パターンのまとめ（再利用可能）

システムにおける「成功」の厳密な定義

モデルが成功と言ったからではありません。各ステップの StepVerificationResult = passed （business モードかつ basis が信頼できる）がすべて完了し、 Run status = PASSED、再生可能なフレーム証拠と action_tags 監査カウントが残ることです。

成功事例に共通する脚本

① 状態が既知（空カート/環境可）→ ② 単一意図のステップ → ③ 決定的アサーション優先 → ④ 視覚は曖昧さ解消のみ → ⑤ 支払は外部シミュ副作用を待つ → ⑥ 硬終点（済）でクローズ。
