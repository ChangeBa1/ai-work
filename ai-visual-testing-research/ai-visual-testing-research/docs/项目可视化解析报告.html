2四角色架构：Planner · Grounder · Executor · Verifier

这是整个项目最重要的架构契约。把“想做什么 / 点哪里 / 怎么发事件 / 是否真的成功”拆开， 才能在黑盒场景下做归因、控风险、可替换模型。

Planner

下一步做什么

读 StructuredScreen + 步骤 intent，输出 SemanticAction（点谁、按什么键、是否微动作）。
禁止输出裸坐标、禁止最终判通过。

Grounder

目标在哪里

MiMo 视觉定位，返回 bbox 候选 + 置信度 + coordinate_space。
禁止决定测试流程；坐标未知/越界必须 fail-safe。

Executor

如何通过 VNC 执行

把语义动作变成键鼠事件；含 batch 按键、type_text、stale_frame 守卫、safe click point。
只负责“发出去”，不负责“算不算业务成功”。

Verifier

是否真的成功

动作后重新截图；独立判断 ActionEffect + 业务断言。
禁止相信 Planner/Grounder 的自我感觉；uncertain ≠ 通过。

4双轨验证：动作效果 ≠ 业务成功

POS 真实事故推动了 Feature 002：全屏像素变化仅 0.4% 时，旧逻辑用“2% screen_changed”会误判无效果并重复点“加入购物袋”。 现在必须同时看两份结果。

flowchart LR ACT[Executor 执行完成] --> W[Wait + 新截图] W --> AE["ActionEffect
no_effect / expected_effect
unexpected_effect / effect_uncertain"] W --> SV["StepVerificationResult
passed / failed / uncertain"] AE --> RG[RepeatGuard / 重试策略] SV --> STEP[步骤最终状态] AE -.独立.-> LOG[(ActionIteration 审计)] SV -.独立.-> LOG

ActionEffect 回答什么？

“这次键鼠动作有没有在 UI 上激起可观察响应？”——用局部 blob、OCR/模板差分， 不证明业务目标达成。

StepVerification 回答什么？

“YAML 里 expected 是否满足？”——text_appears / visual_question 等。 正式业务步必须有业务断言；仅 screen_changed 不够（除非 effect_only）。

非幂等保护：像“加入购物袋 / 金券登记 / 現金確定”这类动作， 若效果已 expected_effect 但业务仍 uncertain，系统禁止盲目再点一次， 必须先加强验证——这是 POS 防双记账的关键。

用例 ID：pos-buy-bag-checkout-001。这是最早打通的“纵向成功切片”场景之一， 也是 002/003 事故回归的主 fixture。下面按设计成功路径解读，并穿插真实 run 中逐步通过的证据模式。

① 前置条件：空购物车

YAML 声明 precondition.facts.cart_item_count，用 visual_question 问： 左侧「合計」绿色数量是否明确为 0。核心代码没有 “cart” 字段——这是 Constitution VI 的落地。 人工也可用 --confirm-precondition cart_item_count=0 跳过自动判定。

Verifier · visual_question Feature 003 facts

② 加入购物袋（非幂等 · 最容易双点）

Planner 输出 click 目标「レジ袋」。OCR 常把字读成「ジ袋」——身份匹配用 normalized_target， 不要求字符串完全相等。点击后 ActionEffect 可能只有 ~0.7% 全屏变化， 但局部 blob + 业务断言共同证明成功：

  • text_appears: 点数 + text_appears: 内税（稳定 chrome，避开「1」「袋」误匹配）
  • visual_question：数量 1 個、金额 5 明确可见才 passed
Planner Executor click ActionEffect = expected_effect trusted_pass 真实 run 例：坐标约 (337,679)

③ 小計：进入支付语义画面

点击右下「小計」。画面大幅变化（global_diff 可到 40%+）。业务门闩极简但有效： OCR 出现「不足」即认为进入待支付态。一步内通常 1 次迭代即可 trusted_pass。

1 iteration 常见 真实 run 例：点击约 (866,627)

④ 預/現計：启动现金 + 等待找零机自动入金

这是案例中最“黑盒”的一步：Agent 只点 POS 按钮，不操作找零机模拟器窗口。 成功判据是对话框出现 預り金 10,000、お釣り 9,995（购物袋 5 元时），且「確定」可点。 OCR 需容忍 10,000 / 10.000 千分位差异（引擎会归一化数字）。

历史失败模式：visual_question 已认为金额对，但 OCR 没读到 “10,000”， 因“确定性断言优先于 VLM”，整体仍 failed（Feature 011 仲裁方向与此相关）。 成功路径要求 OCR 与视觉结论对齐，或断言写法避开脆弱 OCR。

⑤ 確定 → 済

点击现金对话框「確定」。最终用 visual_question 确认商品明细区醒目红色「済」。 只有看到 済，交易才算固定完成——这是业务成功的“硬终点”。

9成功案例 B：金券 + 现金混合支付

用例 ID：pos-buy-bag-mixed-kinken-cash-001。在购物袋登录之后，先用金券支付 4，再现金补 1。 成功的关键是金额输入必须点小键盘「4」，而不是 type_text 或 Escape。

为什么这是“成功案例设计”？

实机证明支付画面键盘焦点不可靠，type_text 很少真正写入金额框； 成功路径改为 Grounder 定位数字键「4」并 click。intent 里写清邻域关系 （上 7 / 右 5 / 下 1），显著提高定位稳定性。

红线操作（失败即偏离成功路径）

禁止 Escape：会弹出「現在の操作を行うには…」挡住金券按钮， 后续 TARGET_NOT_FOUND。禁止乱点 クリア/戻る/キャンセル（除非用于清阻塞提示）。

真实 brief 片段曾显示： add-shopping-bag / calc-subtotal / enter-kinken-amount / apply-kinken 均可 passed， 说明混合支付前半链路已在实机跑通；现金补差步对找零金额文案更敏感，需要断言与 OCR 协同调优。

成功路径上的“工程化细节”（不是偶然点对）

任务视图：先清 POS 错误弹窗

若存在红色「バーコードが不正です」，Win+Tab 会被 POS 抢回前台。成功策略：先点「戻る」再 Win+Tab。

缩略图点击：标题只作锚点

Grounder 曾误锁标题栏 y≈50。成功写法强制 target.text = null， 标题放 nearby_texts，点击缩略图本体。

清空条码：batch_repeat Backspace（Feature 005）

一次 ActionIteration 连按多次退格，只做一轮观察/验证，避免 20 步截图+规划。

type_text 必须真正可用（Feature 006）

修复 vncdotool 客户端无 type 属性后，数字条码才能稳定写入。

验证 ROI 收紧，防止“表里已有条码”假通过

Favorite 表可能已显示 45127366，若 OCR 区域过大，pre-check 会以为输入完成而跳过 type_text。 成功做法：断言区域仅覆盖输入框行。

性能：能 OCR 就不用 visual_question

日文假名 OCR 不稳，故锚点用 ASCII/汉字/数字；VQ 只留给全选反白、金额框、済 等真视觉问题。

“成功”在系统里的精确定义

不是模型说成功，而是：每个步骤的 StepVerificationResult = passed （business 模式且 basis 可信），全部步骤完成 → Run status = PASSED， 并留下可回放的帧证据与 action_tags 审计计数。

成功案例的共同剧本

① 状态已知（空车/环境可用）→ ② 单一意图步骤 → ③ 优先确定性断言 → ④ 视觉只解歧义 → ⑤ 支付等待外部模拟器副作用 → ⑥ 硬终点（済）收口。
