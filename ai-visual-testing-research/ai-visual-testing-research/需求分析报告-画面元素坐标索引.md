# 需求分析报告：画面—元素坐标索引与视觉分析旁路

**主题**：通过"截图离线分析 + 代码静态分析"建立画面与元素的多对多坐标索引，使运行时的确定性操作不再依赖视觉大模型

**日期**：2026-08-05

**状态**：需求分析（未进入设计与实现）

**分析对象**：`ai-visual-testing-research/vnc_agent`（VNC Agent）+ `/mnt/d/POJ/NodeMaster`（被测 POS 系统）

**证据基础**：608 张历史运行截图、4 次真实 run 的分阶段计时、现有 UI 分析产物（189 画面 / 5788 元素）、运行时数据库（`data/vnc_agent.db`）

---

## 一、执行摘要

### 1.1 结论

**提案方向成立，建议立项，但需要修正三处关键假设，否则按原始描述实现会得到一个"建不起来关系、也省不了多少时间"的系统。**

| 判断项 | 结论 |
|---|---|
| 思路是否可行 | ✅ 可行，且基础设施已完成约 70% |
| 是否需要新建大量组件 | ❌ 不需要，主要是打通与修正既有模块 |
| 能否消除视觉模型调用 | ⚠️ 能消除 grounder，但那不是最大开销 |
| 原始方案的元素归并规则 | ❌ 实测会导致多对多关系恒为空，必须修改 |
| 画面版本管理 | ✅ 必须要，且系统当前完全无法自行感知画面变更 |

### 1.2 三处必须修正的假设

**修正一：坐标不能来自代码，身份不能来自坐标。**
现有静态分析产出的 5788 个元素中，带坐标的为 **0 个**。这不是"还没做完"，而是原理限制——4196 个 XAML 元素是相对布局，1018 个 Razor/HTML 元素是运行时布局。正确分工是：**代码提供稳定身份，截图提供坐标观测**。

**修正二：元素归并不能用"位置和尺寸完全相同"。**
实测 103 个跨画面复现的文本元素中，bbox 完全一致的为 **0 个**。按精确相等归并，每个画面的每个元素都会被判为独立元素，多对多关系退化为一对一，索引失去全部价值。应改为 **语义一致 + IoU 容差 + 容器相对坐标**。

**修正三：收益测算的目标搞错了。**
提案瞄准的 grounder 调用在实测中只占单次运行总耗时的 **3.7%～37%**（方差极大）。真正的大头是 planner（每次约 9.5 秒）、capture（每次约 1.4 秒 × 数十次）与 verification（每次约 6 秒）。同一套画面身份索引**可以**顺带砍掉 planner 与 verification，但这必须写进需求范围，否则项目做完了速度只改善个位数百分比。

### 1.3 预期收益

在完整实施（含 planner 旁路）的前提下，对已建立索引的稳定画面：

- 单步耗时从「planner 9.5s + grounder 6~15s + capture 1.4s」降至「capture 1.4s + 模板校验 <50ms」
- 单次完整用例运行预计从 **150～225 秒降至 40～60 秒**
- 模型调用成本按调用次数计降低约 70%～80%

在仅实施 grounder 旁路（即提案的原始范围）的前提下：

- 预计仅改善 **5%～20%**，投入产出比不成立

## 二、问题定义与量化现状

### 2.1 用户反馈的问题

> "经常有点错，时间慢"

### 2.2 实测：时间花在哪里

取 `artifacts/runs/` 下最近 4 次真实运行的 `performance_summary.stage_totals_ms`：

| 阶段 | run 7392616a（总 224s） | run 867660a6（总 156s） | run e261f92c（总 41s） |
|---|---|---|---|
| **planner** | **48.7s**（5 次 @ 9.7s） | **55.4s**（6 次 @ 9.2s） | 11.5s（2 次 @ 5.8s） |
| **capture** | **40.0s**（29 次 @ 1.4s） | 19.9s（20 次 @ 1.0s） | 4.7s（5 次 @ 0.9s） |
| **verification** | **35.7s**（6 次 @ 6.0s） | ~0 | ~0 |
| OCR | 22.5s（14 次） | 4.1s（10 次） | 2.7s（5 次） |
| **grounder** | **8.2s**（1 次） | **58.4s**（4 次 @ 14.6s） | 6.3s（1 次） |
| template | 0.03s | 0.01s | 0.01s |

**关键读数**：

1. grounder 单次成本高（6～15 秒），但**调用次数少**——因为 `ActionPolicy.resolve` 在唯一 OCR/模板命中时本就不调用它。它在总耗时中的占比在 3.7%～37% 之间剧烈波动。
2. planner 每次 9～10 秒且**每步必调**，是最稳定的大头。
3. capture 单次约 1 秒，但一次运行抓 20～29 帧，累计 20～40 秒，**与模型完全无关**，属于 VNC 传输与稳定性等待成本。
4. 上述 4 次 run 状态**全部为 failed**。"慢"与"点错"高度可能同源：定位不稳 → 重试 → 迭代次数翻倍 → 既慢又错。

### 2.3 结论

**性能问题不是"视觉分析太慢"，而是"每一步都要重新问模型"。** 提案的价值不在于替换 grounder，而在于让**已知画面上的已知操作完全不需要问模型**——包括不问 planner"下一步做什么"，不问 verification"做成了吗"。

## 四、关键实测发现

以下 6 项发现构成需求的事实依据。测量方法见附录。

### 发现 1：静态代码分析产出不了坐标（原理限制，非工程遗留）

对 `ui-analysis-bundle-v1/elements.jsonl` 全量统计：

```
元素总数                          5788
带 normalized_bounds 的            0
置信级别                          全部为 statically_inferred
```

按框架拆分：

| 框架 | 画面数 | 元素数 | 带坐标 | 静态可得坐标？ |
|---|---|---|---|---|
| xaml (WPF) | 86 | 4196 | 0 | ❌ Grid/StackPanel 相对布局 |
| razor | 53 | 882 | 0 | ❌ 运行时布局 |
| winforms | 40 | 574 | 0 | ⚠️ Designer.cs 有设计期 Location/Size，需 DPI 与客户区变换 |
| html | 10 | 136 | 0 | ❌ 运行时布局 |

**需求含义**：坐标的权威来源**必须**是截图观测。代码的职责限定为提供稳定身份、画面归属与跳转关系。

### 发现 2：元素记忆当前 0 命中，根因是用大模型生成的散文当主键

`memory/service.py:129` 的查找逻辑：

```python
element = await self.repo.find_element(page.page_id, label)   # label = 归一化后的自由文本
```

数据库中实际存储的 `target_label`：

```
'小計'
'金券'
'标题以 scanner 开头的窗口缩略图内部的浅色预览区域，位于标题文字下方约30像素处'
"标题为 'scanners..' 的窗口缩略图预览区域（包含密集黑色条码/文本列表）"
```

元素身份来自 planner 每轮现编的自然语言描述，措辞变化一个字精确匹配即失效。累计成果：

```
page_memories        5 条
element_memories     8 条
4 次 run 的 element_memory 命中次数   0
```

**需求含义**：元素身份必须由稳定标识符定义（`ui_index` 已有 5788 个），不能由模型输出的描述文本定义。**这是全案性价比最高的单点修正。**

### 发现 3：跨画面精确坐标相等的元素为零——原始归并规则会使索引失效

**测量**：608 张截图按感知哈希聚类，取 12 个最大画面簇的代表图分别 OCR，统计跨画面复现的文本元素。

```
出现在多个画面上的文本         103 个
其中 bbox 完全一致的           0 个
其中可比对且 bbox 不一致的      35 个
```

实例：

| 文本 | 画面 A | 画面 B | 画面 C |
|---|---|---|---|
| `チャージ` | [942,613,1007,646] | [942,611,1008,642] | [942,610,1008,643] |
| `ScannerSimulator` | [15,9,110,23] | [14,7,110,25] | [27,39,126,61] |
| `NonPLU` | [164,223,209,240] | [164,223,209,239] | [256,307,304,326] |
| `端末番号:3112` | [644,26,790,48] | [674,26,811,48] | — |

差异来源有三类，**没有一类代表"不同元素"**：

- **1～3 px 抖动**：OCR 自身噪声（`チャージ`）
- **数十 px 位移**：窗口被拖动（`ScannerSimulator` 模拟器有前台/背面两种状态）
- **上百 px 位移**：同一容器在不同画面中的整体位置不同（`NonPLU`）

反向测量同样不支持精确相等规则：

```
跨画面 bbox 精确相同的位置      115 处
其中文本一致（正确归并）        85 处
其中文本不同（存在误并风险）     30 处
```

误并实例（同位置同尺寸但内容随时间变化）：

```
(860, 4, 1020, 24)   画面A: '2026/07728 14:20'   画面B: '2026/0772315:55'    ← 时钟
```

**需求含义**：位置+尺寸相等**既不充分也不必要**。归并判据须改为三条同时成立：语义一致（role 相同、归一化文本一致）、几何相容（IoU ≥ 阈值，建议 0.8）、坐标相对于所属容器而非屏幕。

### 发现 4：同画面跨运行的坐标也不完全稳定

**测量**：最大画面簇内，跨 13 次不同 run 取 10 张同画面截图分别 OCR。

```
在 10 张中均出现且唯一的文本元素     30 个
10 次采样 bbox 完全一致的           26 个（87%）
存在抖动的                        4 个（13%），幅度 1～5 px
```

抖动明细：`ポイント` dx=1 dy=2 dw=1 dh=2；`次ページ` dx=2 dy=2 dw=3 dh=5；`取引` dx=1 dy=2 dw=1 dh=2；`万券` dh=1。

而这 10 张图之间的像素差异仅 **0.005%～0.018%**（时钟、交易计数器等局部变化）。

**需求含义**：即使输入几乎相同，OCR 输出也带 1～5 px 噪声；若坐标来源改用视觉大模型，噪声将达数十像素级。**任何依赖精确坐标相等的设计都不成立**，坐标必须以"观测样本集合 + 容差区间"建模，而非单一精确值。

### 发现 5：画面指纹对元素级改动几乎无感——系统无法自行发现画面改了

**测量**：以真实截图为基线，用现有 `memory/fingerprint.py`（pHash 0.375 + OCR 文本 0.375 + 布局 0.25）计算相似度，阈值取 `agent.yaml` 现值 high=0.88 / medium=0.72。

| 场景 | 相似度 | 判级 | 后果 |
|---|---|---|---|
| 完全相同（sanity） | 1.0000 | high | ✅ |
| 同画面·另一次 run | 1.0000 | high | ✅ |
| **抹掉一个按钮**（4 个不同按钮分别测试） | **0.9695 ~ 0.9762** | **high** | ⚠️ 仍判为同一画面 |
| **一个元素下移 20px** | **0.9941** | **high** | ⚠️ 仍判为同一画面 |
| 底部面板整体上移 20px | 0.8762 | medium | 降级为提示 |
| 抹掉 4 个按钮 | 0.8690 | medium | 降级为提示 |

**删除一个按钮，相似度仅下降约 3%，仍稳居 high 档。** 系统会以高置信度使用历史坐标去点击一个已不存在的位置，且不产生任何告警。

**需求含义**：画面指纹是**身份**判据，不是**变更**判据。必须引入显式的画面版本管理，且**系统无法靠自己推断版本变更**——这是版本管理需求的根本依据。

### 发现 6：元素级模板校验能够兜住指纹漏掉的全部改动

**测量**：以同一元素的模板图，用现有 `match_element_template`（阈值 0.85，邻域扩展 0.5）在各场景中定位。

| 场景 | 结果 |
|---|---|
| 原图 | 命中 score=1.000 |
| 同画面·另一次 run | 命中 score=1.000 |
| 该按钮被删除 | **未命中 → 拒绝直接点击** |
| 该按钮下移 20px | **未命中 → 拒绝直接点击** |
| 该按钮下移 120px | **未命中 → 拒绝直接点击** |

**发现 5 中指纹漏掉的三种改动，元素级模板校验全部捕获，且对正常的跨 run 波动零误报。**

**需求含义**：任何"走缓存坐标的直接点击"都必须先过元素级模板校验。这一层不是性能优化，而是"人忘了通知系统画面改了"时唯一的安全网，成本仅 1～2ms。

## 五、需求方案

### 5.1 核心设计原则

> **身份由语义决定，坐标是身份在特定观测条件下的属性。**

- **身份** = `(screen_id, element_id, version)`——来自代码静态分析，稳定、可追溯到源文件行号
- **坐标** = 该身份在 `(画面版本, 容器, 分辨率)` 下的观测样本集合——来自截图分析，带容差
- **决策** = 命中索引 → 元素级模板校验 → 通过则直接操作，不通过则回退现有视觉链路

### 5.2 需求分组

#### A. 元素身份与归并（对应发现 1、3、4）

- A1 元素身份以 `ui_index` 的稳定 `element_id` 为主键，禁止使用模型生成的描述文本作为主键
- A2 跨截图归并同一元素须同时满足：role 相同、归一化文本一致（或均为空时层级路径一致）、IoU ≥ 阈值（建议 0.8，可配置）
- A3 坐标以容器相对偏移存储，不存屏幕绝对坐标；容器定位复用 feature 024 的 `geometry` / `scaling` 能力
- A4 每个元素坐标保留多个观测样本，取聚类中心与容差区间，而非单一精确值
- A5 元素须分类为 **static** 与 **dynamic**；dynamic 元素（时钟、商品明细行、金额、交易号）不进入坐标索引，永远走现有视觉链路

> ⚠️ **待量化**：12 个画面样本中，OCR 项数在 13～103 之间波动，商品列表类画面（S3/S6/S8/S9）的 OCR 项数达 99～103，dynamic 元素占比可能过半。此比例直接决定本提案的收益上限，**建议在设计阶段前完成统计**。

#### B. 画面版本管理（对应发现 5）

- B1 版本粒度为**单个画面**，而非整个 bundle。`screen_id` 保持稳定，新增 `version` 维度；坐标挂在 `(screen_id, version)` 上
- B2 版本具备生命周期状态：`unverified`（新分析产出，未经真实运行验证）→ `active` → `stale`（已标记待重分析）→ `superseded`
- B3 **标记 stale 等于降级，不等于停用**——退回现有视觉链路，不得使步骤失败。误标一个画面不应瘫痪整个测试套件
- B4 版本选择依据画面指纹匹配，**不依据"取最新"**。测试环境可能新旧版本 POS 并存，历史运行的回放也需使用当时的版本。版本选择键：`(screen_id, 分辨率, source_revision)`
- B5 失效须级联：某元素失效时，指向它的 `transitions` 与 `element_memories` 中挂载的模板图一并作废。现有 `element_memories` 表缺少关联画面版本的字段，需补充
- B6 **"标记失效"与"重建"分离**。重建需要新截图，而新截图只有实际运行才有。流程为：标记 stale → 下次运行至该画面时自然走视觉链路 → 留存该帧作为新版本素材 → 离线重建 → 新版本落为 `unverified` → 连续 N 次验证通过后转 `active`。此模式与现有 `template_refresh_min_consecutive_successes: 3` 一致，直接沿用

#### C. 变更感知入口（三层，缺一不可）

| 层 | 形态 | 覆盖范围 | 依据 |
|---|---|---|---|
| **L1 手动入口** | CLI/API 指定画面失效；按 `source_path` 批量失效 | 权威、即时 | 用户明确需求 |
| **L2 代码侧自动失效** | 按源文件内容哈希 diff → 反查受影响画面 → 自动标记 | 代码引起的变更 | 189/189 画面有 `source_path`，5788/5788 元素有 `source_evidence`（文件:行号） |
| **L3 运行时兜底** | 点击前元素级模板校验，未命中即拒绝直接点击 | 一切未被通知的变更 | 发现 6 |

**L2 实施提示**：`/mnt/d/POJ/NodeMaster` 下的 `.git` 是**空目录，项目不在版本控制下**，无法依赖 `git diff`。但 bundle 的 `manifest.yaml` 已记录 `source_revision: "tree:6746094166b47e15..."`，说明构建器已在计算源码树内容哈希——改为按文件粒度记录即可，不依赖任何版本控制系统。

- C1 所有版本变更须记录 who / when / why 至审计（沿用 `IndexUsageAuditRecord` 与 `replay_patches` 的既有模式）
- C2 L1 入口须支持"仅标记"与"标记并触发重建"两种语义

#### D. 运行时旁路（对应发现 2、6，及第二节的收益测算）

- D1 **grounder 旁路**：画面指纹命中 + 元素身份命中 + 模板校验通过 → 直接产出坐标，跳过 grounder。此链路已存在（`element_memory_direct_click`），只需修正 A1 即可激活
- D2 **planner 旁路**（收益主体）：已知画面 + 已知用例步骤 → 动作确定，跳过 planner 调用。此形态已存在于 feature 016 replay，需查明其未生效的原因
- D3 **verification 旁路**：已知画面的预期结果可用 OCR/像素比对判定，替代 `visual_question` 调用
- D4 任何旁路失败一律**静默回退**至现有视觉链路，不新增失败类型、不改变步骤最终语义
- D5 旁路命中与跳过须计入 `model_call_skipped` 审计（现有机制）

#### E. 离线建库

- E1 建库为离线批处理，可并发；**运行时禁止并发调用多个模型**（并发只会更慢更贵，运行时目标是零模型调用）
- E2 建库素材优先复用 `artifacts/runs/` 下已有的 608 张历史截图，无需新增采集
- E3 建库产物回填至现有 bundle schema 的 `normalized_bounds` 字段，置信级别置为 `visually_confirmed`——**schema 无需变更**，字段与置信级别均已预留

### 5.3 明确排除范围（Out of Scope）

- 不改变步骤的最终判定语义与失败类型
- 不替代 OCR/VLM 链路，只在其之前增加一条快速通道
- 不处理 dynamic 元素的坐标缓存
- 不引入跨分辨率的坐标推算（当前环境固定 1024×768，587/608 张截图为该分辨率）

按"先验证假设、再扩大投入"的顺序分四期。**每期独立可验收，任一期结论为负都可以停止而不浪费前期投入。**

- **验收**：`memory_hits.element_memory` 从 0 变为正数；重复运行同一用例时 grounder 调用次数下降

- **验收**：产出量化报告，明确本提案的收益上限；据此决定是否继续

### 第 2 期：离线建库 + grounder 旁路（预计 2～3 人周）

## 八、总体建议

1. **立项，但先做第 0 期与第 1 期。** 这两期合计不到 10 人日，却能验证整个提案最关键的两个假设（身份修正是否有效、dynamic 占比是否可接受）。在此之前不建议投入建库工作量。

2. **不要先建大库。** 现有 015/016 已经是本提案的雏形却双双未生效，先查清根因比新建一套更重要——极可能是同一个病根，修一处救活两个模块。

3. **准确性优先于速度。** 4 次运行全部失败的现实说明，"慢"很可能是"不准 → 重试 → 迭代翻倍"的结果。先修准确性，速度会自然回来一部分。

4. **版本管理不是附加功能，是安全前提。** 发现 5 已证明系统对画面变更完全无感知且失败模式是"自信地点错"。在坐标索引投入使用的**同时**，L3 运行时校验必须一并上线，不可延后。

## 附录：测量方法与可复现性说明

本报告全部数据来自对现有产物的只读测量，未修改任何代码或配置。

| 数据 | 方法 | 样本 |
|---|---|---|
| 耗时分解 | 直接读取 `artifacts/runs/*/report.json` 的 `performance_summary.stage_totals_ms` | 最近 4 次 run |
| bundle 统计 | 遍历 `ui-analysis-bundle-v1/*.jsonl` | 全量 189 画面 / 5788 元素 |

| OCR 抖动 | 最大画面簇内跨 13 次 run 取 10 张，用项目配置的日语 PP-OCRv4 模型分别识别后比对 bbox | 30 个共现文本 |
| 跨画面归并 | 12 个最大画面簇各取代表图 OCR，交叉比对 bbox 与文本 | 103 个跨画面文本 |

### 方法局限（如实说明）

- 画面聚类使用粗粒度 16×16 哈希，可能将高度相似但实际不同的画面并入同一簇；跨画面比对因此可能低估差异
- 指纹敏感度测试中的"删除按钮""元素位移"为**合成改动**（纯色填充与贴图），与真实的界面改版在抗锯齿、阴影、周边重排上存在差异，实际相似度可能略低于测得值，但不改变"元素级改动无法被指纹捕获"这一结论的方向
- OCR 抖动测量仅覆盖单个画面簇的 30 个文本元素，其他画面的抖动幅度未测
- 耗时数据来自 4 次运行，且全部为失败运行，成功运行的耗时构成可能不同
