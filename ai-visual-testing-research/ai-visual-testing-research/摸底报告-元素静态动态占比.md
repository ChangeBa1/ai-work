## Q2. 608 张真实截图：static / jitter / dynamic

### 2.1 样本与方法

| 项 | 值 |
|----|-----|
| 截图样本 | `vnc_agent/artifacts/runs/*/bundles/*/safe_evidence.png` → **n=608**（与题述 608 一致；全树 `*.png` 另有 zoom 等共 651） |
| 运行目录 | **80** 个 run_id；带 `report.json` 的 **78** |
| 精确去重 | `content_hash` → **560** 唯一（精确重复率 7.9%） |
| 画面聚类 | 16×16 aHash，汉明距离 ≤10 并查集 → **37** 个画面簇；其中 **17** 簇含 ≥2 个不同 content_hash |
| **元素级（主结论）** | 对 17 个多哈希簇各取最多 3 张代表图 **RapidOCR**（共 OCR **48** 张唯一图）→ 同簇内按归一化文本对齐中心点，轨迹 **n=517** |
| 分类阈值（元素中心距 dmax） | **static**：dmax ≤ 0.5 px；**jitter**：0.5 < dmax ≤ 5 px；**dynamic**：dmax > 5 px；**dynamic_presence**：只在 1 个样本出现（内容有无变化） |
| **瓦片代理（辅）** | 17 簇 × 16×16 格 → **4352** 瓦片；灰阶 MAD：static <1.5，jitter <12，否则 dynamic |

### 2.2 元素级比例（OCR 文本轨迹，n=517）

| 类别 | 条数 | 占比（/517） |
|------|-----:|-------------:|
| **static**（位置完全一致） | **398** | **77.0%** |
| **jitter**（1–5 px） | **31** | **6.0%** |
| **dynamic**（位移 >5 px） | **3** | **0.6%** |
| **dynamic_presence**（同屏簇内文本时有时无） | **85** | **16.4%** |

若把 `dynamic_presence` 与 `dynamic` 合并为「不宜坐标索引」：**88 / 517 = 17.0%**。  
若只把「同文出现 ≥2 次」的 432 条作分母（398+31+3）：static **92.1%**，jitter **7.2%**，dynamic **0.7%**。

### 2.3 瓦片级比例（辅证，n=4352）

| 类别 | 瓦片数 | 占比 |
|------|------:|-----:|
| static | 3855 | 88.6% |
| jitter | 250 | 5.7% |
| dynamic | 247 | 5.7% |

瓦片 dynamic 高于 OCR dynamic：因金额/明细区域像素变化大但 OCR 文本键可能被判为 presence 变化而非位移。

### 2.4 对 IoU / 索引覆盖率的含义

| 设计参数 | 建议（基于本次样本） |
|----------|----------------------|
| 模板/坐标 IoU 阈值 | **0.85–0.90** 可覆盖 static+jitter（≈83% OCR 轨迹或 ≈94%「重复出现文本」） |
| 抖动容忍 | 中心点 **±5 px**（或 IoU 放宽到 0.80）覆盖 jitter 层 |
| 索引覆盖率**上限（乐观）** | 不宜宣称 >**80–85%** 元素可纯坐标直点：约 15–17% 文本轨迹是 presence/大位移动态 |
| 索引覆盖率**上限（收银主屏）** | 本次 OCR 簇含大量模拟器窗口标题；**收银主屏动态比例可能更高**（购物车行、合计金额），需单独再抽样，不宜直接外推 77% static |

### 3.4 与 Q1 的关系 & 对「代码侧自动失效检测」的价值

| 层 | 是否配置表驱动 | 代码侧失效检测价值 |
|----|----------------|-------------------|
| WinForms 574（模拟器） | **基本否**（几何在 Designer） | 低：改表不会动这些窗体；宜用 **Designer/哈希** 侦测 |
| 收银 WPF 预置/功能按钮 | **是** | **高**：主数据变更 ⇒ 按钮集合/顺序/标签变，坐标索引必失效；应用 **表快照哈希 / 行版本** 作为失效信号 |
| 金额、明细列表 | 交易数据驱动 | 高：应标 dynamic，禁止入 approved 坐标索引 |

结论：**配置表驱动布局成立，但主要打在 WPF 收银菜单按钮面，不是 574 WinForms 集合。**  
「代码侧自动失效检测」对 **Preset/Function 菜单主数据 + 关键 XAML/cs 消费点** 价值最大。

## Q4. Feature 016 record-replay 为何只有 1 脚本 / 6 步？

### 4.1 实测库存

| 数据源 | 数量 |
|--------|------|
| `vnc_agent.data` → `replay_scripts` | **1**（`test_case_id=pos-buy-bag-mixed-kinken-cash-001`，`source_run_id=5586df5a-…`，version=1） |
| `replay_steps` | **6**（order 0–5：加购物袋→小计→金券金额→金券→现金余额→…） |
| 每步 `success_count` / `failure_count` | **全部为 0**（从未被 replay 成功/失败计数） |
| `replay_patches` | **0** |
| 磁盘模板 `artifacts/replay/templates/*.png` | **6**（与 6 步一一对应） |
| 测试用例 `mode: replay` | **0**（全部为 `mode: explicit`） |

### 4.2 配置与能力（排除「没实现」）

```yaml
# agent.yaml
replay:
  enabled: true
  auto_generate: true
  patch_auto_apply: false   # ADR：自愈补丁不自动落地
```

代码面：`ReplayRecorder` / `ReplayPlayer` / CLI `replay_scripts_cmd` / 单测与 e2e `test_scenario_20_record_replay.py` 均存在（源码提及 replay 的模块 **28** 个）。  
→ **能力不足不是主因**。

### 4.3 运行为何没长大？

| 观察 | 证据 | 解释 |
|------|------|------|
| 生成门槛高 | Recorder 仅在**整单 exploration fully-passed** 后落库；78 report 中 **passed=7 / failed=71** | 绝大多数跑法产不出脚本 |
| 唯一脚本来源 | 唯一 script 绑定 run `5586df5a`（passed，6 步 mixed kinken） | 与「偶尔一次全绿」一致 |
| 从未回放 | 6 步 success/failure 全 0；无 `mode:replay` YAML | **接入成本 / 流程未采用**：没有人用 replay 模式跑回归 |
| 可观测 | report 内 counter_events 样本未见 `replay_step_replayed` 规模使用 | 运行态几乎不走 player |
