# Feature Specification: 应用感知增强插件框架（Grounding 前置子窗口裁剪放大）

**Feature Branch**: `024-app-perception-plugins`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "像 pos-scan-magazine-checkout.yaml 这样的测试 case，自动化跑的时候操作模拟器经常点错或者操作失败，主要是 UI 识别得也不好。现在想对 POS 应用做优化，最好是可插拔的插件形式：当截图中有模拟器、并且本步骤需要操作模拟器时，把模拟器窗口单独抠出来放大，再交给 AI 去识别，通过各种相对位置的计算得出准确结果。但还有一种情况：截图中虽然有模拟器，但本步骤并不是要操作模拟器，这时就不需要放大处理。"

## 背景与问题定义

真实运行证据（`artifacts/runs/cfa922e8-.../bundles/9874e7a4-.../safe_evidence.png`，1024×768）：被测环境把一个小的辅助工具窗口叠放在主业务画面左上角，该子窗口只占整帧约 **420×615 像素（约 33% 面积）**，窗口内部控件（单行输入框、复选框、按钮、密集表格）在全帧分辨率下每个只有十几到二十几像素高。全屏 OCR 与全屏 Grounding 在这种尺度上：

- 读不准子窗口内的小字标签，导致 `target.text` 无法吸附；
- 分不清"输入框"与其正下方仅隔十几像素的表格首行；
- 把落点推到子窗口边界之外，直接点到背后主画面的业务按钮上（真实事故：本该点子窗口底部的按钮，落点掉到窗口外主画面的按钮区）。

用例作者已经用大量自然语言"相对位置补丁"手工补偿（"目标按钮与某复选框在同一水平线上、位于其右侧"、"输入框是标签 A 与标签 B 之间的白色长条"）。这说明**信息本身在像素里是确定可判的，只是在全帧分辨率下看不清**——属于观察分辨率问题，不是推理能力问题。

现有 feature 014（`zoom_reground`）已经具备"裁剪 + 放大 + 重新 OCR + 重新 Grounding + 严格坐标还原"的全部原语，但它是**事后恢复**：只有当 `target_not_found` / `grounding_low_confidence` 已经发生、并且第一档恢复（recapture / second_candidate）也失败之后才会触发，且 ROI 由**失败目标的候选 bbox** 推导。对于"整类步骤在同一个小子窗口里操作"这种**先验已知**的情形，等到失败两次再补救，既浪费迭代预算，又要冒中间那两次误点击真实改变被测系统状态的风险（误点击可能触发弹窗、改变交易状态，事后不可撤销）。

本 feature 引入**前置增强**：在调用 Grounder **之前**主动判定"本步骤是否在某个已知子窗口内操作"，是则用该子窗口的裁剪放大图去 Grounding。同时把这条能力做成**可插拔扩展点**——核心代码不得知道任何被测应用的名字、窗口标题或控件词汇（Constitution VI 红线）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 子窗口内的小控件被前置放大后一次点中 (Priority: P1)

测试工程师的步骤要点击一个叠在主画面上的小工具窗口内部的按钮。系统在本次迭代调用 Grounder 之前就识别出"当前帧里存在已注册的子窗口，且本步骤的目标语义指向该子窗口内部"，于是把该子窗口区域裁剪出来按自适应倍率放大，用放大图重新 OCR、并以放大图作为 Grounding 输入；模型返回的放大图坐标被严格还原为原帧像素坐标后，走**完全未改动**的既有 action policy / 执行 / 独立验证闭环，第一次就点在正确像素上。

**Why this priority**: 这是本 feature 的直接动因，不解决则小子窗口场景持续误点。

**Independent Test**: 离线 e2e——固定截图 fixture（子窗口叠在主画面上）+ 脚本化 Grounder：对全帧图请求返回低置信/未找到，对放大图请求返回放大图坐标系内的高置信候选；断言最终点击坐标逐像素等于手工计算的 `round(bbox/scale) + crop_offset`，且该迭代的增强审计记录 `activated=true`。

**Acceptance Scenarios**:

1. **Given** 全局开关开启、某插件对当前 target 启用、当前帧中该插件的必需锚点全部命中、本步骤被判定为"在该子窗口内操作"，**When** 本迭代需要 Grounding，**Then** 系统先做一次 ROI 裁剪+放大观察，并以放大图（及与放大图同一坐标系的提示候选）构造 Grounding 请求。
2. **Given** 放大图上的 Grounding 候选，**When** 还原到原帧坐标，**Then** 结果精确等于 `round(v / scale_factor) + crop_offset`，越界/退化候选被严格拒绝（不 clamp、不猜）。
3. **Given** 前置增强产出可执行动作，**When** 执行并验证，**Then** 步骤按既有语义判定，本 feature 不引入任何新的最终态、不新增 FailureType。
4. **Given** 前置增强已激活的迭代，**When** 统计模型调用，**Then** Grounder 调用次数与未增强路径**相同**（增强只替换送模型的图像，不追加 Grounding 调用）。

### User Story 2 - 画面里有子窗口但本步不操作它时必须不激活 (Priority: P1)

同一份截图里既有子窗口也有背后的主画面。当本步骤的目标是**主画面**上的控件（例如"点击主画面中部空白处让子窗口退到背面"、以及其后所有主画面业务步骤）时，系统必须**不激活**增强，按现状走全帧路径。由于激活**只能**来自用例的显式声明（FR-011/FR-013），这类步骤只要不写声明即天然安全——用例作者不需要做任何"排除"动作。

**Why this priority**: 假阳性（不该放大却放大）是**更危险**的方向——它把 Grounder 的视野裁到子窗口内，窗口外的真实目标要么找不到（浪费迭代 + 触发恢复），要么被模型在窗口内"强行找出"一个错的东西并点下去，直接造成误操作。假阴性（该放大却没放大）只是退回今天的行为，不比现状更差。因此激活来源被限制为显式声明，缺省一律不激活。

**Independent Test**: 离线 e2e——同一张 fixture 截图，一组步骤声明了子窗口范围、另一组未声明（目标在窗口外主画面）；断言前者 `activated=true`、后者 `activated=false` 且原因码为 `not_declared`，后者的 Grounding 请求与关闭本 feature 时**逐字节相同**。

**Acceptance Scenarios**:

1. **Given** 子窗口在画面中清晰可见且能被成功检测，**When** 本步骤**未声明** `perception_scope`，**Then** 不激活增强（原因码 `not_declared`），且 MUST NOT 执行任何检测运算——"看得见窗口"本身绝不构成激活理由。
2. **Given** 用例步骤显式声明 `perception_scope: "none"`，**When** 该步骤执行，**Then** 不激活（`declared_off`），语义与未声明一致。
3. **Given** 步骤声明了插件 X，**When** 检测到的"子窗口"矩形面积占整帧比例超过配置上限（检测退化成了近似全屏），**Then** 不激活（`roi_not_subwindow`，放大无收益且会掩盖窗口外区域）。
4. **Given** 步骤声明了插件 X 而当前画面上根本没有该窗口，**When** 判定激活，**Then** 按 FR-013a 处理（默认回退全帧并强制留下 `declared_but_undetected` 审计），MUST NOT 静默。

### User Story 3 - 能力完全可插拔，核心无业务语义 (Priority: P1)

平台工程师可以为任意被测应用新增一个感知增强插件而**不改动任何核心代码**：以声明式档案（数据）描述"这个子窗口长什么样、它内部有哪些锚点词、什么样的步骤算是在它里面操作"；通过配置为某个 target 或某个测试用例启用/停用某些插件；核心的 perception / planning / grounding / runtime 代码中不得出现任何被测应用、窗口标题或业务控件词汇。

**Why this priority**: 这是用户明确要求的"可插拔"验收标准，也是 Constitution VI（业务无关核心）的硬约束；若核心里出现业务分支，本 feature 即为不合格。

**Independent Test**: (a) 静态检查——对核心代码目录做禁词扫描（被测应用名/窗口名/业务控件词），零命中；(b) 用**两个互不相关的 GUI 场景**（不同应用、不同窗口结构）各写一份声明式档案与 fixture，同一套核心代码在两者上都能正确检测、激活、还原坐标；(c) 移除某档案文件后，对应场景自动退回全帧路径，其它场景不受影响。

**Acceptance Scenarios**:

1. **Given** 一份新的声明式插件档案被放入插件目录，**When** 运行启用了该插件的用例，**Then** 无需改动核心代码即可生效。
2. **Given** 两个互不相关 GUI 场景的档案同时注册，**When** 分别运行，**Then** 各自只在自己的场景上激活，互不干扰；同一帧上多个插件同时检测成功时按确定性规则唯一选中一个（不并发放大）。
3. **Given** 核心代码评审，**When** 扫描被测应用/业务词汇，**Then** 零命中；所有业务词汇只存在于档案文件、测试用例与 fixture 中。

---

### User Story 4 - 全链路可观测与一键回滚 (Priority: P2)

测试工程师复盘一次运行时，能对每一个需要 Grounding 的迭代看到：是否做了感知增强、命中哪个插件、检测到的子窗口 ROI 四元组、检测方法与置信度、激活/否决的判定依据（哪条证据触发或否决）、放大倍率、放大图产物路径；**未激活时同样有记录与否决原因**。关闭全局开关后，系统行为与本 feature 之前逐字节一致。

**Why this priority**: 增强改变了送模型的图像与坐标系，没有审计就无法排查坐标还原与误激活；回滚开关是上线安全阀。

**Independent Test**: 断言迭代记录含增强审计对象的全部字段并进入 JSON/HTML 报告；关闭开关后的 Grounding 请求负载与产物集合与基线逐字节一致。

**Acceptance Scenarios**:

1. **Given** 一次激活的增强，**When** 查看该迭代记录，**Then** 含插件名、ROI、检测方法、检测置信度、激活结论、判定依据、缩放因子、放大图产物路径。
2. **Given** 一次被否决的增强（检测成功但未激活，或检测失败），**When** 查看该迭代记录，**Then** 含否决原因码；检测失败时不产生放大图产物。
3. **Given** 全局开关关闭，**When** 运行任意既有用例，**Then** 无增强审计记录产生，Grounding 请求与产物与基线逐字节一致。

---

### Edge Cases

- **检测失败（锚点不全 / 几何退化 / 置信度不足）**：返回"未检测到"，本轮不激活，走全帧路径（fail-open），绝不升级为失败或抛错。
- **ROI 抓屏/裁剪/放大/编码/落盘任一环节失败**：放弃本次增强，本轮回退全帧 Grounding；不消耗恢复预算、不产生 FailureType。
- **同一迭代已有 pending `zoom_reground` 计划（feature 014）**：`zoom_reground` 优先（它是针对**已发生失败**的定向补救），本轮跳过插件增强；**任何单次 Grounding 请求上至多存在一次裁剪+放大变换，绝不叠加**。
- **同一迭代命中 feature 023 的 postmortem 修正点击 或 feature 015 的 memory 高置信直接点击**：这两条路径根本不调用 Grounder，插件增强不参与（增强只作用于真正发起 Grounding 调用的分支）。
- **多个插件在同一帧同时检测成功**：按 (检测置信度降序, 插件名升序) 的确定性规则唯一选中一个；不并发、不合并 ROI。
- **子窗口部分超出屏幕边界**：ROI 是**观察窗口**，允许按既有 viewing-window 语义平移/收缩入界（这不是点击坐标，不违反严格拒绝语义）；收缩后小于最小尺寸时按最小尺寸在屏幕内重排。
- **子窗口检测框把目标切在边缘外**：放大图 Grounding 只能看到 ROI 内的世界；若还原后的候选贴着 ROI 边界（落在配置的边缘带内），MUST 记录该情况；是否因此拒绝候选见"未决问题 Q3"。
- **步骤声明了范围，但目标其实在子窗口外**（用例作者写错）：系统按声明执行（显式声明即作者责任），但 MUST 在审计中记录一条**只读警示**：本轮目标的文本线索（目标文本 / 邻近文本）在当前帧 OCR 上的命中项落在检测矩形之外或跨内外。该警示 MUST NOT 改变激活结论（不否决、不激活），仅用于复盘定位"声明写错了"。
- **本步骤是键盘类动作（按键、输入文本、快捷键）**：不需要坐标，通常不进入 Grounding 分支；即便进入，非坐标产出动作 MUST 不激活（`non_positional_action`）。因此对纯键盘步骤写 `perception_scope` 是无害但无效的。
- **同一步骤内多次迭代**：每步激活次数受上限约束（默认 1 次）；达上限后本步骤后续迭代一律走全帧路径并记录原因，避免"每轮都放大"的隐性成本膨胀。
- **增强后的 Grounding 仍然失败**：按既有失败归因与恢复序列处理；feature 014 的 `zoom_reground` 仍可在后续迭代触发（它从原帧重新裁剪，不与本次增强叠加）。
- **遮罩区域与 ROI 相交**：沿用既有安全遮罩落盘语义（遮罩矩形按裁剪偏移平移、按缩放因子放大）；敏感步骤禁止私有持久化时只落盘遮罩版本。
- **插件档案自身非法（缺必需锚点、几何约束矛盾、倍率越界）**：配置加载期即失败并给出档案路径与字段级原因，MUST NOT 在运行期静默降级。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 扩展点与可插拔性

- **FR-001（扩展点定义）**: 系统 MUST 定义一个通用的"应用感知增强"扩展点（协议接口），其契约仅使用通用结构：输入为当前结构化屏幕（帧标识、分辨率、OCR 项、模板匹配项）与通用步骤上下文（步骤标识、意图文本、语义动作的动作类型与目标描述），输出为"子窗口检测结果（矩形 + 置信度 + 检测方法 + 命中锚点）"与"激活投票（要求激活 / 否决 / 弃权）"。核心 MUST NOT 依赖任何具体插件实现。
- **FR-002（注册与发现）**: 系统 MUST 提供内部插件注册表，支持按唯一名称注册、按名称查找、枚举已注册插件；注册表 MUST 同时支持两种来源：(a) **声明式档案文件**（数据驱动，由核心提供的通用声明式插件实现消费）；(b) 程序化注册的代码插件（供档案无法表达的特殊场景）。重复名称 MUST 在加载期报错。
- **FR-003（启用范围选择）**: 配置 MUST 支持三级选择：全局开关（关闭即完全停用）、按被测目标（`target_id`）启用插件名列表、按测试用例步骤的显式声明覆盖。未被显式启用的插件 MUST NOT 参与任何判定。
- **FR-004（核心业务无关性）**: 核心代码（perception / planning / grounding / runtime / recovery / config 等生产模块）MUST NOT 出现任何被测应用名、窗口标题、业务控件名或场景专用分支；所有此类词汇 MUST 只存在于插件档案、测试用例与 fixture 中。本 feature 声称的通用能力 MUST 至少用两个互不相关的 GUI 场景验证（Constitution VI）。
- **FR-005（内置实现的交付形态）**: 触发本需求的场景（主画面上叠一个小工具子窗口）MUST 以**声明式档案 + fixture** 的形式交付，而不是核心代码中的实现类。

#### B'. 形状无关性与源码派生的相对几何

- **FR-005a（核心不得含任何窗口形状先验）**: 目标子窗口的形状差异极大（实测同一被测环境的 37 个窗体，宽高比跨 0.73–5.34、屏占比跨 3.3%–77.1%）。核心 MUST NOT 内置任何面积比下限、宽高比区间或"子窗口应该多大"的假设。核心只允许两条**与形状无关**的兜底：(a) 面积比上限（默认 0.95，仅用于拒绝"检测退化成整屏"）；(b) 退化尺寸下限（默认短边 24px）。逐窗口的合理性范围 MUST 由**档案**声明（档案描述的是某一个已知窗口，是形状先验的正确归属地）。
- **FR-005b（倍率与形状无关）**: 缩放因子 MUST NOT 由窗口尺寸推导。理由：可读性由**字高**决定，而这些窗体使用默认字体、字高基本恒定，与窗口大小无关；由尺寸推导倍率会让扁宽窗口纵向放大不足。系统 MUST 使用配置的固定 `default_scale`（默认 2.5，档案可覆盖），再由放大图像素总量上限二次夹紧；夹紧后低于 `min_scale` 时 MUST 放弃增强。
- **FR-005c（源码派生的相对几何，可选）**: 档案 MAY 携带一段从被测应用**界面定义源文件**导出的相对几何：设计期客户区尺寸、以及若干控件的名称、字面文本、设计期矩形与**停靠（anchor）语义**。系统 MUST 提供一个**离线生成工具**从界面定义源文件产出该段落的草稿；生成 MUST 是只读的（MUST NOT 写入被测应用源码树），且产物 MUST 经人工核对后才入库。
- **FR-005d（相对几何的运行期映射）**: 系统 MUST 能把设计期矩形映射到**运行期实测窗口边界**上，映射 MUST 尊重 anchor 语义：左/上停靠者以左/上边为基准，右/下停靠者以右/下边为基准，两侧同时停靠者随窗口拉伸，两侧皆不停靠者随尺寸差居中浮动。映射 MUST NOT 使用任何绝对屏幕坐标。
- **FR-005e（相对几何的用途，2026-07-28 真机实测后升级）**: 原红线"只能当提示、绝不能当点击坐标"的**前提是直接使用设计期绝对像素**——该前提已不成立。新做法 MUST 是：用**运行期 OCR 实测到的**锚点位置，最小二乘反解"设计坐标 → 屏幕坐标"的每轴仿射变换（缩放+平移），再用该变换推算目标控件位置。这是**运行期测量**，不是设计期假设：窗口移动、重开、DPI 改变都会让锚点跟着动，解出的变换自动跟随。
  实测依据（1024x768，4 锚点）：`x=0.9988·x_d+7.34`、`y=0.9996·y_d+30.99`，回代残差全部 ≤1.5px，平移量正好等于窗口边框+标题栏高度。
  **升级后的定位**：几何推算 MAY 直接作为点击坐标来源，但 MUST 通过下列全部安全闸（FR-005g），任一不满足 MUST 退回既有模型路径，**绝不猜**。
- **FR-005f（无 Text 控件是主要价值）**: `source_geometry.controls` MUST 同时导出**没有字面 Text 的控件**（以 `Name` 标识）。理由：输入框、无标签按钮这类控件 OCR **永远读不到**，模型只能猜——而它们恰恰是最常被点错的目标。生成脚本 MUST 一并导出。
- **FR-005g（安全闸，缺一不可）**:
  1. **锚点数量** ≥ `min_anchors_for_transform`（默认 **3**）。两点必然精确拟合、残差恒为 0，无法证伪；三点才可能相互矛盾。
  2. **回代残差** ≤ `max_transform_residual_ratio` × 窗口短边（默认 **0.02**，427px 窗口 ≈ 8.5px；实测最大 1.51px，余量充足）。
  3. **解出的缩放** ∈ `[transform_min_scale, transform_max_scale]`（默认 **[0.5, 3.0]**），防退化。
  4. **锚点跨度**：锚点在至少一个轴上 MUST 跨越窗口的 `min_anchor_span_ratio`（默认 **0.25**）。只在一角验证过的拟合，对另一角毫无约束力，MUST NOT 外推。
  5. **预测点 MUST 落在检测到的窗口边界内**，越界**严格拒绝、不 clamp**。
- **FR-005h（Anchor 语义，必须明确处理）**: 单一"每轴缩放+平移"变换**仅在窗口保持设计比例时精确**（平移、等比 DPI 缩放）。若窗口被**拉伸**，WinForms 不缩放控件：`Top|Left` 锚定者保持到左上边距离、`Bottom|Right` 锚定者保持到右下边距离，两组不再共享同一映射，**任何单一变换都无法同时满足**。
  该情形 MUST NOT 被静默误判：拉伸会让边缘锚定的锚点相对其余锚点移位，**残差闸（FR-005g.2）正是捕获它的机制**，拒绝后退回模型路径。规范 MUST 有一条模拟拉伸窗口并断言被拒绝的测试。
  （后续若可调整大小的窗口成为常态，可升级为**按 anchor 分组分别拟合**；本 feature 采用保守的全局拟合 + 严格残差闸。）
- **FR-005i（目标控件的指定）**: 步骤 MUST 通过 `TestStep.perception_target: str | None` 指名要点击的控件（`source_geometry.controls[].name`）。**推荐指名而非描述**：无 Text 控件没有任何文本可供 target 描述匹配，而它们正是本能力的核心价值所在。需与 `perception_scope` 同时声明；未声明 `perception_target` 时不做几何点击。
- **FR-005j（几何点击的执行与终结性）**: 几何推算的落点 MUST 经既有 `safe_click_point` 产生，并走**完全未改动**的执行与独立验证闭环（Constitution IV），MUST NOT 豁免验证。几何点击若未通过验证，该步骤后续迭代 MUST NOT 再次使用几何（推算是确定性的，重试必得同一点），MUST 退回模型路径——不得形成确定性错误答案的循环。

#### B. 子窗口检测

- **FR-006（确定性检测）**: 子窗口检测 MUST 是确定性的、可在固定截图上离线复现的：给定同一帧与同一档案，输出的矩形、置信度与检测方法 MUST 完全一致。MUST NOT 依赖绝对坐标或"第几个窗口"之类的位置假设。
- **FR-007（检测证据）**: 检测 MUST 基于档案声明的证据组合，至少支持：(a) **必需锚点文本集合**——一组文本必须在当前帧 OCR 中全部命中（归一化匹配，容忍省略号截断形态）；(b) 可选的**标题锚点**；(c) 可选的**模板匹配**锚点。矩形 MUST 由这些证据的几何位置推导（锚点并集 + 从锚点出发的确定性边界/连通区域推导），MUST NOT 由模型自由生成。
- **FR-008（合理性校验）**: 推导出的矩形 MUST 通过校验才算检测成功：必须包含全部命中锚点；通过核心的两条形状无关兜底（FR-005a）；并通过**档案可选声明**的逐窗口范围（面积比区间、宽高比区间、最小尺寸）。任一不满足 MUST 返回"未检测到"。档案未声明这些范围时 MUST 只做核心兜底，MUST NOT 套用任何内置形状默认值。
- **FR-009（检测置信度与锚点门槛）**: 检测 MUST 产出 [0,1] 置信度（由命中锚点数占比与各锚点 OCR 置信度按确定性公式合成）；低于配置阈值 MUST 视为未检测到。所需命中的锚点数量 MUST 由档案的 `min_required_anchor_hits` 声明（默认=全部声明锚点），核心 MUST NOT 写死"至少 N 个锚点"的规则。
- **FR-010（fail-open）**: 检测过程中的任何异常 MUST 被吸收为"未检测到"，MUST NOT 抛出到主循环、MUST NOT 产生新的 FailureType。

#### C. 激活判定（**显式声明驱动**——用户已决策）

> **决策（已由用户确认，不再是待确认项）：默认不激活。只有测试用例显式声明"本步骤在某个子窗口内操作"时才激活裁剪放大路径；没有声明就一律视为不操作子窗口。**
> 检测到子窗口**只是激活后的前置条件，本身绝不构成激活理由**；系统 MUST NOT 依据步骤意图自然语言推断、也 MUST NOT 依据"画面上检测到了某个窗口"这类隐式启发自动开启增强。

- **FR-011（判定阶梯，确定性、首个命中即决）**: 激活判定 MUST 按以下固定顺序求值，任一步得出结论即终止：
  1. 步骤**未声明**感知增强范围 → **不激活**（原因码 `not_declared`）。这是绝大多数步骤的路径，MUST 是零开销的最早出口：未声明时 MUST NOT 执行任何检测、匹配或几何运算。
  2. 步骤显式声明"关闭" → **不激活**（`declared_off`）。语义与未声明相同，仅为用例可读性提供显式写法。
  3. 全局开关关闭 / 声明的插件未注册 / 该插件未被允许用于当前被测目标 → **不激活**（`disabled` / `plugin_not_registered` / `plugin_not_allowed`）。
  4. 本步骤已达每步激活上限 → **不激活**（`budget_exhausted`）。
  5. 本轮语义动作不是坐标产出型动作 → **不激活**（`non_positional_action`）。
  6. 运行所声明插件的检测：失败 / 置信度不足 / 面积比例超限 → **不激活**（`not_detected` / `low_detection_confidence` / `roi_not_subwindow`），并按 FR-013a 的"声明了但找不到"语义处理。
  7. 倍率计算后不大于 1.0（放大无收益）→ **不激活**（`scale_not_beneficial`）。
  8. 放大观察失败 → **不激活**（`observation_failed`，fail-open）。
  9. 以上全部通过 → **激活**（`activated`）。
- **FR-012（非对称保守性）**: 缺省语义 MUST 是安全的：未声明即不激活、行为与关闭本 feature 时逐字节一致。规范 MUST 记录误判代价的非对称性：假阳性会把 Grounder 视野裁到子窗口内，可能导致窗口外真实目标找不到或被"就近编造"，进而造成不可撤销的误操作；假阴性只是退回既有全帧行为。因此系统 MUST NOT 引入任何形式的隐式/启发式自动激活。
- **FR-013（显式声明的形态）**: 声明 MUST 分两级，且都是**通用字段**，MUST NOT 为具体业务创建固定字段：
  - **步骤级（唯一的激活开关）**: `TestStep.perception_scope: str | null`。取值为**某个插件/档案的名字**（表示"本步骤在该子窗口内操作"）或 `"none"`（显式关闭）；省略 ⇒ 等同 `"none"`。**只有该字段能激活增强。**
  - **用例级（可选的白名单/校验辅助）**: `TestCase.perception_plugins: list[str]`。声明本用例允许使用的插件名集合；声明后，步骤级 `perception_scope` 的取值 MUST 属于该集合，否则**加载期**报错（拼写错误在运行前就暴露）。省略 ⇒ 只按注册表校验。
  - **部署级（配置，非用例语义）**: 全局开关 + 按被测目标（`target_id`）允许的插件名列表。目标未在配置中出现 ⇒ 允许全部已注册插件；显式配置为空列表 ⇒ 该目标上完全停用（部署侧闸门）。
  - **多子窗口的指定方式**: 每个插件/档案**恰好描述一个**子窗口（由它自己的必需锚点集合唯一确定）。同一被测环境上的多个工具窗口 ⇒ 多个档案；步骤通过 `perception_scope` 写明**本步骤操作的是哪一个**。系统 MUST NOT 在一个步骤内同时激活多个插件。
  - **加载期校验**: `perception_scope` 值非空且不是 `"none"` 时，MUST 在测试用例加载期校验其存在于注册表（或用例级白名单）中，并给出字段路径与可选值列表的错误信息。
- **FR-013a（"声明了但画面上找不到该窗口"的语义）**: 该情形 MUST 被显式记录（原因码 `not_detected` / `low_detection_confidence` / `roi_not_subwindow`，并在审计中标记 `declared_but_undetected=true`），且 MUST 可在报告中被聚合为"步骤声明了范围 X，但在该步骤的 N 次迭代中从未检测到"。行为 MUST 由配置项 `on_declared_window_missing` 决定，取值 `fallback`（回退全帧，**默认**）或 `fail`（本轮判为失败并给出可诊断原因）。默认取 `fallback` 的理由与 `fail` 的适用场景见"未决问题 Q1"。无论取哪种，系统 MUST NOT 静默——审计记录是强制的。

#### C'. 接线位置（2026-07-28 真机验证后的设计变更）

> **背景**：真机 5 轮验证发现，声明了 `perception_scope` 的步骤**完全没有激活**，且
> `perception_enhancement` 为 `null`。根因是增强原先挂在 grounding 分支内，而该步被
> feature 012 的 **OCR 直接点击路径**提前解析掉（规划器把 `target.text` 填成条码数字，
> OCR 精确读到且置信度高于阈值 → 直接点击 → `grounder_outcome: not_attempted`），
> grounding 分支从未进入。**只要目标文本能被 OCR 读到，增强就永远不会生效。**

- **FR-020a（接线位置：观察阶段）**: 增强 MUST 发生在**观察阶段**——每次
  `observe()` 之后、任何下游消费者读取 `StructuredScreen` 之前。产物是**精炼后的
  `ocr_items`**，而不是替换送模型的图像。这样一次增强同时喂给：业务断言验证、
  OCR 直接点击、元素记忆、grounding。MUST NOT 只挂在 grounding 分支。
- **FR-020b（覆盖全部观察点）**: 步骤内的**每一次**观察（动作前、动作后验证、
  重试/恢复再观察）MUST 走同一条增强路径，否则断言与点击会看到不一致的两份 OCR。
- **FR-020c（不再按动作类型设限）**: MUST NOT 因"本轮动作不产出坐标"而跳过增强——
  键盘步骤的**断言**同样依赖精炼后的 OCR（原 `non_positional_action` 原因码保留在
  枚举中仅为兼容历史记录，不再产出）。
- **FR-020d（送 grounder 的图像，2026-07-28 真机验证后补充）**: 只精炼 OCR **不足以**
  解决问题——真机证据：OCR 变准后同一条码在输入框与表格行各命中一次，
  `_unique_ocr_or_template` 的 `len(hits)==1` 不再成立，落到 grounding；而 grounder
  收到的仍是**全帧图**，对小输入框毫无精度改善，返回了"reason 写着输入框、坐标却是表头行"
  的候选，点击落空、后续 Backspace 全部无效，**该步比改动前更差**。
  因此：步骤声明了 scope 且增强已激活时，Grounding 请求 MUST 使用**子窗口放大图**
  （`crop_offset` / `scale_factor` / `resolution` / `original_resolution` 按 014 既有字段填写），
  坐标还原 MUST 复用 014 的 `round(v/scale)+crop_offset` 严格链路（越界/退化拒绝，不 clamp）。
  OCR 精炼（供断言与 OCR 直接点击）与放大图（供 grounder）二者**同时生效**，互不替代。
- **FR-020e（成本控制）**: 精炼结果 MUST 按帧内容哈希在步骤内记忆化；对**未变化**的画面
  重复观察 MUST 直接复用（原因码 `activated_cached`），不消耗预算、不产生额外抓屏与 OCR。
  `max_activations_per_step` 因此只约束"**发生变化的**帧被精炼的次数"。
- **FR-020f（信息不得丢失）**: 精炼 MUST 只替换**检测矩形内**的 OCR 项，矩形外一律保留
  （主画面断言依赖它们）。若放大后的 OCR 在矩形内**一无所获**，MUST 保留原始全帧读数——
  用空集替换会删掉粗读本已捕获的文本，反而不如不增强。

#### D. 放大观察与坐标还原

- **FR-014（复用既有观察原语）**: 裁剪 + 放大 + 放大图重新 OCR + 安全遮罩落盘 MUST 复用既有 ROI 放大观察能力（feature 014 建立的 `observe_zoom` 语义），MUST NOT 另起一套裁剪/放大/落盘实现。ROI 的入界处理 MUST 复用既有 **viewing-window** 语义（允许平移/收缩入界，最小尺寸约束）。
- **FR-015（坐标还原红线）**: 放大图上得到的任何 bbox MUST 先在**放大图分辨率**下完成坐标空间解析，再按 `round(v / scale_factor) + crop_offset` 还原为原帧像素坐标；还原结果越界原帧或退化（x1≥x2 或 y1≥y2）MUST 拒绝该候选——**不 clamp、不猜**。既有严格拒绝语义 MUST 原样保留，MUST NOT 为本 feature 放宽。
- **FR-016（自适应倍率）**: 缩放因子 MUST 由确定性公式从 ROI 尺寸推导——使放大后长边达到配置的目标长边像素数，并被 `[min_scale, max_scale]` 夹紧；结果 MUST 严格大于 1.0，否则 MUST 放弃增强（无收益）。档案 MAY 覆盖目标长边与上下限。
- **FR-017（提示通道坐标空间一致性）**: 随增强图像一起发送的任何提示候选（OCR 候选、模板候选、UI 索引候选）MUST 与该图像处于**同一坐标空间**，或者被整体省略；MUST NOT 出现"图像是放大裁剪图、提示 bbox 是原帧坐标"的混合。具体地：送放大图时 `ocr_candidates` MUST 取 `ZoomObservation.ocr_items_zoom_space`（放大图坐标系），**MUST NOT** 取已还原为原帧坐标的 `ocr_items`；源码几何提示 MUST 先投影进放大图坐标系，投影失败者丢弃。
- **FR-018（相对位置约束的通用表达）**: 插件档案 MUST 能以**通用几何关系**声明锚点约束（例如：与某锚点同一水平带、位于某锚点右侧/左侧/上方/下方、位于两个锚点之间；带容差比例）。这些约束 MUST 作为**还原后候选的几何校验**被求值。校验强度 MUST **逐条**由档案作者在数据中标注（用户已裁决）：
  - 每条约束带 `enforce: bool`（默认 `false`）。`enforce=true` 的约束是**强先验**——违反它的候选 MUST 被拒绝（该候选从 Grounding 结果中剔除；若因此无可用候选，按既有 `target_not_found` 语义继续既有恢复链，MUST NOT 新增 FailureType）。`enforce=false` 的约束是**弱提示**——违反只写入审计的 `constraint_violations`，MUST NOT 剔除候选。
  - 核心 MUST 只实现通用几何关系求值，强弱之分完全由档案数据决定；核心中 MUST NOT 出现任何业务专用的关系词或锚点词。
  - 部署侧 MUST 有一个统一的紧急降级开关（`anchor_constraint_mode`）：默认 `respect_profile`（尊重档案的逐条 `enforce`）；置为 `record_only` 时全部约束降级为只记录，用于约束误伤时的快速止血。
- **FR-019（下游链路不变）**: 还原后的 Grounding 结果 MUST 走完全未改动的既有 action policy / 执行 / 独立验证闭环（Constitution IV）；本 feature MUST NOT 修改 action policy、verification、OCR 引擎选择、planner-skip、答案缓存、feature 013 安全落点、feature 022 stale-frame 守卫的任何语义。

#### E. 优先级、预算与终结性

- **FR-020（与既有分支的优先级）**: 在需要 Grounding 的迭代中，既有优先级链 MUST 保持不变，本 feature 的增强 MUST 插入在链尾、仅作用于"真正要发起 Grounding 调用"的分支：pending `zoom_reground`（014）> postmortem 修正点击（023）> memory 高置信直接点击（015）> **插件前置增强（本 feature）** > 全帧 Grounding。
- **FR-021（优先级，2026-07-28 重写）**: 024 与 014 **都会替换送 grounder 的图像**，因此
  "不叠加"不再是结构性事实，MUST 由显式判断保证：单次 Grounding 请求上 MUST 至多应用
  **一次**裁剪+放大变换。同一迭代内两者同时可用时，**014 的 `zoom_reground` 优先**，
  024 的子窗口放大图本轮让位。
  **理由**：014 只在**真实失败之后**触发，其 ROI 由该次失败自身的证据推导（失败候选 bbox /
  锚点邻域），因此携带**新信息**；而此时 024 的子窗口裁剪图与上一轮送出的**逐字节相同**，
  重发等于让模型再看一遍同一张图，必然空耗一次迭代。审计的 `grounder_image` 字段
  MUST 如实记录本轮 grounder 实际收到的是哪一种图像。
- **FR-022（预算与终结性）**: 本 feature MUST NOT 新增迭代、MUST NOT 新增 Grounding 调用次数、MUST NOT 新增重试路径或 FailureType、MUST NOT 消耗恢复预算。每 TestStep 的激活次数 MUST 有可配置上限（默认 1）；增强的**唯一**新增运行时成本是每次激活的 1 次 ROI 抓屏 + 1 次放大图 OCR。所有失败路径 MUST fail-open 回全帧，保证终结性仍由既有单点裁决。
- **FR-023（配置）**: 全部参数 MUST 集中在配置文件的一个新段落中，含：全局开关、按 target 允许的插件列表、每步激活上限、检测置信度阈值、ROI 面积比例上下限、目标长边/最小最大倍率、放大图像素总量上限、边缘带比例、插件档案目录、`on_declared_window_missing`（`fallback` | `fail`，默认 `fallback`）、`anchor_constraint_mode`；缺省时全部取默认值，MUST NOT 破坏既有配置文件；MUST 有配置模型校验（非法值加载期报错）。

#### F. 可观测性与回滚

- **FR-024（增强审计）**: **声明了 `perception_scope` 的步骤，其每个迭代 MUST 产出一条增强审计记录，绝不为 `null`**——无论该迭代最终走哪条动作解析路径（OCR 直接点击 / 记忆 / 回放 / grounding）。审计 MUST 含 `grounding_reached` 布尔字段，用于区分"根本没走到 grounding"与"走到了但没增强"。真机验证暴露的正是这个缺口：审计为 null 时无法从报告区分"没触发"与"坏了"。记录，含：是否启用、命中插件名（或 null）、检测矩形四元组（或 null）、检测方法、检测置信度、激活结论、**判定原因码与依据**（触发或否决的那条证据）、缩放因子、放大图产物路径（或 null）。**未激活时同样 MUST 记录**否决原因码。
- **FR-025（产物与报告）**: 激活时的放大图 MUST 按既有 artifact 惯例落盘（安全遮罩版本始终落盘；未遮罩模型版本遵循既有私有持久化开关），并 MUST 沿既有链路进入 JSON 与 HTML 报告；模型调用审计的坐标变换标识 MUST 包含裁剪偏移与缩放因子。
- **FR-026（回滚）**: 全局开关关闭（或无插件启用）时，系统行为 MUST 与本 feature 之前**逐字节一致**：不产生增强审计记录、不产生新产物、Grounding 请求负载不变。

### Key Entities

- **AppPerceptionPlugin（扩展点）**: 具名的应用感知增强插件——提供子窗口检测与激活投票；仅以通用结构与核心交互。
- **PluginRegistry（注册表）**: 名称 → 插件实例的内部注册与发现；支持档案来源与程序化来源。
- **PluginProfile（声明式档案，数据）**: 描述一个子窗口——插件名、必需锚点文本集合、可选标题/模板锚点、几何合理性约束（面积比例、宽高比、最小尺寸）、放大参数覆盖、锚点相对位置约束、适用的 target 范围。业务词汇只存在于此。
- **SubWindowDetection（检测结果）**: 矩形（原帧坐标）、置信度、检测方法、命中锚点及其 bbox。
- **ActivationDecision（激活判定）**: 结论（激活/不激活）、原因码、声明来源（步骤声明的插件名）、`declared_but_undetected` 标记、只读的文本线索归属警示。
- **PerceptionScopeDeclaration（用例声明）**: 步骤级 `perception_scope`（插件名 | `"none"` | 省略）+ 用例级可选白名单 `perception_plugins`；加载期校验取值合法性。
- **PerceptionEnhancementAudit（审计记录）**: FR-024 的全部字段，挂在单次动作迭代上。
- **AnchorConstraint（相对位置约束）**: 通用几何关系（同水平带 / 同垂直带 / 左右 / 上下 / 介于两锚点之间）+ 容差比例 + **逐条 `enforce` 标志**（true ⇒ 违反者拒绝候选；false ⇒ 仅记录）。
- **AppPerceptionConfig（配置）**: FR-023 的全部键。

## Clarifications（自动决策，代替 /speckit-clarify）

> 下列决策已在本规范中取值以便继续推进；另有三条真正影响设计走向的选择见"未决问题"章节。

### 决策 1：增强在 Grounding 分支内替换图像，不新增迭代

与 feature 014 的"恢复旗标 + 下一迭代消费"不同，前置增强发生在**同一迭代内**：判定 → ROI 观察 → 用增强图构造本次 Grounding 请求。因此不消耗迭代预算、不增加 Grounding 调用次数，新增成本仅为 1 次 ROI 抓屏 + 1 次放大图 OCR。这正是"前置"相对"事后恢复"的核心收益（014 每次升级要多花一个迭代）。

### 决策 2：`zoom_reground` 优先于插件增强

若本迭代已有 pending `zoom_reground` 计划，说明**已经发生过真实失败**并由恢复引擎做出了定向补救决策，其 ROI 来自失败候选/锚点邻域，针对性强于先验档案。故 014 优先、本轮跳过增强，且任一次 Grounding 请求上至多一次裁剪+放大（FR-021）。

### 决策 3：插件以声明式档案（数据）为主要交付形态

把"这个子窗口长什么样"表达为数据而非代码，是满足 Constitution VI 最干净的方式：核心只有一个通用的声明式插件实现 + 注册表，被测应用知识全部外置。代码插件通道保留给档案无法表达的特殊检测逻辑，但不作为本 feature 的内置交付物。

### 决策 4：自适应倍率而非固定倍率

子窗口大小随分辨率与窗口状态变化，固定 2x 对很小的窗口不够、对很大的窗口浪费像素与带宽。改为"放大后长边达到目标像素数"的确定性公式并夹紧上下限（FR-016）。注意：既有的模型图像降采样只作用于 planner/describe 路径，Grounder 的图像负载为原始文件字节，故放大分辨率能完整送达 Grounder。

### 决策 5：激活来源唯一——用例显式声明（用户已确认）

默认不激活；只有 `TestStep.perception_scope` 显式写明插件名才激活。检测成功是**前置条件**而非激活理由；不做任何基于意图文本的自然语言推断、不做"看见窗口就放大"的隐式启发。缺省语义安全（未声明 ⇒ 与现状逐字节一致），因而"画面上有子窗口但本步不操作它"的场景由**不写声明**天然覆盖，用例作者无需做任何排除动作。文本线索与窗口的归属关系降级为**只读警示**（见 Edge Cases），永不改变激活结论。

### 决策 6：检测矩形不参与点击坐标的任何 clamp

检测矩形是**观察窗口**，可平移/收缩入界；但由它导出的任何点击坐标仍走严格拒绝语义。二者语义边界与 feature 014 完全一致，不得混淆。

## 历史未决问题（已全部关闭，保留裁决理由备查）

### Q1：步骤声明了某子窗口，但画面上检测不到它——静默回退还是显式失败？【已裁决：A/C，默认 `fallback`】

| 选项 | 内容 | 影响 |
|------|------|------|
| A | **回退全帧 + 强制审计记录**（`fallback`，**默认取值 / 推荐**） | 不新增失败源；"声明了却没检测到"在报告中可聚合、可诊断，但不会直接判步骤失败 |
| B | 显式失败：本轮判为失败并给出可诊断原因（`fail`） | 用例作者的声明被当作硬断言，写错立刻暴露；但会新增一个"感知层判失败"的路径 |
| C | 两者皆可配（`on_declared_window_missing: fallback \| fail`），默认 A | 部署侧可按严格度选择；实现代价仅为一个枚举分支 |

**规范当前取 C（默认 `fallback`）。推荐保持默认 `fallback`，理由如下**：

1. **声明是观察提示，不是业务断言。** 判定步骤成败的唯一依据必须是操作后独立采集的证据
   （Constitution IV / 验证独立性门禁）。让感知层的一个提示直接判失败，等于在 Verifier 之外新增
   一个失败裁决者，架构上是倒退，也与 FR-022"不新增 FailureType / 不新增失败路径"冲突。
2. **有真实反例：窗口在步骤开始时本来就不该可见。** 目标用例的 `select-scanner-simulator` 步骤，
   其**目的本身**就是把子窗口切到前台——该步骤开始时窗口只是任务视图里的一个小缩略图，档案锚点
   （小字标签）在那个尺度上根本 OCR 不出来。`fail` 模式会恰好在最需要帮助的步骤上把用例打死。
3. **fail 会把"暂时还没出现"与"永远不会出现"混为一谈。** 步骤内多次迭代是正常的（等待窗口渲染、
   前一步动作生效延迟）；首轮检测不到不代表本步骤错。
4. **诊断性没有损失。** `fallback` 下每一轮都强制写 `declared_but_undetected` 审计，报告可聚合成
   "步骤 X 声明了范围 Y，但 N 次迭代中 0 次检测到"——这比一次硬失败提供的信息更多。

**`fail` 的适用场景**：当团队把子窗口的存在当作步骤的前置不变量、并希望尽早失败而不是让 Grounder
在全帧上瞎猜时，可在部署配置里打开。保留为配置项而非删除。

### Q2：`select-scanner-simulator` 这类"把窗口切到前台"的步骤要不要声明？【已裁决：不声明】

**规范建议：不声明**（见"目标用例的声明标注"附录中的逐步分析）。该步骤的点击目标是**任务视图里的
缩略图**，不是子窗口本体；档案锚点在缩略图尺度上不可读，声明后必然走 `declared_but_undetected`
回退路径——除了多一条审计噪声没有收益。若未来要覆盖"在缩略图上精确落点"的需求，正确做法是为
"任务视图缩略图网格"单独写一个档案（它有自己的锚点：窗口标题文字条），而不是复用子窗口档案。
**此条需要用户确认是否认可**（协调方最初的候选清单里包含了这一步）。

### Q3（已由用户裁决，2026-07-28）：`AnchorConstraint` 采用**逐条 `enforce` 标志**

**裁决结果**：采纳选项 C。每条约束在档案里自带 `enforce: bool`（默认 `false`）：
`enforce=true` ⇒ 违反者**拒绝候选**（强先验，用于消灭"点到下方表格"这类已知事故形态）；
`enforce=false` ⇒ 仅记录违规（弱提示，不误杀）。核心只实现七种通用几何关系，
强弱之分完全由档案作者在**数据**中标注。部署侧保留 `anchor_constraint_mode` 紧急降级开关
（默认 `respect_profile`；置 `record_only` 可一键把全部约束降级为只记录）。已固化为 FR-018。

## Assumptions

- 触发本需求的子窗口在同一被测环境中具有稳定的**内部结构**（锚点文本集合、控件相对关系），但**位置与大小可变**；因此检测必须基于锚点而非绝对坐标。
- 放大对"小控件读不清"有实质改善（这正是 overall_design 的 zoom 观察动作与 feature 014 的既有假设），倍率可配置以便部署侧调优。
- 既有 ROI 放大观察能力在驱动不支持 ROI 抓屏时回退为内存裁剪，语义等价；所有失败返回"无观察"。
- Grounder 的图像负载不经过 planner 侧的降采样，放大后的分辨率能完整送达模型。
- 用例的目标邻近文本与步骤意图已经承载了足够的文本线索用于窗口归属推断（本仓库既有用例均满足）。
- 第二个"互不相关 GUI 场景"可以用离线 fixture 构造（不要求真实第二套被测系统），只需窗口结构与词汇与第一场景完全无关，以验证核心的业务无关性。
- 本 feature 不改动 feature 014 既有的提示候选坐标空间行为；FR-017 只约束本 feature 新增的增强路径（014 的同类不一致作为独立跟进项记录，不在本 feature 范围内）。
- 用例作者愿意为需要增强的步骤补写一行 `perception_scope` 声明（这是用户已确认的激活模型的直接推论）。

假定该被测环境上为各工具窗口分别准备了档案（每个档案恰好描述一个窗口，名称示意）：
`scanner-sim` / `cash-changer` / `ct5100-sim` / `value-card-sim`。

| 步骤 id | 动作类型 | 目标在哪 | 建议声明 | 理由 |
|---|---|---|---|---|
| `open-task-view` | hotkey（或点主画面弹窗的「戻る」）| 主画面 / 全局 | **不声明** | 快捷键无坐标；异常分支点的是主画面弹窗按钮 |
| `select-scanner-simulator` | click | **任务视图的缩略图**（非子窗口本体）| **不声明**（见未决问题 Q2）| 缩略图尺度上档案锚点不可读，声明必然走 `declared_but_undetected` 回退；若要覆盖此需求应另建"任务视图"档案 |
| `focus-barcode-field` | double_click | 子窗口顶部输入框 | **`scanner-sim`** ✅ | 典型受益步骤：输入框与其下方表格首行仅隔十几像素，正是全帧读不清的地方 |
| `clear-barcode-box` | batch_repeat_key | — | **不声明** | 声明式批量按键，绕过 Planner/Grounder，声明无效 |
| `type-barcode-45127366` | type_text | — | **不声明** | 非坐标产出动作，命中 `non_positional_action`；声明无害但无效 |
| `click-scan-button` | click | 子窗口底部按钮 | **`scanner-sim`** ✅ | 最强受益步骤：历史事故正是落点掉到窗口外的主画面按钮区 |
| `return-to-pos-click-blank` | click | **主画面**空白处 | **不声明** ⛔ | intent 明确写着"不要点子窗口内任何位置"；这正是"有窗口但不操作它"的标准反例 |
| `verify-scanned-item-in-cart` | wait / 无动作 | — | **不声明** | 无点击目标 |
| `calc-subtotal` | click | 主画面「小計」 | **不声明** ⛔ | 目标在主画面 |
| `enter-kinken-amount` | click | 主画面小键盘 | **不声明** ⛔ | 目标在主画面 |
| `apply-kinken` | click | 主画面支付按钮 | **不声明** ⛔ | 目标在主画面 |
| `start-cash-for-remainder` | click | 主画面「預/現計」 | **不声明** ⛔ | intent 明确写着"不要点击或操作模拟器窗口"；标准反例 |
| `finalize-mixed-payment` | click | 主画面对话框「確定」 | **不声明** ⛔ | 目标在主画面 |

**统计**：13 个步骤中仅 **2 个**应当声明（`focus-barcode-field`、`click-scan-button`），
另有 1 个边界情况待确认（`select-scanner-simulator`）。这印证了"默认不激活"是正确的缺省——
绝大多数步骤本来就不该增强，让它们零成本、零风险地保持现状比让它们逐一"被推断排除"更可靠。

**e2e 验收用法**：把上表中标 ✅ 的两步与标 ⛔ 的两步（`return-to-pos-click-blank`、
`start-cash-for-remainder`）做成同一张 fixture 上的四个场景，直接对应 SC-001 与 SC-002。
