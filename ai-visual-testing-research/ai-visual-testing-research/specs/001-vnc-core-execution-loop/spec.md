# Feature Specification: VNC 黑盒 GUI 自动化测试核心执行闭环

**Feature Branch**: `001-vnc-core-execution-loop`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "实现"VNC 黑盒 GUI 自动化测试核心执行闭环"。系统需要在纯 VNC 黑盒条件下（只能获取屏幕像素、发送键鼠事件，被测机器不可安装任何辅助程序或使用 UIA/pywinauto/WinRM/SSH/DOM/内部 API/文件系统/注册表）验证观察屏幕→理解当前状态→选择动作→定位目标→执行动作→等待界面稳定→验证结果→保存证据的完整纵向切片是否可行，覆盖声明式测试用例执行、屏幕观察与结构化理解、键盘优先的动作选择、MiMo-V2.5 视觉定位、键鼠执行、页面稳定等待、独立结果验证、基础异常恢复、完整证据留存与面向未来自进化的数据采集。"

## Clarifications

### Session 2026-07-20

- Q: 在单个已声明的测试步骤（TestStep）内部，是否允许 Planner 自主插入未在步骤 intent 中
  声明的微动作（如先聚焦输入框、滚动到目标可见、关闭挡住目标的安全弹窗），并可能多轮迭代
  直到达成该步骤的预期结果？ → A: 允许多轮微动作，直到验证通过或达到该步骤的 `max_retries`
  上限；每个子动作仍需遵循键盘优先与独立验证原则，只有最终对照 `TestStep.expected` 的
  验证结果决定该步骤通过与否。
- Q: TestStep.expected 中组合的多个验证条件，若某个子条件返回"不确定"，整体验证结果应如何
  传播？ → A: `uncertain` 具有传染性——`operator=all` 时，只要有子条件为 `uncertain` 且其余
  子条件不足以单独判定整体为 `failed`，整体即为 `uncertain`；`operator=any` 时，只要没有
  子条件 `passed` 但存在 `uncertain`，整体为 `uncertain` 而非 `failed`。`uncertain` 不会被
  静默折叠为 `passed` 或 `failed`。
- Q: Grounding 结果的"整体置信度偏低""Top-1/Top-2 候选置信度接近难以取舍""目标确实不存在
  （found=false）"这三种情况是否需要区分处理？ → A: 三种情况分别处理，但共用同一个恢复
  引擎：`found=false` 归类为 `target_not_found`（触发重新观察/局部放大再定位）；整体置信度
  低于阈值或 Top-1/Top-2 置信度差值小于阈值，二者统一归类为 `grounding_low_confidence`
  （触发"优先尝试第二候选，再考虑重新 Grounding"）；两类失败均记录到恢复记录与视觉经验
  样本中，保留具体子原因以便未来分析。
- Q: VNC 连接在某测试步骤执行中中断，有限次数重连成功后，应如何处理被中断的这个步骤？ →
  A: 重新执行当前步骤——从重新观察与重新规划开始，不假设断线前已发送的动作已生效；本次
  重试计入该步骤的 `max_retries`。
- Q: 发送给外部模型 API（Planner 强模型、通过 OpenCode Go API 调用的 MiMo-V2.5 Grounder）
  的截图，是否需要与本地保存/报告展示一样先完成敏感区域遮码？ → A: 不需要——敏感区域遮码
  仅作用于本地持久化的截图与报告展示；发送给外部模型 API 的截图保持原图，不做遮码处理。

### Session 2026-07-21

- Q: 当某测试步骤的共享重试预算（`TestStep.max_retries`）已耗尽为 0 的同一时刻，恰好发生
  VNC 连接中断，系统应立即判定该步骤失败，还是仍应至少尝试一次重连？ → A: 预算耗尽优先
  生效——系统 MUST NOT 尝试重连恢复（`restart_step`），该步骤 MUST 直接判定为 `failed`；
  不为 VNC 断线单独开设不受共享预算门控的例外路径，保持"系统级 MUST NOT 出现无限重试
  路径"这一原则在任何时刻都无条件成立（对应 FR-038/FR-039，data-model.md §12）。

### User Story 1 - 执行声明式 GUI 测试用例 (Priority: P1)

作为测试工程师，我提交一份包含测试步骤、操作意图和预期结果的声明式测试用例，Agent 据此通过
VNC 自动执行测试，而不需要人工逐步控制鼠标和键盘。

**Why this priority**: 这是整个闭环的入口——没有可执行的测试用例定义，后续观察、决策、执行、
验证环节都无从谈起。

**Independent Test**: 提供一份仅含 1～2 个步骤的最小 YAML 测试用例（用例 ID、目标 VNC 环境、
自然语言意图、预期结果、超时和最大重试次数），可独立验证系统能否正确加载、解析并按顺序调度
执行，而不依赖后续故事的具体实现细节。

**Acceptance Scenarios**:

1. **Given** 一份包含用例 ID、名称、目标 VNC 环境、至少一个测试步骤（含操作意图、预期结果、
   超时时间、最大重试次数）的测试用例文件，**When** 提交给系统执行，**Then** 系统按顺序加载
   全部步骤并开始调度，不需要人工介入。
2. **Given** 一份缺少必填字段（如没有预期结果）的测试用例，**When** 提交执行，**Then** 系统
   在开始运行前拒绝该用例并给出明确的字段级错误，而不是运行到一半才失败。
3. **Given** 一份仅包含明确步骤（无最终目标自主规划要求）的测试用例，**When** 执行，**Then**
   系统严格按已声明的步骤顺序执行，不额外自主插入或省略步骤。

### User Story 2 - 观察和理解当前屏幕 (Priority: P1)

作为测试工程师，我希望 Agent 在执行动作前获取当前屏幕并形成可记录的结构化屏幕状态，使后续
动作建立在当前真实页面上，而不是依赖固定坐标或假设。

**Why this priority**: 闭环中的"观察屏幕→理解当前状态"两个阶段是后续一切决策的事实依据；
没有可信的观察结果，动作选择和验证都失去意义。

**Independent Test**: 使用一组预先准备的固定截图（覆盖有变化、无变化、含弹窗、含加载动画等
情形），可独立验证观察管线能否正确输出结构化屏幕状态，而无需连接真实 VNC 环境。

**Acceptance Scenarios**:

1. **Given** 一个有效的 VNC 连接，**When** 系统请求观察当前屏幕，**Then** 系统获取完整截图，
   记录实际分辨率、时间戳与截图存储位置。
2. **Given** 已获取的完整截图和一个感兴趣区域，**When** 系统请求区域截图，**Then** 系统返回
   该区域的独立截图并记录其在原图中的坐标偏移。
3. **Given** 连续两次观察之间界面未发生任何变化，**When** 系统比较前后两帧，**Then** 系统
   判定屏幕未变化，并可据此避免重复的高成本理解。
4. **Given** 屏幕上存在已配置的固定图片模板，**When** 系统执行模板匹配，**Then** 系统正确
   识别出模板出现的位置。
5. **Given** 一屏幕文字内容，**When** 系统执行文字识别，**Then** 系统返回文字内容及其在屏幕
   上的位置。
6. **Given** 常规手段（图像哈希比较、OCR、模板匹配）均无法判断当前页面含义，**When** 系统
   判定需要更深入理解，**Then** 系统调用视觉模型进行页面理解，并将结果并入结构化屏幕状态，
   而不仅是保存一段自然语言描述。

### User Story 3 - 选择可靠的操作方式 (Priority: P1)

作为测试工程师，我希望 Agent 优先使用更确定的键盘操作，只有在无法通过键盘完成时才使用视觉
定位和鼠标点击，以减少误操作。

**Why this priority**: 这是闭环中"选择动作"阶段的核心逻辑，决定了后续是走确定性路径还是
视觉兜底路径，直接影响整体可靠性和执行成本。

**Independent Test**: 给定一个语义动作（如"保存当前文档"）和一个模拟的当前页面状态，可独立
验证动作选择逻辑能否按"快捷键 → 焦点导航 → OCR/模板唯一定位 → 视觉定位 → 停止并恢复"的
顺序选出候选方式，而无需真实执行任何键鼠动作。

**步骤粒度说明**（Clarification 2026-07-20）：一个已声明的测试步骤（TestStep）在其 intent
指向的最终目标之外，MAY 由 Planner 自主决定并插入未被显式声明的必要前置微动作（如先聚焦
输入框、滚动使目标可见、关闭挡住目标的安全弹窗），并可能因此在一个步骤内多轮迭代"选择动作
→ 定位 → 执行 → 等待"，直到达成该步骤的预期结果或用尽该步骤的 `max_retries`。每一轮子动作
仍必须遵循本故事的键盘优先顺序和用户故事七的独立验证原则；只有针对该步骤 `expected` 的最终
验证结果决定步骤是否通过。

**Acceptance Scenarios**:

1. **Given** 一个已知可通过 Ctrl+S 完成的保存意图，**When** 系统选择执行方式，**Then** 系统
   优先选择快捷键路径，不调用视觉定位。
2. **Given** 一个没有已知快捷键、但 OCR 能在当前屏幕唯一定位目标文字的意图，**When** 系统
   选择执行方式，**Then** 系统选择 OCR 定位路径，而不直接使用视觉模型。
3. **Given** 一个 OCR 和模板均无法唯一确定目标的意图，**When** 系统选择执行方式，**Then**
   系统进入视觉定位（Grounding）路径。
4. **Given** 上述所有确定性和视觉手段均无法确定目标，**When** 系统评估结果，**Then** 系统
   停止当前动作并进入恢复流程，不得猜测坐标或随意点击。
5. **Given** Planner 产出的语义动作，**When** 检查其输出格式，**Then** 该输出只包含语义
   描述（如"点击登录按钮"、"按 Ctrl+S 保存"），不包含裸屏幕坐标。

### User Story 4 - 通过 MiMo 定位 GUI 目标 (Priority: P1)

作为测试工程师，我希望 Agent 可以把"点击右下角的保存按钮"这样的语义目标转换为实际屏幕区域。

**Why this priority**: 这是闭环中"定位目标"阶段在确定性手段失效时的兜底能力，是验证"键盘
优先、视觉兜底"策略可行性的关键环节。

**Independent Test**: 使用一组预先准备的固定截图和对应的语义目标描述，可独立验证 Grounding
调用、坐标系还原与候选筛选逻辑是否正确，而无需真实连接 VNC 或执行点击。

**Acceptance Scenarios**:

1. **Given** 一张包含多个按钮的截图和"点击登录按钮"这样的语义目标（含角色、文字、自然语言
   描述、附近文字等信息），**When** 调用视觉定位，**Then** 系统返回最多三个候选 Bounding
   Box，每个候选附带置信度和简短选择理由。
2. **Given** 定位输入为局部裁剪图，**When** 系统返回候选坐标，**Then** 坐标已还原为原始
   VNC 屏幕像素坐标（考虑裁剪偏移），而不是裁剪图内的相对坐标。
3. **Given** 截图中确实不存在目标控件，**When** 调用视觉定位，**Then** 系统明确返回"未找到"，
   而不是强行给出一个坐标。
4. **Given** 视觉定位返回的候选坐标，**When** 系统准备执行点击前，**Then** 系统校验该坐标
   位于当前屏幕分辨率范围内，越界候选被拒绝而不被执行。

### User Story 5 - 执行键盘和鼠标动作 (Priority: P1)

作为测试工程师，我希望 Agent 能够通过 VNC 执行基本 GUI 操作，包括文本输入、按键、组合键、
焦点导航以及鼠标移动、点击、双击、右键、滚轮和简单拖拽。

**Why this priority**: 这是闭环中"执行动作"阶段，是所有决策最终落地为真实操作的必经环节。

**Independent Test**: 针对一个已建立的 VNC 连接，可独立触发单一动作类型（如按下 Ctrl+S、
点击某坐标），验证该动作被正确发送、有超时保护，且执行结果被如实记录，而无需依赖 Planner
或 Grounder 的完整决策链路。

**Acceptance Scenarios**:

1. **Given** 一个需要输入文本的步骤，**When** 系统执行文本输入动作，**Then** 目标文本被
   正确发送到 VNC 会话。
2. **Given** 需要执行组合快捷键（如 Ctrl+S）、Tab/Shift+Tab、Enter、Escape、Space 中的
   任意一种，**When** 系统执行该动作，**Then** 对应按键序列被正确发送。
3. **Given** 需要执行鼠标移动、单击、双击、右键、滚轮或简单拖拽中的任意一种，**When** 系统
   执行该动作，**Then** 对应鼠标事件被正确发送，且点击前系统已记录目标区域和实际点击点。
4. **Given** 任意一个动作正在执行，**When** 执行时间超过配置的超时时间，**Then** 系统终止
   该动作并记录超时。
5. **Given** 一个动作因异常提前结束，**When** 系统处理该异常，**Then** 系统释放 Ctrl、Alt、
   Shift、Windows 等修饰键，避免其保持按下状态影响后续操作。
6. **Given** 一个键鼠动作已成功发送到 VNC 会话，**When** 系统记录该动作的执行结果，**Then**
   执行结果仅表示"动作已发送"，不表示对应测试步骤已经通过。

### User Story 6 - 等待页面稳定 (Priority: P1)

作为测试工程师，我希望 Agent 在动作后等待界面真正完成变化，而不是仅使用固定 sleep，以避免
在页面加载过程中误判。

**Why this priority**: 这是闭环中"等待界面稳定"阶段，直接决定验证阶段拿到的截图是否反映了
操作的最终结果，而非过渡态。

**Independent Test**: 使用一组模拟的连续帧序列（持续变化、逐渐收敛、含动态区域如时钟/加载
动画），可独立验证稳定性判定逻辑能否正确识别"稳定"和"未稳定"，而无需真实 VNC 连接。

**Acceptance Scenarios**:

1. **Given** 一个动作执行完毕，**When** 系统开始等待，**Then** 系统至少等待配置的最短等待
   时间，且不超过配置的最大超时时间。
2. **Given** 连续采集的至少三帧屏幕，**When** 系统比较多帧差异，**Then** 系统据此判断页面
   是否已稳定，而不是依据单帧或固定延时。
3. **Given** 屏幕中存在任务栏时钟、鼠标指针附近区域或加载动画等已知动态区域，**When** 系统
   判断稳定性，**Then** 这些区域被屏蔽，不影响稳定性判定结果。
4. **Given** 一个仅需检查特定屏幕区域变化的场景，**When** 系统等待，**Then** 系统只针对该
   区域判断稳定性，而不要求全屏静止。
5. **Given** 预期文字或模板在最短等待时间之后、最大超时之前提前出现，**When** 系统检测到该
   条件，**Then** 系统立即结束等待，不再继续等待到超时。
6. **Given** 等待过程中 VNC 连接断开或出现明显错误画面，**When** 系统检测到该情况，**Then**
   系统立即终止等待并转入相应处理，而不是继续等待到超时。

### User Story 7 - 独立验证操作结果 (Priority: P1)

作为测试工程师，我希望每个关键动作都通过操作后的新截图进行验证，避免 Agent 点错以后继续
执行后续步骤。

**Why this priority**: 这是闭环中"验证结果"阶段，是保证测试结果可信、不自我欺骗的核心防线，
也是本项目"验证独立性"这一非协商原则的直接体现。

**Independent Test**: 使用一组"操作前/操作后"截图对和对应的验证规则（文字出现/消失、模板
出现/消失、区域变化、整体变化），可独立验证判定逻辑能否给出正确的通过/失败/不确定结果，
而无需真实执行动作。

**Acceptance Scenarios**:

1. **Given** 一条验证规则要求"指定文字出现"或"指定文字消失"，**When** 系统对操作后的新
   截图执行验证，**Then** 系统根据该新截图给出准确的通过或失败判定。
2. **Given** 一条验证规则要求"指定模板出现"或"指定模板消失"，**When** 系统执行验证，
   **Then** 系统根据操作后新截图给出准确判定。
3. **Given** 一条验证规则要求"指定区域发生变化"或"页面整体发生变化"，**When** 系统执行
   验证，**Then** 系统根据前后帧对比给出准确判定。
4. **Given** 确定性方法（文字、模板、画面变化）无法给出明确结论，**When** 系统需要进一步
   判断，**Then** 系统才调用视觉模型回答一个明确的页面状态问题作为验证依据。
5. **Given** 任意验证过程，**When** 验证器无法达到通过或失败的确定结论，**Then** 系统返回
   "不确定"，且该结果不会被当作"通过"处理。
6. **Given** 一个动作已经执行，**When** 系统判断该动作对应步骤是否成功，**Then** 判断依据
   来自操作后独立采集的新证据，而不是执行该动作或定位该目标的模型自身的成功声明。
7. **Given** 一个登录页面提交后，**When** 系统重新截图并检查预期首页文字是否出现，**Then**
   只有验证通过后，当前步骤才被标记为通过，测试才会继续下一步骤。
8. **Given** 一个组合了多个条件的预期结果（如"文字 A 出现"且"文字 B 消失"），**When** 其中
   一个子条件判定为"不确定"、其余子条件不足以单独让整体判定为"失败"，**Then** 整体验证
   结果 MUST 为"不确定"而非被静默折叠为"通过"或"失败"（Clarification 2026-07-20）。

### User Story 8 - 处理基础失败 (Priority: P2)

作为测试工程师，我希望 Agent 在常见失败发生时进行有限恢复，而不是直接崩溃或无限循环。

**Why this priority**: 在 P1 闭环已经可以跑通正常路径的基础上，本故事为闭环加固鲁棒性，
使其能够应对真实环境中常见的连接、感知、执行和输入类异常，属于在核心闭环之上的增强能力。

**Independent Test**: 通过预先构造的异常场景（如断开的 VNC 连接、无变化的点击结果、未知
弹窗截图），可独立验证对应失败类型能否被正确识别，并触发对应的有限恢复策略，而无需完整
跑通整条闭环。

**Acceptance Scenarios**:

1. **Given** VNC 连接失败、VNC 连接中断、黑屏、页面长时间不稳定、目标未找到、Grounding
   置信度过低、点击后页面无变化、输入焦点错误、输入法或键盘输入错误、未知弹窗、验证失败、
   操作超时中的任意一种情形，**When** 系统检测到该情形，**Then** 系统将其归类为对应的失败
   类型，而不是笼统报错。
2. **Given** 一个已识别的失败类型，**When** 系统触发恢复，**Then** 系统按该失败类型对应的
   策略执行，如重新截图、额外等待、使用第二个 Grounding 候选、重新进行 Grounding、从鼠标
   路径切换到键盘路径、释放修饰键、按 Escape 或使用 Win+D 恢复到桌面。
3. **Given** 第一次点击未产生预期页面变化，**When** 系统判定验证失败，**Then** 系统尝试
   第二候选或重新定位，而不是立即判定整个测试失败。
4. **Given** 某个失败类型的恢复尝试已达到其配置的最大重试次数，**When** 系统再次遇到同类
   失败，**Then** 系统停止该测试步骤并标记为失败，不再继续重试，杜绝无限循环。
5. **Given** 测试过程中 VNC 连接中断，**When** 系统检测到断线，**Then** 系统立即停止发送
   任何动作、进行有限次数重连，并在重连成功后重新截图、重新识别当前页面，而不是假设之前
   的页面状态仍然有效；被中断的测试步骤 MUST 重新执行（从重新观察与重新规划开始），本次
   重新执行计入该步骤的最大重试次数（Clarification 2026-07-20）。

### User Story 9 - 保存完整测试证据 (Priority: P1)

作为测试工程师，我希望测试完成后能够查看 Agent 为什么执行某个动作，以及失败发生在哪一步。

**Why this priority**: 这是闭环最后一环"保存证据"，也是让测试结果"明确、可追溯"这一核心
用户诉求得以兑现的必要环节；没有完整证据，测试通过或失败的结论就无法被信任或复核。

**Independent Test**: 针对已经执行完毕的一个测试步骤（无论成功或失败），可独立验证系统能否
生成包含操作前后截图、各阶段决策与耗时的完整证据记录，并汇总为可阅读的报告。

**Acceptance Scenarios**:

1. **Given** 任意一个已执行的测试步骤，**When** 该步骤结束，**Then** 系统保存该步骤的操作
   前后截图、OCR 结果、Planner 的结构化动作、Grounding 候选与被选择的候选、实际执行动作与
   实际点击坐标、等待结果、验证结果、重试和恢复记录、使用的模型名称及其原始响应（或安全
   存档）、以及各阶段耗时。
2. **Given** 一次测试运行结束（无论通过、失败还是被取消），**When** 系统生成报告，**Then**
   系统同时生成机器可读的 JSON 报告和人类可阅读的 HTML 报告，且报告中包含明确的通过、失败
   或取消状态。
3. **Given** 某一步骤最终失败，**When** 用户查看报告，**Then** 报告中包含该步骤的失败原因、
   操作前后截图、Grounding 候选、实际点击点、验证证据和全部恢复尝试记录，足以定位问题根因。

### User Story 10 - 为未来自进化保留数据 (Priority: P3)

作为系统开发者，我希望第一版能够积累未来截图理解和自进化所需的数据，但本功能不负责训练或
在线修改模型。

**Why this priority**: 这是面向后续功能（页面/元素记忆、Record-Replay、视觉自进化）的前瞻性
数据留存，不影响本次闭环自身是否成立，因此优先级低于闭环本体及其鲁棒性增强。

**Independent Test**: 检查一次已完成的测试运行所产生的数据，可独立验证其是否包含足以支撑
未来构建页面记忆、元素记忆、成功轨迹、失败样本、Grounding 正负样本等能力的必要字段，而无需
实际实现任何记忆检索或训练功能。

**Acceptance Scenarios**:

1. **Given** 一次已执行的动作，**When** 系统采集该动作的相关数据，**Then** 采集内容足以在
   未来用于构建页面记忆、元素记忆、成功操作轨迹、失败目标、Grounding 正负样本、人工纠正
   样本和策略成功率等经验。
2. **Given** 已采集的数据，**When** 检查系统在本功能范围内的行为，**Then** 系统仅执行采集
   和保存，不自动更新任何模型权重、不自动修改测试断言、不自动覆盖正式回放脚本、不会因为
   一次成功就永久接受新的界面基线。

---

### Edge Cases

- 测试用例声明的目标 VNC 环境不存在或凭据错误时，系统应在连接阶段即失败并给出明确原因，
  而不是进入后续观察或执行阶段后才报错。
- 屏幕分辨率或 DPI 与测试用例假设不一致时，系统应能记录实际分辨率，并将后续所有坐标换算
  建立在实际分辨率之上，而不是假设固定分辨率。
- 观察阶段完全无法获取任何有效截图（如持续黑屏或连接假死）时，系统应将其归类为对应失败
  类型并触发恢复，而不是把空白截图当作正常页面继续处理。
- Grounding 返回的多个候选置信度非常接近、难以区分优劣时，系统应有明确规则选择候选或判定
  为不足以确定，而不是随意选择第一个。
- 验证规则本身引用了一个屏幕上永远不会出现的文字或模板（用例编写错误）时，系统应在达到
  超时后明确判定失败并说明原因，而不是无限等待。
- 页面因动态内容（如持续滚动的公告、跳动的进度百分比）永远不会真正"稳定"时，系统应依据
  屏蔽动态区域或仅检查特定区域的机制，仍然能够在合理时间内做出稳定性判断。
- 同一失败类型在不同恢复策略下反复出现、始终未能解决时，系统应在达到全局最大重试或恢复
  次数后停止整个测试，而不是持续消耗时间和模型调用。
- 测试执行过程中系统进程被中断或异常退出后重新启动时，系统应能识别到未完成的运行记录，
  而不是产生不完整或矛盾的报告。
- 某个测试步骤配置的敏感遮罩区域恰好与该步骤需要视觉定位或验证的目标区域重叠时（Clarification
  2026-07-20 决定遮罩不作用于外发模型 API 的截图），系统仍会将该区域的原始画面发送给外部
  模型 API；用例编写者应避免此类重叠，而不是依赖系统自动检测并绕过遮罩语义。
- VNC 连接在某测试步骤执行过程中中断、重连成功后，系统应将该步骤视为需要从重新观察开始
  完整重做，而不是假设断线前发送的动作已生效并跳到等待或验证阶段继续（对应 FR-039 的
  澄清）。
- Planner 在同一测试步骤内多轮插入前置微动作（如反复尝试聚焦、反复关闭弹出的提示）却始终
  无法达成该步骤预期结果时，系统应在用尽该步骤的 `max_retries` 后停止并标记为失败，而不是
  无限迭代微动作（对应 FR-038 的无限重试禁令同样适用于步骤内的微动作迭代）。

## Requirements *(mandatory)*

### Functional Requirements

**测试用例与调度**

- **FR-001**: 系统 MUST 支持加载声明式测试用例，用例至少包含用例 ID、名称、目标 VNC
  环境、一个或多个测试步骤。
- **FR-002**: 每个测试步骤 MUST 至少包含自然语言操作意图、预期结果、步骤超时时间和最大
  重试次数。
- **FR-003**: 系统 MUST 在测试运行开始前校验测试用例格式，字段缺失或格式错误的用例 MUST
  被拒绝并给出具体错误说明，而不是运行中途失败。
- **FR-004**: 第一版 MUST 只支持按已声明步骤顺序执行的"明确步骤型"用例，MUST NOT 要求
  系统根据单一最终目标自主生成完整长任务计划。

**屏幕观察与理解**

- **FR-005**: 系统 MUST 能获取完整 VNC 屏幕截图，并能获取指定区域的截图。
- **FR-006**: 系统 MUST 能识别屏幕中的文字及其位置（OCR）。
- **FR-007**: 系统 MUST 能判断当前屏幕相较上一帧是否发生变化。
- **FR-008**: 系统 MUST 能识别已配置的固定图片模板在屏幕上的位置。
- **FR-009**: 系统 MUST 为每次观察保存截图、实际屏幕分辨率和时间信息。
- **FR-010**: 当图像哈希比较、OCR 和模板匹配等常规手段均无法理解当前页面含义时，系统
  MUST 调用视觉模型进行补充理解。
- **FR-011**: 系统 MUST 将每次观察结果转换为结构化数据（而非仅保存自然语言描述），供后续
  决策和证据留存使用。

**动作选择**

- **FR-012**: 系统 MUST 按以下优先级顺序尝试确定下一步执行方式：① 已配置的明确快捷键；
  ② Tab / Shift+Tab / Enter / Space 等焦点导航；③ OCR 或固定模板能够唯一确定的目标；
  ④ MiMo-V2.5 GUI Grounding；⑤ 以上均无法确定时，停止当前动作并进入恢复。同一测试步骤内
  MAY 因此多轮迭代该优先级选择（例如先聚焦、再输入；先关闭挡路弹窗、再继续原定动作），
  每一轮迭代仍必须独立遵循本优先级顺序（Clarification 2026-07-20，见用户故事三"步骤粒度
  说明"）。
- **FR-013**: 负责"选择下一步做什么"的组件（Planner）MUST 只输出语义动作（如"点击登录
  按钮"“按 Ctrl+S 保存”），MUST NOT 直接输出裸屏幕坐标。
- **FR-014**: 当所有确定性和视觉手段均无法确定目标时，系统 MUST NOT 猜测坐标或执行任意
  位置的点击。

**GUI 目标定位（Grounding）**

- **FR-015**: 视觉定位请求 MUST 支持传入当前原始截图或局部截图、目标角色、目标文字、目标
  自然语言描述、目标附近文字、OCR 候选区域和模板候选区域。
- **FR-016**: 视觉定位结果 MUST 明确表示目标是否存在，MUST 返回最多三个候选 Bounding
  Box，且每个候选 MUST 附带置信度和简短选择理由。
- **FR-017**: 视觉定位返回的坐标 MUST 能还原为原始 VNC 屏幕的像素坐标；当输入为裁剪图时，
  系统 MUST 记录并应用裁剪偏移完成还原。
- **FR-018**: 当视觉定位无法可靠判断目标位置时，MUST 返回"未找到"，MUST NOT 强制生成
  一个坐标。
- **FR-019**: 系统 MUST 在执行点击前校验候选坐标是否位于当前屏幕分辨率范围内，越界坐标
  MUST 被拒绝。

**键鼠执行**

- **FR-020**: 系统 MUST 支持通过 VNC 执行以下动作：普通文本输入、单键、组合快捷键、Tab、
  Shift+Tab、Enter、Escape、Space、鼠标移动、单击、双击、右键、滚轮、简单拖拽。
- **FR-021**: 每个动作 MUST 具有独立的执行超时。
- **FR-022**: 动作因异常提前结束时，系统 MUST 释放 Ctrl、Alt、Shift、Windows 等修饰键。
- **FR-023**: 每次鼠标点击前，系统 MUST 记录目标区域和实际点击点。
- **FR-024**: 动作执行结果 MUST 仅表示"VNC 动作已发送"，MUST NOT 被视为对应测试步骤已经
  通过。

**等待页面稳定**

- **FR-025**: 系统 MUST 支持配置最短等待时间和最大等待超时时间。
- **FR-026**: 系统 MUST 连续采集至少三帧屏幕，并根据多帧差异判断页面是否稳定，MUST NOT
  仅依赖固定 sleep 作为稳定性判断的唯一依据。
- **FR-027**: 系统 MUST 支持仅检查预计会发生变化的特定屏幕区域，而不要求全屏静止。
- **FR-028**: 系统 MUST 支持屏蔽任务栏时钟、鼠标指针附近区域和加载动画等已知动态区域，
  使其不影响稳定性判断。
- **FR-029**: 当预期文字或模板在等待过程中提前出现时，系统 MUST 立即结束等待。
- **FR-030**: 当等待过程中检测到 VNC 断开或出现明显错误画面时，系统 MUST 提前终止等待并
  转入相应处理流程。

**独立验证**

- **FR-031**: 系统 MUST 支持以下验证方式：指定文字出现、指定文字消失、指定模板出现、
  指定模板消失、指定区域发生变化、页面整体发生变化、视觉模型回答一个明确的页面状态问题。
- **FR-032**: 验证 MUST 优先采用 OCR、模板和画面变化等确定性方法；只有确定性方法无法
  判断时，MUST 才使用视觉模型进行语义验证。**测试用例编写指引（需求质量门禁 2026-07-21
  澄清）**：`visual_question` 是 `VerificationCondition` 的一种显式声明类型（见
  data-model.md §7），由测试用例作者在编写 `expected` 时主动选择，而非系统在其他类型
  （`text_appears` 等）判定为"不确定"时自动升级触发的运行时逃逸路径——系统本身不实现
  "确定性验证器返回不确定后自动改问视觉模型"的自动升级机制。因此本条"只有确定性方法无法
  判断时才使用视觉模型"MUST 理解为对测试用例编写者的指引与系统整体成本路由原则（对齐宪法
  "资源约束"条款"语义验证仅作为最后手段"），而非要求为每个已声明的确定性条件额外实现自动
  升级分支：编写者 SHOULD NOT 在文字/模板/区域变化等确定性类型足以表达断言意图时声明
  `visual_question`。
- **FR-033**: 每次验证 MUST 产生"通过"“失败”“不确定”三种结果之一；"不确定" MUST NOT
  被当作"通过"处理，也 MUST NOT 被静默折叠为"失败"。当 `expected` 组合多个验证条件时
  （Clarification 2026-07-20）：`operator=all` 下，若存在子条件为"不确定"且其余子条件不足
  以单独判定整体为"失败"，整体结果 MUST 为"不确定"；`operator=any` 下，若没有子条件"通过"
  但存在"不确定"，整体结果 MUST 为"不确定"而非"失败"。
- **FR-034**: 验证依据 MUST 来自操作后独立采集的新截图和证据；负责执行动作或定位目标的
  组件 MUST NOT 仅凭自身先前输出宣布操作成功。
- **FR-035**: 只有当前步骤验证通过后，系统才 MUST 继续执行下一测试步骤；验证未通过时
  MUST NOT 继续执行后续步骤。

**基础失败处理**

- **FR-036**: 系统 MUST 能识别以下失败类型：VNC 连接失败、VNC 连接中断、黑屏、页面长时间
  不稳定、目标未找到、Grounding 置信度过低、点击后页面无变化、输入焦点错误、输入法或键盘
  输入错误、未知弹窗、验证失败、操作超时。其中（Clarification 2026-07-20）：Grounding
  明确返回"未找到"时 MUST 归类为"目标未找到"；Grounding 整体置信度低于配置阈值、或 Top-1
  与 Top-2 候选置信度差值小于配置阈值（难以取舍）这两种情况，MUST 统一归类为"Grounding
  置信度过低"，但 MUST 各自记录具体触发原因（整体偏低 / Top1-Top2 接近）供恢复记录与未来
  自进化数据使用。
- **FR-037**: 系统 MUST 支持以下基础恢复策略：重新截图、额外等待、使用第二个 Grounding
  候选、重新进行 Grounding、从鼠标路径切换到键盘路径、释放修饰键、按 Escape、使用 Win+D
  恢复到桌面。
- **FR-038**: 每一类失败 MUST 配置独立的最大重试次数；达到最大重试次数后系统 MUST 停止
  当前测试步骤并标记为失败，MUST NOT 出现无限重试或无限循环。
- **FR-039**: VNC 连接中断时，系统 MUST 立即停止发送动作、进行有限次数重连，并在重连成功
  后重新截图和重新识别当前页面。重连成功后（Clarification 2026-07-20），系统 MUST 将被
  中断的测试步骤视为需要重新执行——从重新观察与重新规划开始，MUST NOT 假设断线前已发送的
  动作已经生效并直接从等待或验证阶段继续；本次重新执行 MUST 计入该步骤的 `max_retries`。
  若断线发生时该步骤的 `max_retries` 已耗尽为 0（Clarification 2026-07-21），系统 MUST NOT
  尝试重连恢复，MUST 直接将该步骤判定为 `failed`——预算耗尽的优先级高于 VNC 重连尝试。

**证据与报告**

- **FR-040**: 系统 MUST 为每个测试步骤保存：操作前后截图、OCR 结果、Planner 的结构化动作、
  Grounding 候选与被选择的候选、实际执行动作与实际点击坐标、等待结果、验证结果、重试和
  恢复记录、使用的模型名称及其原始响应（或安全存档）、各阶段耗时。
- **FR-041**: 系统 MUST 在测试运行结束后生成 JSON 报告和人类可阅读的 HTML 报告，报告 MUST
  包含明确的通过、失败或取消状态。
- **FR-042**: 失败步骤的报告 MUST 包含失败原因及相关截图证据，足以定位失败发生的具体步骤
  和原因。

**面向未来自进化的数据采集**

- **FR-043**: 系统 MUST 为每个动作保存足以在未来构建页面记忆、元素记忆、成功操作轨迹、
  失败目标、Grounding 正负样本、人工纠正样本和策略成功率的相关数据。
- **FR-044**: 第一版 MUST NOT 自动更新任何模型权重、MUST NOT 自动修改测试断言、MUST NOT
  自动覆盖正式回放脚本、MUST NOT 因一次成功就永久接受新的界面基线；本功能仅负责数据采集
  和保存。

**配置与安全**

- **FR-045**: 系统 MUST 支持配置：VNC 地址和端口、VNC 连接超时、VNC 重连次数、Planner
  模型、Grounder 模型、模型 API 地址、模型调用超时、Grounding Top-K、OCR 开关、模板匹配
  开关、页面稳定阈值、默认步骤超时、默认最大重试次数、截图保存策略、敏感信息遮罩区域。
- **FR-046**: 负责"下一步做什么"的 Planner 组件 MUST 可替换，MUST NOT 与特定模型供应商
  耦合。**验收方式（需求质量门禁 2026-07-21 澄清）**：验收时仅修改 `models.yaml` 中
  `models.planner.provider` 字段并提供满足 `PlannerProvider` Protocol（见
  contracts/model-provider-contract.md）的新实现类完成注册，MUST NOT 需要改动
  `planning/`、`perception/`、`verification/`、`execution/` 中任何调用方代码，且既有的
  离线/单元测试套件（对应 US1~US7、US9 的 Independent Test）MUST 仍能通过。
- **FR-047**: 密码和 API Key MUST NOT 直接写入普通配置文件或测试日志中的明文形式。
- **FR-048**: 系统 MUST NOT 读取或依赖 Windows UI Automation、pywinauto、WinRM、SSH、
  浏览器 DOM、被测应用内部接口、文件系统接口或注册表接口；MUST NOT 要求在被测机器安装
  任何辅助 Agent 或程序。
- **FR-049**: 已配置的敏感信息遮罩区域（FR-045）MUST 应用于本地持久化的截图与生成的 JSON/
  HTML 报告（Clarification 2026-07-20）；发送给外部 Planner 或 Grounder 模型 API 的截图
  MUST NOT 应用该遮罩，保持原图以保证视觉理解与定位的可用性。团队 MUST 知悉该权衡：凡配置
  为敏感区域的画面内容，仍会以原始像素形式发往外部模型 API；测试用例编写者 SHOULD 避免让
  Grounding/Planner 依赖敏感区域本身作为定位或理解目标。

### Key Entities

- **测试用例（Test Case）**：一次测试的声明式定义，包含用例 ID、名称、目标 VNC 环境、一个
  或多个测试步骤。
- **测试步骤（Test Step）**：测试用例中的最小可执行单元，包含自然语言操作意图、预期结果、
  超时时间、最大重试次数，以及该步骤最终的通过/失败/取消状态。一个测试步骤 MAY 关联一个
  或多个由 Planner 自主决定的语义动作迭代（如先聚焦、再输入；先关闭挡路弹窗、再继续），
  但只有针对该步骤 `预期结果` 的最终验证结果决定步骤本身的通过与否（Clarification
  2026-07-20）。
- **屏幕观察（Structured Screen Observation）**：一次屏幕采集所形成的结构化状态，包含
  截图引用、分辨率、时间、OCR 结果、模板匹配结果、变化检测结果，以及必要时的视觉模型理解
  结果。
- **语义动作（Semantic Action）**：Planner 针对当前步骤给出的下一步意图描述（如"点击登录
  按钮"），不含裸坐标。
- **定位结果（Grounding Result）**：针对某个语义目标的定位输出，包含是否找到、最多三个
  候选 Bounding Box、每个候选的置信度和理由，以及还原后的原始屏幕坐标；`found=false`、
  整体置信度偏低、Top-1/Top-2 置信度接近这三种情况均需在结果中保留可区分的具体原因
  （Clarification 2026-07-20），前者归类为"目标未找到"，后两者统一归类为"Grounding 置信度
  过低"但各自记录子原因。
- **执行结果（Execution Result）**：一次键鼠动作的实际发送记录，包含执行的操作类型、实际
  坐标（如适用）、是否超时、起止时间，明确区分"动作已发送"与"步骤已通过"。
- **等待结果（Wait Result）**：一次稳定性等待的结果，包含耗时、触发结束等待的原因（稳定、
  预期条件出现、超时、异常终止）。
- **验证结果（Verification Result）**：针对某个测试步骤的独立判定，取值为通过/失败/不
  确定，包含判定依据和证据引用。组合多个子条件时，"不确定"具有传染性，不会被静默折叠为
  "通过"或"失败"（Clarification 2026-07-20，规则见 FR-033）。
- **恢复记录（Recovery Attempt）**：某次失败发生后触发的一次恢复尝试，包含失败类型、
  采用的恢复策略、本次尝试是否解决问题、已用重试次数。
- **测试运行证据（Run Evidence / Report）**：一次测试运行的完整记录集合，包含全部步骤的
  操作前后截图、决策与执行细节、耗时、最终报告（JSON 与 HTML）及总体状态。
- **视觉经验样本（Visual Experience Sample）**：为未来自进化预留的数据单元，记录动作前后
  的观察、语义动作、定位候选、执行与验证结果，供后续构建页面/元素记忆和模型改进使用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在固定分辨率和固定 DPI 的 Windows 10 VNC 环境中，系统能够完成一次完整的
  观察→理解→选择动作→定位→执行→等待→验证→保存证据闭环，且每个阶段均有可查阅的记录——
  "可查阅的记录"的客观判定标准 MUST 以 FR-040 枚举的字段集合（操作前后截图、OCR 结果、
  Planner 结构化动作、Grounding 候选与被选择的候选、实际执行动作与实际点击坐标、等待
  结果、验证结果、重试和恢复记录、模型名称及原始响应、各阶段耗时，具体落地为
  data-model.md §9 的 `ActionIteration` 各字段）为准：验收时逐字段核对每一轮
  `ActionIteration` 是否非空/已填充，而非仅凭主观印象判断"完整"。
- **SC-002**: 当某个动作未通过独立验证时，系统不会自动执行下一测试步骤——在人工抽查的
  失败案例中，此情况的发生比例为零。**抽查范围与方法（需求质量门禁 2026-07-21 澄清）**：
  抽查对象为 SC-006/SC-007 所定义的十次参考测试流程连续运行中产生的全部失败步骤（含
  `failed` 与预算耗尽后按 `failed` 处理的 `uncertain`），逐条核对其后是否仍有
  `StepRecord.iterations` 非空的后续步骤被执行（对应 data-model.md §12
  `STEP_COMPLETED_FAILED` 规则：未开始的后续步骤 MUST 保持 `pending`、不产生
  `iterations`）；不与 SC-006/007 分开另行组织独立的抽样批次。
- **SC-003**: 所有动作、等待和恢复过程均配置有超时和最大重试次数；人工审查测试运行日志时
  不应发现任何未设上限的重试或等待。
- **SC-004**: 当目标定位结果不确定（返回"未找到"）时，系统不会执行任何点击；人工抽查中此
  情况的发生比例为零。
- **SC-005**: 每一次测试失败都附带完整、可复核的视觉证据（操作前后截图、定位候选、验证
  依据、恢复过程），使测试工程师无需重新运行即可判断失败原因。
- **SC-006**: 在预先约定的一组参考测试流程上连续运行十次，至少九次得到与实际结果一致的
  通过/失败判定。
- **SC-007**: 在上述十次参考测试运行中，不出现"实际操作未达成预期效果，但报告判定为通过"
  的情况。
- **SC-008**: 系统在不依赖独立显卡、不运行本地大型视觉语言模型的普通办公电脑上即可完成
  上述闭环运行。
- **SC-009**: 单个 VNC 会话运行期间，系统在普通办公电脑（无独立显卡）上的本地资源占用
  保持在可持续运行的水平，不出现因资源耗尽导致的运行中断。
- **SC-010**: 本次运行产生的记录数据，经人工检查可确认足以支撑后续页面记忆、元素记忆、
  Record-Replay 和视觉自进化能力的构建，而无需额外重新采集。

## Assumptions

- **技术约束（由需求方明确给出，作为本功能的既定前提，而非实现阶段自由选择）**：
  - VNC 操作使用 vncdotool 完成。
  - GUI 视觉定位（Grounding）通过 OpenCode Go API 调用 MiMo-V2.5 完成。
  - Planner（负责"下一步做什么"的决策组件）必须可替换，不与特定模型供应商绑定。
  - Agent 运行时（状态机/调度核心）由本项目自行实现，不借助 OpenCode Agent 或其他现成
    Agent 框架作为运行核心。
  - 控制端为普通办公电脑，不要求独立显卡，且不在本地运行大型视觉语言模型；本地仅使用
    轻量图像处理、OCR、模板匹配，重理解能力通过远程模型 API 获取。
  - 第一版（MVP）只需同时控制一台 VNC 机器、执行一个测试任务，不要求多机并发或分布式
    调度。
- 被测 Windows 10 环境在测试期间保持固定分辨率和固定 DPI；分辨率变化不在本功能范围内
  处理。
- 用于验收标准（连续运行十次、九次成功）的"参考测试流程"由测试团队在验收阶段另行准备
  一组具有代表性的、可通过键盘和/或视觉定位完成的应用交互场景（例如对示例桌面应用完成
  登录或保存类操作），具体应用和步骤内容不在本次规格中固化。
- 页面稳定性判断、置信度阈值等具体数值型参数（如最小等待时间、连续帧数、像素差异阈值、
  Grounding 置信度阈值）作为可配置项在实现阶段给出符合"多帧差异判定+可配置阈值"这一
  行为要求的默认值，具体数值由实现阶段依据实测调优，不影响本规格对行为本身的要求。
- 敏感区域遮罩仅覆盖本地持久化的截图与生成的报告，不覆盖发往外部 Planner/Grounder 模型
  API 的截图（Clarification 2026-07-20，见 FR-049）；这是一项经过权衡的既定行为，而非
  实现阶段可自由调整的细节——测试用例设计与敏感区域配置应避免让需要遮罩的画面同时成为
  视觉定位或验证目标。
- **Planner 供应商的视觉理解能力耦合（需求质量门禁 2026-07-21 澄清）**：FR-010（观察补充
  理解）与 FR-032（`visual_question` 验证）均通过同一个 `PlannerProvider` 实现的
  `describe_screen` 方法获得视觉理解能力（见 contracts/model-provider-contract.md），
  与 `plan` 共用同一供应商配置（FR-046 的可替换性针对整个 `PlannerProvider`，而非分别
  针对 `plan`/`describe_screen` 两个方法单独替换）。这是一项已知的、经过权衡的既定限制：
  若团队选择的 Planner 模型本身不具备可靠的视觉理解能力，`describe_screen` MUST 通过
  返回低置信度结果（`mode="describe"`）或 `answer="uncertain"`（`mode="answer_question"`）
  的方式优雅降级，而不是抛出异常（见 contracts/model-provider-contract.md 契约保证），
  但这意味着该部署下 FR-010 的补充理解与 FR-032 的视觉验证实质上不可用；如未来需要为
  纯文本 Planner 单独接入独立的视觉理解供应商，需要新增功能重新设计该耦合关系，不在本次
  纵向切片范围内。
- 本功能范围内不包含：多台 VNC 机器并发、分布式任务调度、完整目标驱动的长任务自主规划、
  Record-Replay 执行引擎、自动生成并应用自愈补丁、页面和元素经验的自动复用、人工标注 Web
  界面、在线或本地模型训练、自定义轻量视觉模型、多 Agent 协作、MCP、Web 测试编排平台、
  CI/CD 集成、Windows UIA/WinRM/客户机 Helper，以及无法通过 VNC 操作的 UAC 安全桌面场景
  的自动处理（遇到此类场景应停止并报告，而非尝试绕过）。
