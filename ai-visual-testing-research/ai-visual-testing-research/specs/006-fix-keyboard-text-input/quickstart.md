# Quickstart: Validating the `type_text` Driver Fix

This is a run/validation guide, not an implementation guide — see `data-model.md` and
`contracts/text-input-contract.md` for the field/interface specifics, and `tasks.md` (generated by
`/speckit-tasks`) for the implementation steps themselves.

## Prerequisites

- `vnc_agent` dev environment set up (`pip install -e ".[dev]"` from `vnc_agent/`), Python 3.12.
- Steps 1-3 below run entirely offline — no live VNC target required (they use a fake vncdotool client
  shaped like `VNCDoToolClient`, per `contracts/text-input-contract.md`).
- Step 4 requires a live Windows VNC target reachable per `vnc_agent/config/vnc-targets.yaml`
  (`win10-test-01`) with `VNC_AGENT_VNC_PASSWORD` set, and the ScannerSimulator app already showing
  its default barcode `2000900010268` in the Barcode field, matching the state at the start of the
  original failing run (`18ba967a-822c-4860-a90d-d8e849205a75`).

## 1. Run the new/changed unit and integration tests directly

```bash
cd vnc_agent
pytest tests/integration/test_vncdotool_text_input.py -v
pytest tests/unit/test_keyboard_executor_type_text.py -v
pytest tests/unit/test_execution_router_type_text.py -v
```

Expected: all pass. Together these prove:
- `VNCToolDriver._sync_text` no longer calls any nonexistent client method for ordinary characters —
  a fake client exposing only `keyPress` (no `type`, no `paste`) receives one `keyPress` call per
  character, in declared order, for a mixed digits/letters/punctuation string, and separately for the
  literal barcode string `"45127366"` (FR-001, FR-002, FR-003, SC-002).
- Newline maps to a single `keyPress("enter")` call and Tab to a single `keyPress("tab")` call, not to
  a literal character send (FR-004, FR-005).
- An empty string produces zero client calls (FR-006, SC-003).
- A `keyPress` raised exception partway through a multi-character string stops immediately — no
  further `keyPress` calls occur after the failure point (FR-007).
- `KeyboardExecutor.type_text` still delegates as a pure pass-through to `driver.send_text` (unchanged
  contract, FR-013).
- `ExecutionRouter.execute()` reports `success=False` with a non-empty `error_message` when the
  driver's `send_text` raises mid-send, and does not report the partial input as success (FR-008,
  FR-009, SC-004).

The same `tests/integration/test_vncdotool_text_input.py` file also carries the second, unrelated
synthetic scenario required by FR-016/SC-006 (Clarification Session 2026-07-24, Q2): a distinct
character-set/context case (independent of the barcode text) exercised through the identical,
unmodified `_sync_text` code path, proving the fix is not barcode-specific.

## 2. Confirm the regression test would have caught the original defect

```bash
git stash push -- vnc_agent/src/vnc_agent/drivers/vncdotool_driver.py
pytest tests/integration/test_vncdotool_text_input.py -v
git stash pop
```

Expected: with the pre-fix `_sync_text` (still calling `client.type(ch)`) restored, the test fails
with an `AttributeError` about the fake client having no `type` attribute — the same failure mode
recorded in `ExecutionResult.error_message` for run `18ba967a-822c-4860-a90d-d8e849205a75`
(`"type object 'VNCDoToolClient' has no attribute 'type'"`). After `git stash pop` restores the fix,
the test passes again (SC-005).

## 3. Confirm existing behavior is untouched (regression gate)

```bash
pytest tests/unit/ tests/integration/ tests/e2e/ -v
```

Expected: the full existing suite still passes, including (at minimum, spot-check if the full run is
slow):

```bash
pytest tests/e2e/test_scenario_02_keyboard_first.py -v
pytest tests/unit/test_keyboard_executor_repeat.py -v
pytest tests/unit/test_execution_router_batch_repeat.py -v
```

These exercise the pre-existing `press_key`/`hotkey`/`press_key_repeat` paths in the same driver and
router files, which this fix must not alter (FR-012, FR-013).

## 4. (Requires a live Windows VNC target) Full ScannerSimulator case rerun

```bash
VNC_AGENT_VNC_PASSWORD=*** vnc-agent run testcases/pos-scan-magazine-checkout.yaml --target win10-test-01
```

Expected, reproducing and resolving the original accident scenario end-to-end:
- `focus-barcode-field` succeeds as before (double-click selects the existing barcode).
- `type-barcode-45127366` now succeeds: the run's HTML/JSON report shows `execution_result.success ==
  true` for this step **and** the step's independent post-action verification (visual confirmation
  that the Barcode field shows exactly `45127366`) also passes — the report must not be judged solely
  on `execution_result.success` (SC-001, per the spec's explicit requirement that screen-content
  confirmation is separate from the execution-result flag).
- `click-scan-button` is reached and executes (it was previously never run because the prior step
  failed and stopped the case).
- No step in the report shows `2000900010268` (the stale value from the original failing run) as the
  final Barcode field content.
