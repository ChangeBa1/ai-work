# Feature Specification: 修复键盘文本输入能力（type_text 驱动缺陷）

**Feature Branch**: `[006-fix-keyboard-text-input]`

**Created**: 2026-07-24

**Status**: Draft

- Q: FR-016 所要求的“至少两个互不相关的测试场景”，第二个场景应满足什么条件？ → A: 第二个场景无需是独立的真实业务 GUI 测试用例；可以是与条码输入无关的合成/契约级场景（例如不同字符组合、不同通用控件上下文），与 FR-015 回归测试同层级，无需真实 VNC 会话。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 已聚焦输入控件的普通文本输入按序正确送达 (Priority: P1)

测试用例设计者编写一个 `type_text` 步骤，指向一个已经通过前序步骤（如双击全选）获得输入焦点的
文本框。系统执行该步骤时，必须将声明的文本内容按原始字符顺序完整送达该输入控件，使输入框最终
显示的内容与声明文本一致。

**Why this priority**: 这是本次事故的直接触发路径——文本输入是黑盒 GUI 测试中最基础、最高频的
动作之一；只要这条路径不可用，任何依赖表单/字段输入的测试用例都无法继续执行后续步骤，因此必须
最优先修复。

**Independent Test**: 可独立验证：让一个已聚焦、已全选原内容的输入控件执行一次 `type_text`
步骤，声明文本为纯数字字符串，观察执行结果为成功且截图/断言确认输入框内容与声明文本一致。

**Acceptance Scenarios**:

1. **Given** 一个已获得焦点且原内容已被全选的输入控件，**When** 执行 `type_text` 步骤声明文本
   `"45127366"`，**Then** 执行结果标记为成功，且输入控件最终显示内容为 `45127366`（覆盖原有
   内容，八位数字不多不少）。
2. **Given** 同一测试用例中 `type_text` 步骤成功完成，**When** 后续步骤继续点击输入框旁的操作
   按钮，**Then** 该后续步骤能够正常执行，不因前序输入失败而被跳过或收到陈旧数据。
3. **Given** 声明文本包含字母、数字与常见 ASCII 标点的混合字符串，**When** 执行 `type_text`
   步骤，**Then** 输入控件中出现的字符顺序与声明文本的字符顺序完全一致，不发生乱序、丢字符或
   重复字符。

---

### User Story 2 - 换行与 Tab 的既有语义保持不变 (Priority: P2)

测试用例设计者在声明文本中使用换行符或 Tab 字符，期望系统分别将其解释为“确认/回车”与“切换到
下一个控件”的既有键盘语义，而不是把它们当作普通可见字符逐一输入。

**Why this priority**: 换行/Tab 语义是当前实现已经存在且被依赖的行为；修复过程中必须原样保留，
避免在解决 P1 缺陷的同时引入新的回归。

**Independent Test**: 可独立验证：声明一段包含 `\n` 或 `\t` 的文本，执行后确认对应位置触发的是
“确认/换行”或“切换焦点”的效果，而不是插入不可见字符或报错。

**Acceptance Scenarios**:

1. **Given** 声明文本中包含换行符，**When** 执行 `type_text` 步骤，**Then** 该位置被解释为回车
   确认动作，而非在控件中插入换行符字面量。
2. **Given** 声明文本中包含 Tab 字符，**When** 执行 `type_text` 步骤，**Then** 该位置被解释为
   切换到下一个可聚焦控件的动作，而非在当前控件中插入制表符字面量。

---

### User Story 3 - 空文本与中途失败的结果必须真实可信 (Priority: P2)

无论是声明空字符串，还是在文本发送过程中遇到底层异常，系统上报的执行结果都必须准确反映实际发生
的情况：空文本视为“无操作但成功”，中途异常必须视为整体失败，不得把部分完成的输入误报为成功。

**Why this priority**: 这是保障测试结果可信度的核心约束——测试系统的价值建立在“通过”真正代表
成功之上；如果失败被误判为成功，回归基线会掩盖真实缺陷，比缺陷本身更危险。

**Independent Test**: 可独立验证：分别构造空字符串输入场景与底层发送中途抛出异常的场景，检查
执行结果的成功/失败标记、错误信息是否与实际情况一致。

**Acceptance Scenarios**:

1. **Given** 声明文本为空字符串，**When** 执行 `type_text` 步骤，**Then** 系统不发送任何键盘
   事件，且执行结果标记为成功（无操作亦为成功）。
2. **Given** 文本发送过程中在某个字符处发生底层驱动异常，**When** 该异常发生，**Then** 系统必须
   立即停止继续发送后续字符，且执行结果标记为失败，错误信息中包含可用于定位问题的驱动层描述，
   不得将已发送的部分字符呈现为“输入完成”。
3. **Given** 文本发送在允许的时间窗口内未完成，**When** 触发超时，**Then** 执行结果标记为超时
   失败，而不是被误判为成功（例如仅因为屏幕在等待期间发生了无关的时钟/状态变化）。

---

### Edge Cases

- 声明文本仅包含换行或仅包含 Tab（无普通字符）时，是否仍能正确逐一触发对应语义，且不遗漏最后
  一个字符？
- 声明文本中连续出现多个换行或 Tab（如 `"\n\n"`、`"\t\t"`）时，是否按顺序逐一触发，而不是合并
  为一次动作？
- 声明文本长度较长（如数十至上百字符）时，是否仍能保持顺序且不因批量发送而丢字符？
- 目标输入控件未处于焦点状态（例如前序聚焦步骤本身失败）时，`type_text` 是否仍会尝试发送，其
  失败原因是否与“文本发送本身失败”可区分（此为既有前序步骤职责，不在本次修复范围内改变，但
  错误信息不应产生误导）？
- 声明文本中包含可打印 ASCII 标点符号（如 `-`、`_`、`.`、`@`、`/`、`:` 等测试数据中常见符号）
  时，是否都能正确送达而不是仅数字/字母可用？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在执行针对已聚焦输入控件的 `type_text` 动作时，按声明文本的原始字符
  顺序，将完整文本内容送达该控件。
- **FR-002**: 系统 MUST 正确支持纯数字字符串的输入（覆盖本次事故的直接触发场景），输入结果与
  声明文本逐字符一致。
- **FR-003**: 系统 MUST 至少支持全部可打印 ASCII 字符（字母、数字、常见标点符号）的顺序输入。
- **FR-004**: 系统 MUST 保留现有的换行语义：声明文本中的换行符 MUST 被解释为“确认/回车”动作，
  而不是被当作普通字符送入控件。
- **FR-005**: 系统 MUST 保留现有的 Tab 语义：声明文本中的 Tab 字符 MUST 被解释为“切换焦点到
  下一个控件”动作，而不是被当作普通字符送入控件。
- **FR-006**: 当声明文本为空字符串时，系统 MUST NOT 发送任何键盘事件，且 MUST 将该动作视为
  成功的无操作（no-op）。
- **FR-007**: 当文本发送过程中任意一个字符的发送失败（底层驱动异常）时，系统 MUST 立即停止发送
  后续字符，MUST NOT 继续发送剩余内容。
- **FR-008**: 当文本发送中途失败时，系统 MUST 将该动作的执行结果标记为失败，MUST NOT 将部分
  完成的输入报告为成功。
- **FR-009**: 执行结果 MUST 准确区分“成功”“超时”“驱动错误”三类情形，且该判定 MUST 仅依据
  实际发送过程中观察到的结果，MUST NOT 因执行期间发生的无关画面/时钟变化而将失败误判为成功，
  或将成功误判为失败。
- **FR-010**: 系统 MUST NOT 依赖远程剪贴板粘贴（例如 Ctrl+V 或等价的剪贴板注入方式）作为普通
  文本输入的实现手段。
- **FR-011**: 本次修复 MUST NOT 修改任何正式测试用例（testcase YAML）的步骤定义或断言内容来
  规避或掩盖驱动层缺陷。
- **FR-012**: 本次修复 MUST 仅改动项目自身的通用驱动层或执行层代码，MUST NOT 修改第三方依赖库
  的已安装代码（site-packages）。
- **FR-013**: 本次修复 MUST NOT 改变现有对外可调用的文本输入相关公共接口的调用方式（即调用方
  仍以相同的方式请求“发送一段文本”“执行一次文本输入动作”“路由一次文本输入动作”，无需感知
  内部实现变化）。
- **FR-014**: 核心文本输入实现 MUST 保持业务无关：MUST NOT 出现任何被测应用、行业或具体测试
  场景专用的字段、关键词、分支或硬编码测试数据（包括但不限于条形码、扫码模拟器相关命名或具体
  条码数值）。
- **FR-015**: 系统 MUST 提供自动化回归测试，验证文本输入执行路径中不再调用任何不存在的底层
  方法，防止同类“调用了不存在的驱动方法”缺陷再次发生且未被测试捕获。该回归测试 MUST 可在
  不连接真实 VNC 会话的情况下运行（使用可替身/fake 客户端验证调用路径），以便稳定纳入常规
  自动化测试套件；真实 VNC 环境下的端到端确认由 SC-001 单独覆盖，不要求纳入同一测试。
- **FR-016**: 声称已修复的通用文本输入能力 MUST 至少通过两个互不相关的测试场景验证，以证明
  修复是通用能力而非只适配单一事故用例。其中一个场景 MUST 是本次事故的真实业务用例（经真实
  VNC 会话确认，见 SC-001）；第二个场景 MAY 为与条码输入无关的合成/契约级场景（例如不同字符
  组合、不同通用控件上下文），MAY 与 FR-015 回归测试同层级运行，MUST NOT 要求额外的真实 VNC
  会话。

### Key Entities

- **文本输入动作（type_text 动作）**: 一次针对当前已聚焦控件的完整文本输入请求；关键属性包括
  待输入的文本内容、执行结果（成功/失败/超时）、失败时的错误描述。
- **执行结果（ExecutionResult）**: 对一次动作执行情况的独立记录；关键属性包括成功与否、是否
  超时、错误码/错误信息；其判定必须真实反映执行过程，不受执行期间无关环境变化影响。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用 `pos-scan-magazine-checkout.yaml` 重新运行 `type-barcode-45127366` 步骤时，
  输入框内容从原值变为声明的 `45127366`，步骤执行结果为成功，且后续 `Scan` 步骤能够被执行
  （不再因文本输入失败而中断）。
- **SC-002**: 对包含字母、数字、常见 ASCII 标点的混合文本进行输入验证时，100% 的字符按声明顺序
  出现在目标控件中，不发生丢字符、乱序或多余字符。
- **SC-003**: 对空字符串输入进行验证时，动作执行结果 100% 标记为成功，且验证过程确认未产生任何
  键盘事件。
- **SC-004**: 对中途注入的发送异常进行验证时，动作执行结果 100% 标记为失败，且不出现“部分输入
  被判定为成功”的情况。
- **SC-005**: 新增的自动化回归测试（使用可替身/fake 客户端、无需真实 VNC 会话）在修复前的代码
  上必须能够复现“调用不存在的驱动方法”这一失败模式，在修复后的代码上必须稳定通过，从而具备
  防止同类回归的能力，且可稳定纳入常规自动化测试套件运行。
- **SC-006**: 修复后的文本输入能力在至少两个互不相关的测试场景下均验证通过——一个是本次事故的
  真实业务用例（真实 VNC 会话确认，对应 SC-001），另一个是与条码输入无关的合成/契约级场景
  （无需真实 VNC 会话）——且核心实现代码中不包含任何具体业务场景的专用分支或硬编码值。

## Assumptions

- 修复范围仅覆盖可打印 ASCII 字符及现有的换行、Tab 语义；任意 Unicode 字符或输入法（IME）级别
  的文本输入不在本次修复范围内（与用户声明的范围外一致）。
- 不更换当前使用的 VNC 客户端库，修复必须在项目自身代码范围内完成。
- 不对 Planner、Grounder 或 Verifier 的职责与实现做任何调整；本次修复仅涉及“已经确定目标控件
  并已获得焦点之后，如何把文本发送出去”这一执行层能力。
- 输入控件是否已经处于正确聚焦状态，由测试用例中的前序步骤（如点击、双击全选）负责保证；本次
  修复不改变“如何让控件获得焦点”的既有行为。
- 现有对外公共调用方式（发起一次文本输入请求、路由一次文本输入动作）的入参与返回结构保持不变，
  修复仅涉及这些调用背后如何与底层 VNC 会话交互。
