# Feature Specification: 稳定动作身份与坐标空间定位纠正

**Feature Branch**: `003-action-identity-grounding`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "002（自适应动作效果检测与可信业务验证）已实现并离线测试通过（116 passed, 1
skipped），但在真实 VNC 验收（Run ID cefe36a9-f5c3-4622-9998-ef06690a5ab6）中暴露出两个新缺陷：①
Planner 在同一测试步骤的重试中对同一非幂等业务动作（点击购物袋按钮，action_id 始终为 act-1）改写了
intent/target 描述措辞，导致 RepeatGuard 的自由文本相等判断将后两轮误判为 different_action，从而执行了
两次多余的鼠标点击；其中一次改写把目标从"购物袋按钮"变成了"已添加的购物袋商品行"，这是危险的目标漂移，
不应被直接点击；② Grounder 返回的候选坐标缺乏明确的坐标空间协议（原始像素 vs 0–1000 归一化），在
1024×1568 这类纵向尺寸远超 1000 的非正方形分辨率下容易被误用，很可能是其中一次点击落在错误屏幕位置的
根因。整屏变化比例低至 0.4669% 时 ActionEffect 仍正确判定为 expected_effect（002 的修复本身有效），但
因为 pos-buy-bag-checkout.yaml 仍只声明了 screen_changed，业务验证结果只能停留在 weak assertion /
uncertain，导致该问题未能在验收前被发现，"小計"这第二个步骤也从未被执行到。本 feature 需要：用不依赖
自由文本完全相等的稳定动作身份（结合 step、action_type、action_id、规范化业务目标）修正 RepeatGuard 的
同一动作判定；识别并阻止"可交互控件→结果展示元素"这类危险目标漂移的直接点击；为 Grounder 建立显式坐标
空间协议（至少支持原始像素坐标与 0–1000 归一化坐标），执行前统一换算为当前截图的原始像素坐标，缺失/
矛盾/越界时停止并重新定位而非猜测；把 pos-buy-bag-checkout.yaml 升级为使用 verification_mode: business
的可信业务验收用例（购物车恰好 1 件 5 円、レジ袋文字出现、随后点击小計并验证进入小計确认画面、不得进入
支付）；保持旧格式用例可加载但与可信业务通过在报告中清晰区分；报告需可审计动作身份、RepeatGuard 判定、
坐标空间换算与最终业务断言依据；不得通过盲目 Tab、额外点击或自动清空购物车来恢复；常规自动化测试不得
连接真实 VNC，真实 VNC 验收仍作为独立人工批准环节。SSMS 与本 feature 无关，不写入需求或错误分类。"

## Clarifications

### Session 2026-07-21

- Q: RepeatGuard 计算稳定动作身份时，其作用范围应该是什么？跨测试步骤出现相同 `action_id` 是否也应
  被视为同一动作身份的延续？ → A: 动作身份的判定范围 MUST 限定在当前测试步骤（TestStep）内；不同
  测试步骤之间，即便语义动作的 `action_id` 数值相同，也 MUST NOT 被视为同一稳定动作身份的延续。
- Q: 在同一测试步骤内，当 `action_type` 与 `action_id` 相同，但 `intent`/`target.role`/`target.text`/
  `description` 等自由文本字段被 Planner 同义改写时，是否足以构成“同一逻辑动作”的判定依据？
  → A: 是。同一测试步骤内相同 `action_type` 与相同且非空 `action_id` 的组合即构成强匹配证据，MUST
  视为同一逻辑动作，即使 `intent`、`target.role`、`target.text` 或 `target.description` 在这些迭代
  之间发生同义改写或表述差异；若 `action_type` 不同，则不得命中该强匹配分支。
- Q: 当同一测试步骤内连续迭代未提供相同的 `action_id`（缺失、为空或确实变化）、导致动作身份存在歧义
  时，系统的默认行为应该是什么？ → A: 采用保守的 fail-safe 默认行为：当动作身份或"新目标是否符合
  步骤 intent"的验证结果存在歧义，且前一次同一逻辑非幂等动作尚未被可靠判定为 `no_effect` 时，系统
  MUST 禁止再次执行，转入重新观察与加强业务验证，而不是默认放行执行。
- Q: 当 Planner 在同一测试步骤重试时改变了目标对象（`action_id` 不再匹配或目标描述实质变化），系统
  应如何判断这是否是一次合法的新目标，而不是简单地当作"真正不同的动作"直接放行执行？ → A: MUST NOT
  自动视为真正不同的动作；系统 MUST 先验证新目标是否仍然符合该测试步骤已声明的 `intent`，只有验证
  通过才 MAY 将其视为该步骤内的合法新目标并允许执行；验证不通过或存在歧义时按上一条 fail-safe 规则
  处理。
- Q: Grounder 响应中坐标空间应该通过什么规范化字段声明，支持哪些取值，转换应该在管线中发生几次？ →
  A: Grounder 返回的每个候选目标 MUST 通过显式字段 `coordinate_space` 声明坐标空间，取值至少包含
  `pixel`（原始像素坐标）与 `normalized_1000`（0–1000 归一化坐标，X/Y 两轴分别独立相对图像宽度/
  高度归一化）；从声明的坐标空间换算为原始像素坐标的转换 MUST 有且仅发生一次，系统 MUST NOT 对已经
  完成换算的坐标重复换算，也 MUST NOT 在多个处理环节各自独立换算导致结果不一致。
- Q: 对于本 feature 之前产生的、不包含 `coordinate_space` 字段的历史 Grounder 响应，系统应如何处理？
  → A: 默认仍需拒绝并停止，但允许一种受限例外：当且仅当系统能够仅依据当前截图分辨率与已有证据
  （如候选坐标数值范围）可靠、无歧义地推断出其坐标空间时，MAY 使用推断结果继续执行；只要推断存在
  任何不确定性，MUST 拒绝该候选并停止，MUST NOT 猜测后仍然点击。
- Q: `pos-buy-bag-checkout.yaml` 升级为可信业务用例后，本 feature 范围内的其他旧格式用例应如何处理？
  → A: 仅 `pos-buy-bag-checkout.yaml` 本身从 legacy weak assertion 用例迁移为正式业务
  （`verification_mode: business`）用例；本 feature 范围内的其他旧格式用例继续保持既有的兼容加载与
  弱断言判定行为，不强制迁移。
- Q: 真实 VNC 验收运行时，被测环境的起始状态（购物车 0 件、0 円）应如何达成？程序是否可以自行点击
  "クリア"（清空/清除）类操作来重置现场？ → A: 真实 VNC 验收运行 MUST NOT 由程序自动点击"クリア"或
  等效的清空/重置操作来清理被测环境；验收运行的起始状态（购物车 0 件、合计 0 円）MUST 由人工确认后
  才允许开始运行，而不是由程序自行清理现场后开始。

### User Story 1 - 措辞改写不应打断对同一非幂等业务动作的识别 (Priority: P1)

作为测试工程师，我希望当 Planner 在同一测试步骤的重试中，用不同的措辞重新描述同一个业务动作（例如
"点击购物袋按钮" 改写成 "点击\"レジ袋\"（购物袋）按钮，将一个购物袋商品加入购物车"）时，系统仍能把它
识别为同一个非幂等业务动作的重复尝试，而不是把它当作一个全新的、可以自由执行的不同动作；这一判定 MUST
限定在当前测试步骤范围内，且当同一步骤内 `action_id` 保持相同时，MUST 以此作为决定性证据，不因措辞
差异而改判。

**Why this priority**: 这是本次真实验收事故的直接根因——RepeatGuard 依赖 intent/target 描述的自由文本
完全相等来判断"是否为同一动作"，Planner 三轮重试中始终使用相同的 `action_id`（"act-1"）却改写了
措辞，导致后两轮被误判为 `different_action`，从而执行了两次本应被拦截的多余鼠标点击。不修复这一判定，
后续所有关于"非幂等动作不得重复执行"的保证（002 已交付）都会在真实模型改写措辞时失效。

**Independent Test**: 使用该次真实运行中三轮迭代的固定 `SemanticAction` 记录（`action_id` 均为
"act-1"，但 intent/target.description 逐轮改写），可独立验证稳定动作身份判定与 RepeatGuard 能否将
后两轮识别为同一动作的重复尝试，而无需连接真实 VNC 环境。

**Acceptance Scenarios**:

1. **Given** 同一测试步骤内连续两轮迭代的语义动作，`action_type` 相同、`action_id` 相同且非空，
   **When** 系统计算两轮动作的稳定动作身份，**Then** 系统判定二者身份相同——即使 `intent`、
   `target.role`、`target.text` 或 `target.description` 的自由文本表述在这两轮之间不完全一致，
   `action_type` 与 `action_id` 的组合相同即构成决定性证据。
2. **Given** 上述场景中第一轮动作已产生 `expected_effect` 但业务结果仍 `uncertain`，**When** 系统据此
   判断第二轮是否可以执行，**Then** RepeatGuard 判定二者为同一动作并拦截第二轮的直接执行，转入加强
   验证，而不是将其归类为 `different_action` 并放行。
3. **Given** 目标文字锚点因 OCR 波动个别字符缺失（如"レジ袋"被识别为"ジ袋"），但上下文（附近文字、
   位置区域、action_id）表明仍是同一目标，**When** 系统计算规范化业务目标，**Then** 系统仍将其识别为
   同一核心业务目标，而不是因逐字符不完全相等就判定为不同目标。
4. **Given** 一次真正不同的语义动作（如 `action_type` 不同、或明确指向另一个业务功能），**When** 系统
   计算稳定动作身份，**Then** 系统正确判定为不同身份，不得因过度宽松的匹配而错误合并两个真正不同的
   动作。
5. **Given** 两个不同测试步骤中恰好出现了数值相同的 `action_id`，**When** 系统计算稳定动作身份，
   **Then** 系统不会将其视为同一动作身份的延续——测试步骤边界具有强制力，动作身份 MUST NOT 跨步骤
   匹配。
6. **Given** 同一测试步骤内连续迭代未提供相同的 `action_id`（缺失、为空或确实发生变化），**When**
   系统评估新目标是否可以被视为一次合法的新动作，**Then** 系统 MUST NOT 默认将其当作真正不同的动作
   直接放行执行，而是先验证新目标是否仍然符合该测试步骤已声明的 `intent`。
7. **Given** 上述验证结果存在歧义（既不能确认是同一动作，也不能确认新目标符合步骤 intent），且前一次
   同一逻辑非幂等动作尚未被可靠判定为 `no_effect`，**When** 系统决定下一步操作，**Then** 系统默认
   采用 fail-safe：禁止再次执行，转入重新观察与加强业务验证，而不是默认放行。
8. **Given** 同一测试步骤内，Planner 提出的新目标具有独立于此前非幂等动作的交互目的（如先关闭遮挡
   该按钮的弹窗、先滚动使目标可见），且经步骤 intent 一致性验证判断为符合该步骤已声明的 intent，
   **When** 系统评估该新目标，**Then** 系统允许将其视为合法的步骤内前置微动作并执行；但该微动作
   本身 MUST NOT 被用作重新执行同一个已经产生效果、业务结果尚未确定的主要非幂等动作的手段。

### User Story 2 - 识别并阻止从可交互控件到结果展示元素的危险目标漂移 (Priority: P1)

作为测试工程师，我希望当 Planner 把目标描述从一个可交互控件（如"购物袋按钮"）改写为一个非交互的结果
展示元素（如"已添加的购物袋商品行"）时，Agent 能识别出这是一次危险的目标漂移，并且不直接对新目标执行
点击，而不是像真实事故中那样直接点了下去；这类漂移正是 User Story 1 中"新目标是否符合步骤 intent"
验证失败的一种具体、高风险的表现形式。

**Why this priority**: 这是本次真实事故中最危险的一步——第三轮迭代中 Planner 把目标描述从"购物袋按钮"
改成了"点击购物袋（レジ袋）商品行，将其加入购物车"，系统随后直接点击了商品列表中的一行文字而非按钮；
这次点击恰好没有造成明显破坏（`effect_uncertain`），但这类漂移在其他场景下可能触发选中/删除/跳转等
非预期后果，必须在执行前而非事后才拦截。

**Independent Test**: 使用该次真实运行第二、三轮迭代中"按钮→商品行"的目标描述漂移作为固定输入，可独立
验证危险目标漂移判定能否在执行阶段之前拒绝直接点击，而无需真实触发任何鼠标动作。

**Acceptance Scenarios**:

1. **Given** 同一测试步骤内，新提出的目标描述从指向一个可交互控件（如"按钮"）变为指向一个非交互的
   结果展示元素（如"商品行"、"列表条目"、"已添加的商品"），**When** 系统评估该目标是否符合 User
   Story 1 所要求的"与步骤 intent 一致"验证，**Then** 系统判定该验证不通过，归类为危险动作漂移，不
   直接执行点击。
2. **Given** 判定为危险动作漂移，**When** 系统决定下一步，**Then** 系统停止当前直接执行路径，转入既有
   的失败分类与恢复/重新定位流程，而不是猜测这是否安全后仍然点击。
3. **Given** 危险动作漂移的判定，**When** 系统评估该轮的动作效果，**Then** 该判定 MUST 在动作被发送
   执行之前就已生效，不依赖执行后 ActionEffect 的结果来回溯认定。
4. **Given** 一次目标描述的变化仍然指向同一类可交互控件（例如按钮的措辞变化，但角色、位置、锚点文字
   均一致或高度吻合），**When** 系统评估是否为危险漂移，**Then** 系统不得将这类正常的措辞变化误判为
   危险漂移。
5. **Given** 同一测试步骤内，新提出的目标仍然指向一个可交互控件，但该控件已不再是该步骤 intent 所
   指向的那一个控件（例如从"购物袋按钮"漂移为"删除按钮"这类另一个不相关的可交互控件），**When**
   系统评估该目标是否符合步骤 intent 一致性验证，**Then** 系统同样判定该验证不通过，归类为危险动作
   漂移，不直接执行点击——危险漂移的判定不局限于"控件→非交互元素"这一种方向。

### User Story 3 - Grounder 坐标必须遵循显式坐标空间协议，缺失或矛盾时停止而非猜测 (Priority: P1)

作为测试工程师，我希望 Grounder 返回的每个候选坐标都通过显式字段 `coordinate_space` 声明其坐标空间
（`pixel` 原始像素坐标或 `normalized_1000` 归一化坐标），系统在执行点击前把它换算为当前截图的原始像素
坐标且只换算一次；当坐标空间缺失、自相矛盾或换算后越界时，系统应停止并重新定位，而不是把归一化坐标当作
像素坐标直接使用。

**Why this priority**: 这很可能是本次真实事故中第二轮点击落在错误屏幕位置（从原本约 y=678 变成
约 y=430）的根因——被测环境分辨率为 1024×1568，纵向尺寸远超 1000，如果模型返回的是 0–1000 归一化
坐标而系统当作原始像素坐标直接使用，就会产生这类大幅偏移，且该偏移不会被现有的越界校验捕获（因为
430 本身仍在 0–1568 范围内，只是不是模型真正想表达的位置）。

**Independent Test**: 使用固定的候选坐标数据（分别声明 `coordinate_space` 为 `pixel` 与
`normalized_1000`）配合 1024×1568 等非正方形、纵向尺寸超过 1000 的画面尺寸，可独立验证坐标空间换算
逻辑能否得到正确的原始像素坐标，而无需连接真实 VNC 环境或真实调用 Grounder 模型。

**Acceptance Scenarios**:

1. **Given** 一个候选目标显式声明 `coordinate_space: normalized_1000`，画面实际分辨率为 1024×1568，
   **When** 系统在执行前换算该候选坐标，**Then** 系统按 X 轴相对宽度、Y 轴相对高度分别换算，得到
   落在 [0,1024) × [0,1568) 范围内的正确原始像素坐标，而不是把归一化数值直接当作像素坐标使用；该次
   换算 MUST 有且仅发生一次。
2. **Given** 一个候选目标显式声明 `coordinate_space: pixel`，**When** 系统在执行前处理该候选，
   **Then** 系统不对其做归一化换算，直接使用（并仍需校验其落在当前截图分辨率范围内）。
3. **Given** 一个候选目标未声明 `coordinate_space`、声明了 `pixel`/`normalized_1000` 之外的未知
   取值、或声明的坐标空间与其数值范围明显矛盾（如声称像素坐标但数值超出截图分辨率、或声称归一化
   坐标但数值超出 [0, 1000]），且——对不含 `coordinate_space` 字段的历史响应——系统无法找到恰好
   一种解释（`pixel` 或 `normalized_1000`）同时满足完整边界约束与已有证据一致性约束，**When** 系统
   处理该候选，**Then** 系统拒绝该候选，不猜测其含义后仍然执行点击。
4. **Given** 全部候选均因坐标空间缺失、矛盾、未知取值或换算后越界而被拒绝，**When** 系统评估下一步，

### Edge Cases

- 目标文字锚点因 OCR 波动个别字符缺失或多出（如"レジ袋"被识别为"ジ袋"）时，规范化业务目标匹配应
  如何在"容忍轻微 OCR 噪声"与"避免把两个真正不同的目标错误合并"之间取舍？
- 页面因上一次动作成功而发生布局变化（如商品列表新增一行导致后续控件的屏幕坐标整体偏移，如本次
  事故中按钮位置从约 y=678 变为候选返回的约 y=430）时，系统应如何区分"同一控件因布局变化而换了
  位置"与"目标已经漂移到了另一个元素"？
- 同一测试步骤内，Planner 合理地插入了必要的前置微动作（如先关闭遮挡的弹窗、先滚动使目标可见，
  001 已允许的行为）而使用了不同的 `action_id` 和目标时，系统应如何将这种"步骤内合法的新子目标"
  与"对同一非幂等动作的危险身份漂移"区分开，避免 fail-safe 规则误伤前者？（区分依据是：合法的
  前置微动作通常指向与此前动作不同的、真正独立的交互目的，且通过与步骤 intent 一致性验证；仅当
  新目标被判定为原地"替代"了同一个尚未确认业务结果的非幂等动作时，才适用本 feature 的 fail-safe
  与危险漂移规则。）
- Grounding 候选完全未声明 `coordinate_space`、且其数值本身在两种可能空间下都不越界（即无法仅凭
  数值范围消歧）、当前截图分辨率与已有证据也不足以可靠推断时，应如何处理？（按 FR-015 拒绝该候选
  并停止，不得任选一种空间强行使用。）
- 危险目标漂移判定触发、且该测试步骤的重试预算耗尽仍未能重新定位到正确目标时，该步骤最终应如何
  收尾？（应按既有的预算耗尽规则判定该步骤失败，不得为漂移场景单独开辟额外的重试通道。）
- 旧格式用例与本 feature 更新后的新格式用例在同一次测试运行或同一份报告中混合出现时，两类判定结果
  的呈现如何保持互不误导？
- 归一化坐标与真实原始像素坐标在数值上恰好同时落在两种空间的合理范围内（如坐标数值本身小于
  1000 且分辨率也大于该数值）时，如何避免歧义？（在 `coordinate_space` 已被显式声明的前提下不存在
  歧义；本条边界仅适用于坐标空间缺失的场景，此时按 FR-015 拒绝而非猜测。）
- 真实 VNC 验收运行前，人工确认的起始状态（0 件/0 円）与程序实际观察到的起始画面不一致时，系统应
  如何处理？（应视为环境前置条件不满足，停止并报告，而不是自行尝试清理或纠正现场后继续运行。）

## Requirements *(mandatory)*

### Functional Requirements

**稳定动作身份**

- **FR-001**: 动作身份的判定范围 MUST 限定在当前测试步骤（TestStep）内；不同测试步骤之间，即便
  语义动作的 `action_id` 数值相同，也 MUST NOT 被视为同一稳定动作身份的延续。
- **FR-002**: 在同一测试步骤内，当连续迭代的语义动作具有相同的 `action_type`，并提供了相同且非空的
  `action_id` 时，`action_type` 与 `action_id` 的组合即构成同一逻辑动作的强匹配证据——MUST 视为
  同一稳定动作身份，即使 `intent`、`target.role`、`target.text` 或 `target.description` 在这些迭代
  之间发生了同义改写或表述差异。相同 `action_id` 但不同 `action_type` 的动作不满足本条强匹配条件，
  MUST 按 FR-007 视为不同业务动作的决定性危险信号。
- **FR-003**: 当同一测试步骤内的连续迭代未提供相同的 `action_id`（包括缺失、为空或确实发生变化）
  时，系统 MUST NOT 仅因此就默认视为一次真正不同的业务动作；MUST 先验证新的目标是否仍然符合该
  测试步骤已声明的 `intent`，只有验证通过才 MAY 将其视为该步骤内的合法新目标并允许执行。当新目标
  经该验证后被判断为具有独立于此前动作的交互目的、且不构成对同一非幂等动作的延续的合法前置微动作
  （例如关闭遮挡的弹窗、滚动使目标可见，参见 001 已确立的步骤内微动作机制）时，系统 MAY 将其视为
  该步骤内的新合法目标并允许执行；此类微动作本身 MUST NOT 被用于重新执行同一个已经产生效果、业务
  结果尚未确定的主要非幂等动作。
- **FR-004**: 当系统无法可靠证明同一测试步骤内新提出的动作与前一次非幂等动作确实不同时（包括
  `action_id` 缺失/变化、或 FR-003 所要求的步骤 intent 一致性验证结果存在歧义），系统 MUST 保守地
  将新动作视为可能与前一次为同一逻辑非幂等动作；若前一次该动作对应的业务结果（StepVerificationResult）
  尚未确定为 `passed` 或 `failed`，且其 ActionEffect 尚未被可靠判定为 `no_effect`，系统 MUST 禁止
  执行该新动作，转入重新观察与加强业务验证，MUST NOT 默认放行执行。本条 fail-safe 规则 MUST 仅
  约束非幂等动作；对幂等动作，系统 MAY 按 001/002 已确立的既有规则自由重试，不受本条约束。
- **FR-005**: 当目标文字锚点因 OCR 波动在相邻迭代间出现个别字符缺失或多出（如"レジ袋"与"ジ袋"）、
  但其余上下文（附近文字、目标区域、`action_id`）表明仍指向同一业务目标时，系统 SHOULD 仍将其识别
  为同一核心业务目标，而不是仅要求逐字符完全相等；本条使用 SHOULD 而非 MUST NOT，是因为 OCR 噪声
  容忍本身是概率性、尽力而为的匹配增强，区别于 FR-002 中"`action_id` 相同即决定性证据"这一确定性
  强规则——`action_id` 缺失时，OCR 容忍匹配仅作为 FR-003 步骤 intent 一致性验证的辅助信号之一，
  不单独构成决定性证据。
- **FR-006**: RepeatGuard（或本 feature 引入的等效重复执行防护组件）判断"是否为同一非幂等动作"
  MUST 基于 FR-001～004 定义的稳定动作身份与 fail-safe 规则，MUST NOT 仅依据自由文本是否逐字相等。
  对任一非幂等动作，只有当其上一次执行对应的 ActionEffect 被可靠确认为 `no_effect`、且该测试步骤
  的共享重试预算仍有剩余时，系统才 MAY 允许重新执行该动作——这是允许重新执行非幂等动作的唯一条件；
  `expected_effect`、`effect_uncertain`、`unexpected_effect` 三种 ActionEffect 状态，以及动作身份
  或步骤 intent 一致性判定存在歧义的情形，均 MUST NOT 触发重复执行。
- **FR-007**: 稳定动作身份的匹配 MUST NOT 过度宽松到将两个真正不同的业务动作（如不同的 `action_type`
  或明确指向不同业务功能的目标）错误合并为同一身份。

**危险目标漂移检测**

- **FR-008**: 当同一测试步骤内，新提出的目标从指向一个可交互控件（如按钮）漂移为指向一个非交互的
  结果展示元素（如已添加的商品行、列表条目、状态文字）时，系统 MUST 将其判定为不满足 FR-003 所要求
  的"与步骤 intent 一致"验证，归类为危险动作漂移。同样地，当新提出的目标从一个可交互控件漂移为
  另一个不符合该测试步骤已声明 intent 的可交互控件时（即新目标仍然可交互，但已不再是该步骤 intent
  所指向的那一个控件），系统 MUST 同样将其判定为不满足步骤 intent 一致性验证，归类为危险动作漂移；
  危险动作漂移的判定 MUST NOT 仅局限于"可交互控件→非交互结果展示元素"这一种漂移方向。
- **FR-009**: 判定为危险动作漂移时，系统 MUST NOT 直接对新目标执行点击等动作；MUST 停止当前直接
  执行路径，转入既有的失败分类与恢复/重新定位流程。
- **FR-010**: 危险动作漂移的判定 MUST 在动作被发送执行之前完成（例如在动作选择或重复执行防护阶段），
  MUST NOT 等到执行后依据该轮 ActionEffect 的结果才回溯认定。
- **FR-011**: 危险动作漂移的判定 MUST NOT 将目标描述的正常措辞变化（角色、位置、锚点文字均一致或
  高度吻合、仍指向同一类可交互控件）误判为危险漂移。

**Grounding 坐标空间协议**

- **FR-012**: Grounder 返回的每个候选目标 MUST 通过显式字段 `coordinate_space` 声明其边界框所使用
  的坐标空间，取值至少包含 `pixel`（原始像素坐标）与 `normalized_1000`（0–1000 归一化坐标，X、Y
  两个坐标轴分别独立相对图像宽度、高度归一化）。同一次 Grounding 响应中的不同候选 MAY 分别独立声明
  不同的 `coordinate_space`；系统 MUST 对每个候选分别按其自身声明的坐标空间独立完成换算与校验，
  MUST NOT 对整个响应套用单一坐标空间假设。
- **FR-013**: 系统在使用任何候选坐标执行动作之前，MUST 将其统一换算为当前实际截图分辨率下的原始
  像素坐标；换算逻辑 MUST 同时正确处理正方形与非正方形（如 1024×1568）分辨率，不得将某一归一化坐标
  轴的数值误当作另一坐标轴或原始像素值直接使用。`normalized_1000` 的合法取值范围为闭区间
  [0, 1000]（0 与 1000 本身均视为合法边界值，不视为越界）。候选的完整边界框（bbox）换算后的四个
  角点、以及最终用于点击执行的坐标点，MUST 全部落在当前实际截图分辨率的原始像素范围内；任一角点或
  最终点击点越界，均 MUST 按 FR-015/016 的越界规则拒绝该候选。
- **FR-014**: FR-013 所述的换算——即同一个候选坐标从其声明的坐标空间换算为原始像素坐标——MUST 有
  且仅发生一次；系统 MUST NOT 对已经完成 FR-013 换算的坐标重复执行该换算，也 MUST NOT 在多个处理
  环节各自独立实现并执行该换算导致结果不一致；本条与 FR-013 描述的是同一次换算的"仅一次"约束，而
  非两个独立的换算步骤。
- **FR-015**: 当候选目标未声明 `coordinate_space`、声明了 FR-012 定义之外的未知取值（既非 `pixel`
  也非 `normalized_1000`）、或声明的坐标空间与其数值范围明显矛盾（如声称像素坐标但数值超出截图
  分辨率、或声称归一化坐标但数值超出 [0, 1000]）时，系统 MUST 拒绝该候选，MUST NOT 猜测其含义后
  仍然执行点击。对于本 feature 之前产生的、不含 `coordinate_space` 字段的历史 Grounder 响应，系统
  MAY 尝试推断其坐标空间，但推断 MUST 同时满足以下条件才可采用：(a) 将该候选坐标分别代入 `pixel`
  与 `normalized_1000` 两种解释后，MUST 恰好有一种解释同时满足完整的边界约束（换算或校验后其 bbox
  与点击点均落在当前截图分辨率范围内）与已有证据的一致性约束（如与同一响应中其他已声明坐标空间的
  候选、或已知目标区域证据不矛盾）；(b) 若两种解释都满足上述约束、都不满足、或已有证据本身相互
  冲突，则视为无法可靠推断，MUST 按拒绝处理。不满足条件 (a) 的情形 MUST 一律拒绝该候选，MUST NOT
  猜测后仍然点击。
- **FR-016**: 当全部候选均因坐标空间缺失、矛盾或换算后越界而被拒绝时，系统 MUST 停止当前直接执行
  路径并转入既有的失败分类与恢复/重新定位流程，MUST NOT 回退到猜测坐标。
- **FR-017**: 坐标空间协议的处理 MUST 在宽高不相等、且纵向尺寸超过 1000 像素（如 1024×1568）的画面
  上有明确定义的正确行为，确保 0–1000 归一化 Y 坐标不会被误当作原始像素 Y 坐标直接使用。

- **FR-037**: 所有可能由本 feature 新增结果（`dangerous_drift`、`ambiguous_fail_safe`、坐标空间拒绝）

  或证据相互冲突时，系统 MUST 将运行判定为环境前置条件失败、保存失败原因与证据并停止；MUST NOT
  发送任何业务或恢复动作，也 MUST NOT 自动清理或纠正现场。仅两项数值均可靠且完全一致时才可开始执行。

- **FR-034**: 更新后的 `pos-buy-bag-checkout.yaml` MUST 有对应的离线端到端回归测试，验证其能在固定

### Key Entities

- **稳定动作身份（Stable Action Identity）**：作用范围严格限定在单个测试步骤内的复合标识，由该
  测试步骤、`action_type`、（若同一步骤内连续迭代提供了相同且非空的）`action_id`、以及规范化核心
  业务目标共同组成；`action_type` 与非空 `action_id` 同时相同即为决定性强匹配证据，可覆盖 `intent`/`description`/
  `role`/`target.text` 等自由文本的改写差异；不同测试步骤之间不共享同一身份。
- **步骤意图一致性验证（Step Intent Consistency Check）**：当同一步骤内动作身份因 `action_id`
  缺失或变化而无法直接确认时，用于判断新提出的目标是否仍然符合该测试步骤已声明业务意图的验证过程；
  验证不通过或结果存在歧义时，MUST 按 fail-safe 规则处理，不得默认当作合法新目标放行。
- **规范化核心业务目标（Normalized Business Target）**：从 `SemanticAction.target` 中提取、对措辞与
  无关文本改写具有鲁棒性的目标标识，优先基于目标文字锚点 `target.text`（并容忍轻微 OCR 噪声）。
- **危险动作漂移判定（Dangerous Target Drift Classification）**：步骤意图一致性验证中的一种具体、
  高风险的不通过情形——判断同一测试步骤内，新目标是否从指向可交互控件漂移为指向非交互结果展示元素，
  或漂移为另一个不符合该步骤 intent 的可交互控件（即控件仍可交互，但已不是该步骤 intent 所指向的
  那一个）；判定为漂移时在执行前阻止直接点击。
- **坐标空间声明（Coordinate Space Declaration）**：Grounding 候选目标通过显式字段 `coordinate_space`
  声明的坐标空间类型（`pixel` / `normalized_1000`）；同一响应内的不同候选可各自独立声明不同类型，
  每个候选独立换算与校验。缺失、声明了未定义的取值、与数值范围矛盾、或（针对历史响应）两种解释都
  满足/都不满足边界与一致性约束、或证据本身冲突而无法可靠推断时，均视为无效声明。
- **转换后执行坐标（Resolved Execution Coordinates）**：坐标空间声明按当前实际截图分辨率换算得到的
  原始像素坐标，是执行点击前的最终校验对象；该换算对每个候选坐标有且仅发生一次；换算后的完整边界框
  四角与最终点击点均须落在当前截图分辨率范围内（`normalized_1000` 的 0 与 1000 本身视为合法边界）；
  缺失、矛盾或越界的声明均 MUST NOT 产生可用的转换后坐标。
- **可信业务验收用例（Trustworthy Business Acceptance Test Case）**：更新后的
  `pos-buy-bag-checkout.yaml`，以业务结果断言（购物车件数、金额、レジ袋文字、小計确认画面）取代仅靠
  `screen_changed` 的弱证据判定，止步于小計确认画面、不进入支付；其起始状态在真实验收运行中由人工
  确认，不由程序自动清理。
- **起始状态前置条件（Start State Precondition）**：真实 VNC 验收运行中，人工确认记录与程序首次独立
  观察结果的自动比较结果；只有件数和金额均可靠且完全一致时允许发送首个输入事件。
- **实际发送动作清单（Executed Action Log）**：仅包含执行结果证明键盘或鼠标事件已经发送的动作；
  被安全组件拦截的动作提案保留在逐轮审计中，但不属于该清单、不得增加分类执行次数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在"加入购物袋"步骤的离线回归测试与真实验收运行中，鼠标点击次数严格为 1 次。
- **SC-002**: 购物袋数量严格从 0 件变为 1 件、合计金额严格从 0 円变为 5 円，且该结果由业务结果断言
  （而非仅 `screen_changed`）确认。
- **SC-003**: "加入购物袋"步骤全程不产生任何额外的鼠标点击或键盘 Tab 按键（在离线回归测试与真实
  验收运行中均适用）。
- **SC-004**: "小計"步骤的点击次数严格为 1 次（在离线回归测试与真实验收运行中均适用）。
- **SC-005**: 整次测试运行中与支付相关的动作执行次数为 0（在离线回归测试与真实验收运行中均适用）。
- **SC-006**: 即使 Planner 在同一步骤的重试中对同一非幂等业务动作使用不同的措辞或目标描述，该动作
  被重复执行的次数仍为 0；"重复执行"的判定依据 FR-001～007 定义的稳定动作身份与 fail-safe 规则。
- **SC-007**: 在整屏变化比例低至约 0.4669% 的固定截图回归场景中，系统仍 100% 判定该动作效果为
  `expected_effect`。
- **SC-008**: 正式业务步骤的最终判定不会以弱断言（`weak_assertion_warning=True`）状态呈现为通过。
- **SC-009**: 本 feature 新增的全部场景均有对应的固定截图或 mock 驱动的离线回归测试覆盖，这些测试
  运行过程中发起真实 VNC 连接的次数为 0。
- **SC-010**: 本 feature 交付前既有的全部离线自动化测试，在应用本 feature 改动后重新运行时全部继续
  通过，不出现回归。
- **SC-011**: 真实 VNC 验收运行中，程序自动点击"クリア"或等效清空/重置操作的次数为 0；验收运行的
  起始状态均由人工确认记录后才开始。
- **SC-012**: 真实 VNC 验收运行产生的报告中，购物袋点击次数、小計点击次数、支付相关动作次数、
  "クリア"或等效清空操作次数均可直接从报告的分类统计字段（FR-036）读出；统计仅包含明确已发送的
  动作，被拦截的提案计数为 0 且仍可在逐轮审计记录中识别，无需复核原始日志或重新运行即可完成审计。
- **SC-013**: 在人工确认的起始状态与首次程序观察任一数值不一致、无法可靠提取或证据冲突的全部离线
  回归场景中，运行 100% 在首个键盘或鼠标事件发送前停止，实际发送动作次数为 0，报告明确标记
  `start_state_precondition_failed` 及对应证据；两项数值完全一致的场景 100% 通过该前置门禁。

## Assumptions

- 本 feature 建立在 002（自适应动作效果检测与可信业务验证）已交付的 `ActionEffect`、
  `StepVerificationResult`、`RepeatGuard`、`verification_mode` 等实体与流程之上，复用而不重新定义
  这些既有概念，只在"动作身份判定"与"Grounding 坐标空间处理"这两个由真实验收暴露出的薄弱环节上做
