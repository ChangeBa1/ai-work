# Feature Specification: 通用动作身份、目标一致性与坐标空间安全

**Feature Branch**: `003-action-identity-grounding`

**Created**: 2026-07-21

**Rebaselined**: 2026-07-22（依据 Constitution v1.1.0 Principle VI 重新基线为业务无关的框架能力；不新建
feature，不改变分支/目录）

**Status**: Draft

**Constitution Baseline**: v1.1.0 — Principle VI（业务无关核心与声明式场景隔离）

**Input**: 本 feature 是通用的、业务无关的、基于 GUI 的 AI 规范驱动测试框架在以下四个方面的能力加固：
①测试步骤范围内的稳定动作身份，用于非幂等动作的重复执行防护，但该身份匹配本身 MUST NOT 被当作新目标
安全的证明；②新目标与步骤已声明 intent 的一致性验证，以及由此驱动、而非由单一信号（如 `action_type`
变化）直接判定的危险目标漂移分类；③Grounder 显式 `coordinate_space` 声明与一次性坐标转换，缺失/矛盾/
未知/越界时 fail-safe 拒绝而非猜测；④声明式的运行前置条件（命名 facts/assertions）、声明式的已发送
动作审计（tags/matchers/counters）、通用恢复策略预算与人工确认门禁，以及通用 JSON/HTML 审计证据。
生产核心（domain、runtime、planning、grounding、execution、verification、reporting、recovery、config）
MUST NOT 包含任何被测应用、行业、页面或测试场景专用的字段、关键词、状态、操作类别、期望值或流程分支；
被测应用的具体业务语义只允许出现在测试用例 YAML、示例与离线回归 fixture、或通过通用接口注册的可选
场景 profile 中。触发本次重新基线的历史事故背景见下文 Background（非规范性）。

## Background（非规范性，历史动机）

002（自适应动作效果检测与可信业务验证）已实现并离线测试通过，但在一次真实环境验收运行中，一个 POS
风格的购物场景（点击"加入购物袋"按钮结算用例，对应离线回归 fixture
`vnc_agent/testcases/pos-buy-bag-checkout.yaml`）暴露出两类通用框架缺陷，而非该场景独有的问题：

1. Planner 在同一测试步骤的重试中对同一非幂等业务动作改写了 intent/target 描述措辞，暴露出"稳定动作
   身份判定过度依赖自由文本完全相等"这一通用缺陷；其中一轮把目标描述从一个可交互按钮改写成了一个非
   交互的结果展示元素，这类改写若被直接执行点击，属于危险目标漂移，且不应仅因为改写前后 `action_id`
   相同或前一轮效果为 `no_effect` 就被视为安全。
2. Grounder 返回的候选坐标缺乏显式坐标空间协议（原始像素 vs 归一化坐标），在宽高比悬殊的非正方形
   分辨率下容易被误用，暴露出"坐标空间缺乏显式声明与安全 fail-safe"这一通用缺陷。

这次事故也促使团队意识到：验收前置条件（起始状态是否符合预期）与已发送动作的审计统计，此前都是围绕
该具体业务场景手工搭建的，不具备可复用性；这正是本 feature 将其重新设计为通用声明式机制（命名
facts/assertions、tags/matchers/counters）的直接动机。该场景对应的离线回归 fixture 继续保留在
`vnc_agent/testcases/` 与测试套件中，作为本 feature 众多回归验证场景之一，但 MUST NOT 是唯一验收依据，
也 MUST NOT 定义任何公共实体或公共配置字段。

## Clarifications

### Session 2026-07-21

- Q: 稳定动作身份判定的作用范围应该是什么？跨测试步骤出现相同 `action_id` 是否也应被视为同一动作身份
  的延续？ → A: 动作身份的判定范围 MUST 限定在当前测试步骤（TestStep）内；不同测试步骤之间，即便
  `action_id` 数值相同，也 MUST NOT 被视为同一稳定动作身份的延续。
- Q: 在同一测试步骤内，当 `action_type` 与 `action_id` 相同，但 `intent`/`target.role`/`target.text`/
  `description` 等自由文本字段被同义改写时，是否足以构成"同一逻辑动作尝试"的判定依据？ → A: 是，仅
  限于此判定目的（用于非幂等重复执行防护）。同一测试步骤内相同 `action_type` 与相同且非空 `action_id`
  的组合构成"同一逻辑动作尝试"的强匹配证据，即使自由文本表述发生同义改写或差异。但该强匹配 MUST NOT
  被当作新目标本身安全的证明——见本 Session 及 2026-07-22 Session 中关于目标安全冲突检查的补充决定。
- Q: 当同一测试步骤内连续迭代未提供相同的 `action_id`（缺失、为空或确实变化）时，系统的默认行为应该
  是什么？ → A: 采用保守的 fail-safe 默认行为：当动作身份或"新目标是否符合步骤 intent"的验证结果存在
  歧义，且前一次同一逻辑非幂等动作尚未被可靠判定为 `no_effect` 时，系统 MUST 禁止再次执行，转入重新
  观察与加强验证，而不是默认放行执行。
- Q: 当 Planner 在同一测试步骤重试时改变了目标对象，系统应如何判断这是否是一次合法的新目标？ → A:
  MUST NOT 自动视为真正不同的动作；系统 MUST 先验证新目标是否仍然符合该测试步骤已声明的 `intent`，
  只有验证通过才 MAY 将其视为该步骤内的合法新目标并允许执行；验证不通过或存在歧义时按上一条 fail-safe
  规则处理。
- Q: Grounder 响应中坐标空间应该通过什么规范化字段声明，转换应该在管线中发生几次？ → A: Grounder 返回
  的每个候选目标 MUST 通过显式字段 `coordinate_space` 声明坐标空间，取值至少包含 `pixel`（原始像素
  坐标）与 `normalized_1000`（0–1000 归一化坐标，X/Y 两轴分别独立相对图像宽度/高度归一化）；从声明的
  坐标空间换算为原始像素坐标的转换 MUST 有且仅发生一次，MUST NOT 重复换算，也 MUST NOT 在多个处理
  环节各自独立换算导致结果不一致。
- Q: 对于不包含 `coordinate_space` 字段的历史 Grounder 响应，系统应如何处理？ → A: 默认仍需拒绝并
  停止，但允许一种受限例外：当且仅当系统能够仅依据当前截图分辨率与已有证据可靠、无歧义地推断出其坐标
  空间时，MAY 使用推断结果继续执行；只要推断存在任何不确定性，MUST 拒绝该候选并停止，MUST NOT 猜测后
  仍然点击。

### Session 2026-07-22（Constitution v1.1.0 重新基线：两个安全问题修正）

- Q（安全问题 A）：当同一测试步骤内连续迭代提供了相同且非空的 `action_id` 时，这一匹配是否足以证明
  新一轮的目标本身对当前证据而言是安全的，可以直接执行？ → A: 不足以。相同 `action_id`（叠加相同
  `action_type`）MUST 仅被视为"同一逻辑动作尝试"的强匹配证据，用于非幂等重复执行防护判定，MUST NOT
  被当作新目标安全性的证明。当新一轮目标的角色（role）、交互性质（可交互 vs 非交互）或空间证据与
  前一轮目标发生实质冲突时，无论 `action_id` 是否相同，系统 MUST 仍然运行步骤 intent 一致性/危险目标
  漂移检查（见 FR-003、FR-004）；前一轮该动作的 `ActionEffect` 已被判定为 `no_effect`，同样 MUST NOT
  免除这一检查——`no_effect` 只影响"是否允许重新执行同一未变目标"，不影响"变化后的新目标是否安全"。
- Q（安全问题 B）：`action_type` 在同一测试步骤内的迭代之间发生变化，是否应被无条件视为危险目标漂移
  （`dangerous_drift`）？ → A: 不应。`action_type` 变化 MUST 仅被视为触发步骤 intent 一致性检查的
  风险信号，MUST NOT 被无条件等同于 `dangerous_drift` 判定结果。是否允许执行，MUST 由三者共同决定：
  新目标声明的交互目的（如关闭遮挡元素、滚动使目标可见、重新聚焦、等待、重新观察等合法的步骤内前置
  微动作）、该目标声明的动作风险级别、以及步骤 intent 一致性检查的结果；仅当声明目的不构成合法微动作、
  或一致性检查不通过时，才 MUST 判定为 `dangerous_drift`。
- Q: FR-024～026 声明的"运行前置条件 named facts"与既有的"业务结果断言"（`verification_mode`）机制
  之间是什么关系？是两套独立的声明语法，还是同一机制在不同时机的应用？ → A: 二者 MUST 是同一底层
  fact/assertion 声明机制（命名 key + 期望值/matcher）在两个不同触发时机上的应用，共享同一声明语法与
  校验器实现，不是两套独立的接口：运行前置条件在发送首个输入事件之前触发一次性比较；业务结果断言
  （复用既有 `verification_mode`）在每个测试步骤执行后触发比较。本 feature 不新增第二套并行的断言
  语法。
- Q: FR-013 要求 `dangerous_drift` 分类由"声明目的"、"声明风险级别"、"一致性检查结果"三者共同
  决定；这三者应如何组合成最终判定？ → A: 采用 AND 语义，且风险级别路由到既有恢复策略契约，而不是
  新增独立的风险裁决逻辑：仅当（1）新目标声明的交互目的属于 FR-006 定义的合法步骤内微动作类别、
  （2）该目的通过步骤 intent 一致性检查、且（3）该目标声明的动作风险级别不高于该类合法微动作被
  允许直接执行所要求的阈值时，MAY 直接执行；以上任一条件不满足，MUST 判定为 `dangerous_drift` 或
  按 FR-034 规定的恢复策略契约路由（例如风险级别触发"是否需要人工确认"字段为真的恢复策略），MUST NOT
  新增脱离 FR-034 六字段契约之外的独立风险裁决通道。
- Q: 规范中多处提到"场景 profile"作为与测试用例并列的业务语义声明位置，但未定义其注册机制或是否为
  必需组件；本 feature 范围内，场景 profile 应如何定位？ → A: 场景 profile MUST 是完全可选的声明
  容器，等同于把本 feature 声明的 facts/tags/matchers 打包成可在多个测试用例间复用的配置；核心框架
  MUST 在零 profile 注册的情况下完整工作——仅靠测试用例内联声明前置条件与动作 tag 即可满足全部
  FR-024～028 要求。本 feature MUST NOT 新增独立的 profile 注册接口/公共 API；"通过通用接口注册的
  可选场景 profile"这一 Constitution 表述在本 feature 范围内即指"测试用例可选择将声明内容抽取为
  可复用配置文件"，不是一个新的强制组件。

### User Story 1 - 稳定动作身份用于非幂等重复执行防护，但不证明目标安全 (Priority: P1)

作为测试工程师，我希望当 Planner 在同一测试步骤的重试中用不同措辞重新描述同一个非幂等动作时，系统仍能
把它识别为同一逻辑动作尝试的重复，而不是一个全新的、可以自由执行的不同动作；同时我也希望这一身份匹配
本身绝不会被当作"新一轮目标本身安全"的证明——只要新一轮目标的角色、交互性质或空间证据与前一轮发生
实质冲突，系统仍必须运行目标一致性检查，即使 `action_id` 相同、即使前一轮效果是 `no_effect`。

**Why this priority**: 这是本次真实事故的直接根因——重复执行防护此前依赖自由文本完全相等判断"是否为
同一动作"，导致改写措辞后被误判为不同动作而重复执行；同时事故中"目标从按钮改写为结果展示元素"这一
最危险的一步，恰恰发生在 `action_id` 保持相同的情况下——如果把身份匹配误当作目标安全的证明，这类危险
漂移就会被直接放行。

**Independent Test**: 使用固定的语义动作序列（同一测试步骤内、`action_id` 相同但 `intent`/
`target.description` 逐轮改写，以及一组 `action_id` 相同但目标角色/交互性质/空间证据发生冲突的构造
序列），可独立验证稳定动作身份判定、重复执行防护与目标安全隔离，无需连接真实环境。

**Acceptance Scenarios**:

1. **Given** 同一测试步骤内连续两轮迭代，`action_type` 相同、`action_id` 相同且非空，**When** 系统
   计算两轮动作的稳定动作身份，**Then** 系统判定二者为同一逻辑动作尝试——即使 `intent`、
   `target.role`、`target.text` 或 `target.description` 的自由文本表述不完全一致。
2. **Given** 上述场景中第一轮动作已产生某种 `ActionEffect` 但业务结果仍 `uncertain`，**When** 系统据此
   判断第二轮是否可以执行，**Then** 系统拦截第二轮的直接执行，转入加强验证，而不是将其归类为
   "不同动作"并放行。
3. **Given** 目标文字锚点因识别噪声在相邻迭代间出现个别字符缺失或多出，但其余上下文（附近文字、目标
   区域、`action_id`）表明仍是同一目标，**When** 系统计算规范化业务目标，**Then** 系统仍将其识别为
   同一目标，而不是因逐字符不完全相等就判定为不同目标。
4. **Given** 一次真正不同的语义动作（`action_type` 不同、或明确指向另一个已声明的不同目的），
   **When** 系统计算稳定动作身份，**Then** 系统判定为不同身份，不得错误合并两个真正不同的动作。
5. **Given** 两个不同测试步骤中恰好出现数值相同的 `action_id`，**When** 系统计算稳定动作身份，
   **Then** 系统不会将其视为同一动作身份的延续——测试步骤边界具有强制力。
6. **Given** 同一测试步骤内连续迭代未提供相同的 `action_id`，**When** 系统评估新目标能否被视为一次
   合法新动作，**Then** 系统 MUST NOT 默认放行执行，而是先验证新目标是否仍符合该步骤已声明的 intent。
7. **Given** 上述验证结果存在歧义，且前一次同一逻辑非幂等动作尚未被可靠判定为 `no_effect`，
   **When** 系统决定下一步操作，**Then** 系统采用 fail-safe：禁止再次执行，转入重新观察与加强验证。
8. **Given** 同一测试步骤内，新目标具有独立于此前非幂等动作的交互目的（如先关闭遮挡该目标的弹窗、先
   滚动使目标可见），且经步骤 intent 一致性验证判断为符合该步骤 intent，**When** 系统评估该新目标，
   **Then** 系统允许将其视为合法的步骤内前置微动作并执行；但该微动作 MUST NOT 被用作重新执行同一个
   已产生效果、业务结果尚未确定的主要非幂等动作的手段。
9. **Given** 同一测试步骤内连续两轮迭代 `action_type` 与 `action_id` 均相同（满足强匹配），但新一轮
   目标的角色从"可交互控件"变为"非交互结果展示元素"，或目标的空间证据（区域、锚点位置）与前一轮
   发生实质冲突，**When** 系统评估是否可以直接执行新一轮动作，**Then** 系统 MUST NOT 因 `action_id`
   匹配就直接放行，而是必须运行步骤 intent 一致性/危险目标漂移检查，其结果决定是否允许执行。
10. **Given** 场景 9 中前一轮该动作的 `ActionEffect` 已被可靠判定为 `no_effect`，**When** 系统评估
    新一轮目标，**Then** `no_effect` 仅影响"是否允许重新执行同一未变目标"，MUST NOT 被当作免除场景 9
    所要求的一致性/漂移检查的理由——检查仍必须运行。

### User Story 2 - 危险目标漂移由风险信号与声明目的共同判定，而非单一信号直接等价 (Priority: P1)

作为测试工程师，我希望当新目标的类别或描述发生变化时（例如 `action_type` 改变），系统把这仅仅当作
一个需要进一步核实的风险信号，而不是直接等价于"危险漂移"；系统应结合新目标声明的交互目的、其声明的
动作风险级别、以及步骤 intent 一致性检查结果，共同决定是放行合法的步骤内微动作（如关闭弹窗、滚动、
重新聚焦、等待、重新观察），还是判定为危险目标漂移并阻止直接执行。

**Why this priority**: 这是本次真实事故中最危险的一步——目标从可交互控件被改写为非交互的结果展示
元素，系统随后直接执行了点击。但同时，如果矫枉过正把任何 `action_type` 变化都当作危险漂移，会误伤
合法的步骤内微动作（关闭遮挡弹窗、滚动到可见区域等），导致测试无法正常推进。必须两者兼顾。

**Independent Test**: 使用一组固定的目标描述变化序列（真正危险的"控件→展示元素"漂移、"控件→另一
不相关控件"漂移、以及合法的"关闭弹窗后操作原目标""滚动后操作原目标"微动作），可独立验证危险目标
漂移判定既能拦截真正的漂移，又不会误杀合法微动作，无需真实触发任何鼠标动作。

**Acceptance Scenarios**:

1. **Given** 同一测试步骤内，新目标从指向一个可交互控件变为指向一个非交互的结果展示元素，且该变化
   不构成任何已声明的合法步骤内微动作、也未通过步骤 intent 一致性验证，**When** 系统评估该目标，
   **Then** 系统判定为危险目标漂移，不直接执行点击。
2. **Given** 判定为危险目标漂移，**When** 系统决定下一步，**Then** 系统停止当前直接执行路径，转入
   既有的失败分类与恢复/重新定位流程，而不是猜测这是否安全后仍然执行。
3. **Given** 危险目标漂移的判定，**When** 系统评估该轮的动作效果，**Then** 该判定 MUST 在动作被发送
   执行之前就已生效，不依赖执行后的效果结果来回溯认定。
4. **Given** 一次目标描述的变化仍然指向同一类可交互控件（角色、位置、锚点文字一致或高度吻合），
   **When** 系统评估是否为危险漂移，**Then** 系统不得将这类正常的措辞变化误判为危险漂移。
5. **Given** 新目标仍然指向一个可交互控件，但该控件已不再是该步骤 intent 所指向的那一个（例如漂移
   为另一个不相关的可交互控件），**When** 系统评估该目标，**Then** 系统同样判定为危险目标漂移——
   危险漂移的判定不局限于"控件→非交互元素"这一种方向。
6. **Given** 同一测试步骤内，新目标的 `action_type` 相较上一轮发生变化，但该新目标声明了一个独立的
   合法交互目的（如"关闭遮挡当前目标的弹窗"或"滚动使当前目标可见"），其声明的动作风险级别不高于该
   微动作类别被允许直接执行所要求的阈值，并通过了步骤 intent 一致性验证——即 FR-013 的 (a)(b)(c)
   三个条件同时满足，**When** 系统评估是否为危险漂移，**Then** 系统 MUST NOT 仅因 `action_type`
   发生变化就判定为危险漂移，而是允许将其视为合法的步骤内微动作并执行。
7. **Given** 同一测试步骤内，新目标的 `action_type` 发生变化，且 FR-013 的 (a)(b)(c) 条件中任一项
   不满足（未声明可识别为合法微动作的交互目的、或未通过步骤 intent 一致性验证、或声明的动作风险
   级别超出该微动作类别允许直接执行的阈值），**When** 系统评估该目标，**Then** 系统判定为危险目标
   漂移，并按 FR-034 的恢复策略契约路由（若该风险级别对应的策略声明需要人工确认，则进入人工确认
   而非直接执行或直接放弃）——`action_type` 变化本身仅是促使系统运行该验证的风险信号，不是判定
   依据本身。

### User Story 3 - Grounder 坐标必须遵循显式坐标空间协议，缺失或矛盾时停止而非猜测 (Priority: P1)

作为测试工程师，我希望 Grounder 返回的每个候选坐标都通过显式字段 `coordinate_space` 声明其坐标空间
（`pixel` 或 `normalized_1000`），系统在执行点击前把它换算为当前截图的原始像素坐标且只换算一次；当
坐标空间缺失、自相矛盾、取值未知或换算后越界时，系统应停止并重新定位，而不是把归一化坐标当作像素
坐标直接使用。

**Why this priority**: 这很可能是本次真实事故中点击落在错误屏幕位置的根因——被测环境为宽高比悬殊的
非正方形分辨率（例如纵向尺寸远超 1000 的画面），如果模型返回的是 0–1000 归一化坐标而系统当作原始
像素坐标直接使用，就会产生大幅偏移，且该偏移不一定会被越界校验捕获。

**Independent Test**: 使用固定的候选坐标数据（分别声明 `coordinate_space` 为 `pixel` 与
`normalized_1000`）配合至少一个非正方形、纵向尺寸超过 1000 的画面尺寸（如 1024×1568，仅作示例），
可独立验证坐标空间换算逻辑能否得到正确的原始像素坐标，无需连接真实环境或真实调用 Grounder 模型。

**Acceptance Scenarios**:

1. **Given** 一个候选目标显式声明 `coordinate_space: normalized_1000`，画面实际分辨率为非正方形且
   纵向尺寸超过 1000（例如 1024×1568），**When** 系统在执行前换算该候选坐标，**Then** 系统按 X 轴
   相对宽度、Y 轴相对高度分别换算，得到落在画面分辨率范围内的正确原始像素坐标，而不是把归一化数值
   直接当作像素坐标使用；该次换算 MUST 有且仅发生一次。
2. **Given** 一个候选目标显式声明 `coordinate_space: pixel`，**When** 系统在执行前处理该候选，
   **Then** 系统不对其做归一化换算，直接使用（并仍需校验其落在当前截图分辨率范围内）。
3. **Given** 一个候选目标未声明 `coordinate_space`、声明了未知取值、或声明的坐标空间与其数值范围
   明显矛盾，且对不含 `coordinate_space` 字段的历史响应，系统无法找到恰好一种解释同时满足完整边界
   约束与已有证据一致性约束，**When** 系统处理该候选，**Then** 系统拒绝该候选，不猜测其含义后仍然
   执行点击。
4. **Given** 全部候选均因坐标空间缺失、矛盾、未知取值或换算后越界而被拒绝，**When** 系统评估下一步，
   **Then** 系统停止当前直接执行路径并转入既有的失败分类与恢复/重新定位流程。
5. **Given** 同一次 Grounding 响应中不同候选分别声明了不同的 `coordinate_space`，**When** 系统处理
   这些候选，**Then** 系统对每个候选分别按其自身声明独立换算与校验，不对整个响应套用单一坐标空间
   假设。

### User Story 4 - 声明式运行前置条件（named facts/assertions） (Priority: P2)

作为测试工程师，我希望能在测试用例或场景 profile 中以通用的命名 fact/assertion（key + 期望值或
matcher）声明运行前置条件，而不是依赖框架核心为某个具体业务预置固定字段；系统在发送第一个输入事件
之前，将声明的前置条件与独立观察到的证据自动比较，任一不一致、证据不可读或相互冲突时，系统停止运行
并报告前置条件失败，而不是自动执行重置/清理类动作来凑齐前置条件。

**Why this priority**: 此前用于验收的起始状态确认是围绕某一具体业务场景手工搭建的，不具备通用性；
这类前置条件检查与"是否允许框架自行清理/重置环境"这两个问题在任何被测应用上都会出现，必须提供业务
无关的通用机制。

**Independent Test**: 使用一组声明了通用命名前置条件（如某计数字段的期望值、某状态标记的期望值）
与匹配/不匹配的固定证据快照的离线场景，可独立验证前置条件比较逻辑与"不匹配即零输入停止"的行为，
无需连接真实环境。

**Acceptance Scenarios**:

1. **Given** 测试用例声明了一组命名前置条件（key + 期望值/matcher），**When** 系统在发送任何输入
   事件之前独立观察证据，**Then** 系统将观察到的证据与声明的前置条件逐项比较，仅当全部项一致时才
   允许继续执行。
2. **Given** 任一声明的前置条件与观察证据不一致、证据无法可靠提取、或证据本身相互冲突，**When**
   系统评估是否可以开始执行，**Then** 系统 MUST 停止运行、保存失败原因与证据，且 MUST NOT 发送任何
   业务或恢复动作。
3. **Given** 前置条件要求的初始状态尚未达成，**When** 系统评估如何达成该状态，**Then** 系统 MUST NOT
   自动执行状态变更类的重置/清理动作来凑齐前置条件；该初始状态 MUST 通过外部/人工确认或独立配置
   提供的证据来满足。
4. **Given** 全部声明的前置条件均与观察证据一致，**When** 系统评估是否可以开始执行，**Then** 系统
   允许运行继续，不产生任何框架自发起的重置类动作。

### User Story 5 - 声明式已发送动作审计（tags/matchers/counters） (Priority: P2)

作为测试工程师，我希望测试用例或场景 profile 能以通用的 tag/matcher 声明需要审计的动作类别，而不是
让框架核心为某个具体业务硬编码固定的动作分类；报告应仅统计执行结果证明键鼠事件确实已发送的动作，
按声明的 tag 分类计数，被安全组件拦截、未真正发送的动作提案不计入发送次数，但仍需在逐轮审计记录中
保留其"被拦截"状态。

**Why this priority**: 此前的动作分类审计（如按具体业务动作类别统计次数）是围绕某一具体场景硬编码的，
不能复用到其他被测应用；必须提供业务无关的声明式审计机制，同时保持"拦截动作不计入发送次数"这一安全
不变量。

**Independent Test**: 使用一组声明了通用 tag 的动作序列（部分动作真实发送、部分被安全组件拦截），
可独立验证按 tag 分类的发送次数统计与拦截记录的正确性，无需连接真实环境。

**Acceptance Scenarios**:

1. **Given** 测试用例或场景 profile 为若干动作声明了通用 tag（基于 `action_type`/目标/intent 的
   matcher），**When** 系统生成报告，**Then** 报告按声明的 tag 对"确实已发送"的动作分类计数。
2. **Given** 一个动作提案被 RepeatGuard、一致性检查或坐标空间拒绝拦截、未产生真正的键鼠发送，
   **When** 系统统计按 tag 的发送次数，**Then** 该提案 MUST NOT 计入任何 tag 的发送次数，但 MUST 在
   逐轮审计记录中保留为"被拦截"状态，可供复核。
3. **Given** 核心框架代码，**When** 检查其是否包含任何具体业务的固定动作分类字段或默认 tag，
   **Then** 核心代码中不存在此类固定分类，所有分类均来自测试用例/场景 profile 的声明。

### User Story 6 - 恢复策略预算与人工确认门禁，不执行未声明的状态变更动作 (Priority: P2)

作为测试工程师，我希望即使系统在应对身份判定歧义、危险目标漂移或坐标空间问题时进入恢复流程，也不会
通过发送无依据的默认按键导航、执行额外点击，或执行任何不在该测试步骤已声明动作范围内的状态变更动作
来"恢复"，因为这些手段本身就可能造成新的、更难排查的状态破坏；每条可能触达的恢复策略都必须显式声明
预算与门禁字段，缺失时视为配置错误而拒绝生效。

**Why this priority**: 本次真实事故已经证明"任由系统在识别失败时自由决定下一步"会导致额外的、破坏
性的操作；本 feature 在收紧动作身份与坐标判定的同时，必须明确恢复路径本身也不能引入新的破坏性操作，
且这一约束必须以业务无关的通用方式表达（"任何不在已声明动作范围内的状态变更动作"，而不是某个具体
业务操作的名称）。

**Independent Test**: 使用一组模拟"动作身份判定不确定""危险漂移""坐标空间被拒绝"等场景，可独立验证
系统触发的恢复策略集合中不包含无依据的默认按键导航、额外点击或任何未声明的状态变更动作，无需真实
执行任何键鼠动作。

**Acceptance Scenarios**:

1. **Given** 危险目标漂移或坐标空间被拒绝触发了恢复流程，**When** 系统选择恢复策略，**Then** 系统
   MUST NOT 发送无依据的默认按键导航作为鼠标点击的替代。
2. **Given** 同样的恢复场景，**When** 系统选择恢复策略，**Then** 系统 MUST NOT 执行任何不在该测试
   步骤已声明动作范围内、会改变被测应用状态的操作。
3. **Given** 恢复策略耗尽该测试步骤的共享重试预算仍未解决问题，**When** 系统评估该步骤，**Then**
   系统将该步骤判定为失败并停止，而不是尝试用未声明的操作强行让步骤"看起来通过"。
4. **Given** 危险目标漂移、动作身份歧义或坐标空间拒绝进入恢复框架，**When** 系统解析对应恢复策略，
   **Then** 该策略显式声明最大次数、冷却时间、是否消耗全局重试额度、是否允许改变动作路径、是否需要
   强模型、是否需要人工确认；任一声明缺失时系统按配置错误 fail closed，MUST NOT 使用隐式默认值继续
   恢复。

### User Story 7 - 报告可审计动作身份、漂移判定、坐标换算与前置条件评估 (Priority: P2)

作为测试工程师，我希望测试报告中能看到每一轮迭代计算出的稳定动作身份、目标一致性/危险漂移判定理由、
Grounding 候选声明的坐标空间与换算前后坐标、前置条件评估记录，以及按声明 tag 分类的动作发送次数
统计，这样复核问题时无需重新运行即可定位根因。

**Why this priority**: 这是让 User Story 1～6 的判定逻辑本身可验证、可审计的必要配套——没有这些字段，
即便判定逻辑正确，复核人员也无法从报告中直接看出判定依据。

**Independent Test**: 检查一次已完成的离线测试运行所产生的 JSON/HTML 报告，可独立验证其是否包含
稳定动作身份、一致性/漂移判定理由、坐标空间声明与换算前后坐标、前置条件评估记录、按 tag 分类的动作
计数这些字段，无需重新运行测试。

**Acceptance Scenarios**:

1. **Given** 任意一轮已执行的动作迭代，**When** 查看其报告记录，**Then** 报告中包含该轮计算得到的
   稳定动作身份摘要（含所属测试步骤与是否命中 `action_id` 强匹配）以及一致性/漂移判定结果与理由。
2. **Given** 一轮涉及 Grounding 的动作迭代，**When** 查看其报告记录，**Then** 报告中包含候选声明的
   `coordinate_space`、换算前的原始候选坐标、以及换算后用于实际执行的原始像素坐标。
3. **Given** 一次运行声明了前置条件，**When** 查看其报告记录，**Then** 报告中包含声明的前置条件、
   观察到的证据、以及比较结果。
4. **Given** 一次运行声明了动作 tag，**When** 查看其报告记录，**Then** 报告中包含按 tag 分类的
   已发送动作计数，以及被拦截提案的逐轮审计记录。

### User Story 8 - 离线优先验证，覆盖至少三个互不相关场景，POS 事故仅作附加回归 (Priority: P3)

作为测试工程师，我希望本 feature 的全部通用机制都通过至少三个互不相关的离线场景验证（而不仅仅是
触发本次重新基线的那一个 POS 场景），以证明实现是真正业务无关的框架能力，而不是只适配了单一测试
用例；POS 购物袋事故可以继续作为其中一个附加的离线回归 fixture，但绝不能是唯一验收依据。真实/在线
环境上的验证仍只作为独立于常规自动化测试之外、需要人工批准的环节。

**Why this priority**: 这是保证本次修复本身通用、可信、可长期防止回归的收尾环节，依赖前述故事已经
实现，因此优先级最低，但对"任何声称通用的框架能力变更都必须用至少两个互不相关场景验证"这一 Constitution
要求是必要的。

**Independent Test**: 直接运行覆盖以下场景的离线回归测试集，可独立验证本 feature 的判定结果在互不
相关的场景间保持一致：

1. **表单填写并提交**：一个通用表单场景，Planner 在同一"提交"步骤的重试中改写措辞后仍需被识别为
   同一非幂等提交动作，提交动作 MUST NOT 被重复执行。
2. **无文字图标打开菜单**：一个仅通过图标（无文字标签）触发的菜单打开场景，用于验证视觉目标身份识别
   与坐标空间协议在缺乏文字锚点时依然正确（尤其在非正方形分辨率下）。
3. **弹窗关闭或滚动后再操作目标**：一个目标先被弹窗遮挡、需要先关闭弹窗或滚动才能操作的场景，用于
   验证合法的步骤内微动作不会被误判为危险目标漂移。
4. **POS 购物袋结算（附加回归 fixture）**：既有的 `vnc_agent/testcases/pos-buy-bag-checkout.yaml`
   离线回归 fixture，作为第四个补充场景验证，不作为前三个通用场景之外的唯一或首要验收依据。

**Acceptance Scenarios**:

1. **Given** 本 feature 交付前既有的全部离线自动化测试，**When** 应用本 feature 的改动后重新运行，
   **Then** 全部既有测试继续通过，不出现回归。
2. **Given** 上述三个互不相关的离线场景（表单提交、图标菜单、弹窗/滚动微动作），**When** 分别运行
   对应的离线回归测试，**Then** 三个场景各自独立证明本 feature 的稳定动作身份、危险漂移判定、坐标
   空间协议均按声明的通用规则工作，不依赖任何场景专属的核心代码分支。
3. **Given** POS 购物袋结算离线回归 fixture，**When** 运行该场景，**Then** 该场景使用与前三个通用
   场景完全相同的核心机制通过，且其通过或失败 MUST NOT 是本 feature 声称的任何通用能力的唯一验收
   依据。
4. **Given** 需要在真实/在线环境上验证本次修复，**When** 团队安排该验证，**Then** 该验证作为独立于
   常规自动化测试运行之外的环节，仅在获得最终人工批准后执行一次，而不是被纳入常规测试流水线自动
   触发。

### Edge Cases

- 目标文字锚点因识别噪声在相邻迭代间出现个别字符缺失或多出时，规范化业务目标匹配应如何在"容忍轻微
  噪声"与"避免把两个真正不同的目标错误合并"之间取舍？
- 页面因上一次动作成功而发生布局变化（如新增内容导致后续控件的屏幕坐标整体偏移）时，系统应如何区分
  "同一控件因布局变化而换了位置"与"目标已经漂移到了另一个元素"？
- 同一测试步骤内，Planner 合理地插入了必要的前置微动作（使用了不同的 `action_id` 和目标）时，系统
  应如何将这种"步骤内合法的新子目标"与"对同一非幂等动作的危险身份漂移"区分开？（区分依据是：合法的
  前置微动作通常声明独立的交互目的，且通过步骤 intent 一致性验证；仅当新目标被判定为原地"替代"了
  同一个尚未确认业务结果的非幂等动作时，才适用本 feature 的 fail-safe 与危险漂移规则。）
- 同一测试步骤内 `action_id` 相同、但目标的角色/交互性质/空间证据发生冲突时，若这一验证被跳过会
  产生什么后果？（不得跳过——见 US1/AC9-10 与 FR-003/004；`action_id` 匹配与前一轮 `no_effect` 都
  不能替代该检查。）
- `action_type` 变化但新目标声明了合法交互目的、通过一致性验证的情形，是否应被直接判定为漂移？
  （不应——见 US2/AC6 与 FR-012/013；`action_type` 变化仅是风险信号，不是判定结果本身。）
- Grounding 候选完全未声明 `coordinate_space`、且其数值本身在两种可能空间下都不越界、当前截图分辨率
  与已有证据也不足以可靠推断时，应如何处理？（拒绝该候选并停止，不得任选一种空间强行使用。）
- 声明的运行前置条件与程序独立观察到的证据不一致、或证据本身相互冲突时，系统应如何处理？（视为环境
  前置条件不满足，停止并报告，不发送任何输入事件，也不自行尝试清理或纠正现场后继续运行。）
- 危险目标漂移判定触发、且该测试步骤的重试预算耗尽仍未能重新定位到正确目标时，该步骤最终应如何
  收尾？（按既有的预算耗尽规则判定该步骤失败，不为漂移场景单独开辟额外的重试通道。）
- 旧格式测试用例（不声明前置条件/tag/业务断言）与本 feature 声明式机制并存于同一次运行或同一份
  报告中时，两类判定结果的呈现如何保持互不误导？

## Requirements *(mandatory)*

### Functional Requirements

**稳定动作身份（测试步骤范围）**

- **FR-001**: 动作身份的判定范围 MUST 限定在当前测试步骤内；不同测试步骤之间，即便语义动作的
  `action_id` 数值相同，也 MUST NOT 被视为同一稳定动作身份的延续。
- **FR-002**: 在同一测试步骤内，当连续迭代的语义动作具有相同的 `action_type` 并提供了相同且非空的
  `action_id` 时，该组合构成"同一逻辑动作尝试"的强匹配证据，用于非幂等重复执行防护判定，即使
  `intent`、`target.role`、`target.text` 或 `target.description` 在这些迭代之间发生了同义改写。
  该强匹配 MUST NOT 被当作新一轮目标本身安全的证明（见 FR-003）。相同 `action_id` 但不同
  `action_type` 的动作不满足本条强匹配条件。
- **FR-003**（安全问题 A）: 无论 FR-002 定义的强匹配是否成立，当新一轮目标的角色（role）、交互性质
  （可交互 vs 非交互）或空间证据与前一轮目标发生实质冲突时，系统 MUST 仍然运行 FR-006 定义的步骤
  intent 一致性检查，才能决定是否允许执行该新一轮目标；`action_id` 相同 MUST NOT 被单独当作跳过
  该检查的理由。
- **FR-004**（安全问题 A）: 前一轮同一逻辑非幂等动作的 `ActionEffect` 已被可靠判定为 `no_effect`，
  MUST NOT 被当作免除 FR-003 所要求检查的理由；`no_effect` 仅影响"是否允许按 FR-010 重新执行同一
  未变目标"，不影响"变化后的新目标是否安全"这一独立判断。
- **FR-005**: 当同一测试步骤内的连续迭代未提供相同的 `action_id`（缺失、为空或确实变化）时，系统
  MUST NOT 仅因此默认视为一次真正不同的动作；MUST 先运行 FR-006 定义的步骤 intent 一致性检查，
  只有验证通过才 MAY 将其视为该步骤内的合法新目标并允许执行。
- **FR-006**: 步骤 intent 一致性检查 MUST 判断新提出的目标是否仍然符合该测试步骤已声明的 intent；
  当新目标被判断为具有独立于此前动作的交互目的、且不构成对同一非幂等动作的延续的合法步骤内微动作
  （例如关闭遮挡目标的弹窗、滚动使目标可见、重新聚焦、等待、重新观察）时，验证 MAY 通过；此类微动作
  本身 MUST NOT 被用于重新执行同一个已经产生效果、业务结果尚未确定的主要非幂等动作。
- **FR-007**: 当系统无法可靠证明同一测试步骤内新提出的动作与前一次非幂等动作确实不同时（包括
  `action_id` 缺失/变化、FR-003 触发的冲突检查结果存在歧义、或 FR-006 的一致性验证结果存在歧义），
  系统 MUST 保守地将新动作视为可能与前一次为同一逻辑非幂等动作；若前一次该动作对应的业务结果尚未
  确定，且其 `ActionEffect` 尚未被可靠判定为 `no_effect`，系统 MUST 禁止执行该新动作，转入重新观察
  与加强验证，MUST NOT 默认放行执行。本条 fail-safe 规则 MUST 仅约束非幂等动作。
- **FR-008**: 当目标文字锚点在相邻迭代间因识别噪声出现个别字符缺失或多出，但其余上下文（附近文字、
  目标区域、`action_id`）表明仍指向同一目标时，系统 SHOULD 仍将其识别为同一目标，而不要求逐字符
  完全相等；本条使用 SHOULD 而非 MUST，因为噪声容忍是概率性、尽力而为的匹配增强，区别于 FR-002
  中"`action_id` 相同即决定性证据"这一确定性规则。
- **FR-009**: 非幂等重复执行防护判断"是否为同一动作"MUST 基于 FR-001～007 定义的稳定动作身份、
  安全冲突检查与 fail-safe 规则，MUST NOT 仅依据自由文本是否逐字相等。
- **FR-010**: 对任一非幂等动作，只有当其上一次执行对应的 `ActionEffect` 被可靠确认为 `no_effect`、
  且该测试步骤的共享重试预算仍有剩余时，系统才 MAY 允许重新执行该动作——这是允许重新执行非幂等动作
  的唯一条件；其余 `ActionEffect` 状态，以及动作身份、安全冲突检查或步骤 intent 一致性判定存在歧义
  的情形，均 MUST NOT 触发重复执行。
- **FR-011**: 稳定动作身份与安全冲突检查 MUST NOT 过度宽松到将两个真正不同的业务动作（不同的
  `action_type` 或明确指向不同已声明目的的目标）错误合并为同一身份。

**危险目标漂移检测（风险信号驱动，安全问题 B）**

- **FR-012**（安全问题 B）: `action_type` 在同一测试步骤内的迭代之间发生变化，MUST 仅被系统视为
  触发 FR-006 步骤 intent 一致性检查的风险信号，MUST NOT 被无条件等同于 `dangerous_drift` 判定
  结果。
- **FR-013**（安全问题 B）: `dangerous_drift` 的最终分类 MUST 由以下三者以 AND 语义共同决定，而不是
  由 `action_type` 变化单独决定，也不由三者之一单独否决或单独放行：仅当 (a) 新目标声明的交互目的
  构成 FR-006 定义的合法步骤内微动作、且 (b) 该目的通过 FR-006 步骤 intent 一致性检查、且 (c) 该
  目标声明的动作风险级别不高于该类合法微动作被允许直接执行所要求的阈值时，系统 MAY 直接执行该新
  目标；(a)(b)(c) 任一条件不满足，系统 MUST NOT 直接执行。风险级别对是否需要额外的人工确认或强模型
  介入的处理，MUST 通过 FR-034 定义的恢复策略契约（而非本条新增的独立风险裁决逻辑）路由，MUST NOT
  开辟脱离该契约之外的风险裁决通道。
- **FR-014**: 当 FR-013 的 (a)(b)(c) 任一条件不满足——包括新目标的声明交互目的不构成任何合法步骤内
  微动作、或未通过步骤 intent 一致性检查、或声明风险级别超出阈值——并且该目标从指向一个可交互控件
  变为指向一个非交互的结果展示元素，或从一个可交互控件漂移为另一个不符合该步骤已声明 intent 的可
  交互控件时，系统 MUST 将其判定为危险目标漂移；危险目标漂移的判定 MUST NOT 仅局限于"可交互控件→
  非交互结果展示元素"这一种漂移方向。
- **FR-015**: 判定为危险目标漂移时，系统 MUST NOT 直接对新目标执行点击等动作；MUST 停止当前直接
  执行路径，转入既有的失败分类与恢复/重新定位流程。
- **FR-016**: 危险目标漂移的判定 MUST 在动作被发送执行之前完成，MUST NOT 等到执行后依据该轮
  `ActionEffect` 的结果才回溯认定。
- **FR-017**: 危险目标漂移的判定 MUST NOT 将目标描述的正常措辞变化（角色、位置、锚点文字均一致或
  高度吻合，仍指向同一类可交互控件）误判为危险漂移。

**Grounding 坐标空间协议**

- **FR-018**: Grounder 返回的每个候选目标 MUST 通过显式字段 `coordinate_space` 声明其边界框所使用
  的坐标空间，取值至少包含 `pixel`（原始像素坐标）与 `normalized_1000`（0–1000 归一化坐标，X、Y
  两个坐标轴分别独立相对图像宽度、高度归一化）。同一次 Grounding 响应中的不同候选 MAY 分别独立声明
  不同的 `coordinate_space`；系统 MUST 对每个候选分别按其自身声明的坐标空间独立完成换算与校验，
  MUST NOT 对整个响应套用单一坐标空间假设。
- **FR-019**: 系统在使用任何候选坐标执行动作之前，MUST 将其统一换算为当前实际截图分辨率下的原始
  像素坐标；换算逻辑 MUST 正确处理非正方形分辨率（例如宽高比悬殊、纵向尺寸超过 1000 的画面），不得
  将某一归一化坐标轴的数值误当作另一坐标轴或原始像素值直接使用。
- **FR-020**: FR-019 所述的换算——同一个候选坐标从其声明的坐标空间换算为原始像素坐标——MUST 有且
  仅发生一次；系统 MUST NOT 对已经完成换算的坐标重复换算，也 MUST NOT 在多个处理环节各自独立实现
  并执行该换算导致结果不一致。
- **FR-021**: 当候选目标未声明 `coordinate_space`、声明了 FR-018 定义之外的未知取值、或声明的坐标
  空间与其数值范围明显矛盾时，系统 MUST 拒绝该候选，MUST NOT 猜测其含义后仍然执行点击。对于不含
  `coordinate_space` 字段的历史 Grounder 响应，系统 MAY 尝试推断其坐标空间，但推断 MUST 同时满足：
  (a) 将该候选坐标分别代入 `pixel` 与 `normalized_1000` 两种解释后，MUST 恰好有一种解释同时满足
  完整的边界约束与已有证据的一致性约束；(b) 若两种解释都满足、都不满足、或已有证据本身相互冲突，
  则视为无法可靠推断，MUST 按拒绝处理。
- **FR-022**: 当全部候选均因坐标空间缺失、矛盾或换算后越界而被拒绝时，系统 MUST 停止当前直接执行
  路径并转入既有的失败分类与恢复/重新定位流程，MUST NOT 回退到猜测坐标。
- **FR-023**: `normalized_1000` 的合法取值范围为闭区间 [0, 1000]（0 与 1000 本身均视为合法边界值）。
  候选的完整边界框换算后的四个角点、以及最终用于点击执行的坐标点，MUST 全部落在当前实际截图分辨率
  的原始像素范围内；任一角点或最终点击点越界，均 MUST 按 FR-021/022 的越界规则拒绝该候选。

**声明式运行前置条件**

- **FR-024**: 测试用例或场景 profile MAY 声明运行前置条件，形式为一组通用命名 fact（key + 期望值
  或 matcher）；核心框架 MUST NOT 为任何具体业务预置固定的前置条件字段。该声明语法与校验器 MUST 与
  既有业务结果断言（`verification_mode`）机制共享同一套底层 fact/assertion 实现，仅触发时机不同
  （运行前置条件在发送首个输入事件之前触发一次性比较；业务结果断言在每个测试步骤执行后触发比较）；
  本 feature MUST NOT 为运行前置条件新增第二套并行的、与业务结果断言不兼容的声明语法。
- **FR-025**: 系统在发送第一个输入事件之前，MUST 将声明的前置条件与独立观察到的证据自动比较；任一
  项不一致、证据无法可靠提取、或证据本身相互冲突时，系统 MUST 将运行判定为前置条件失败、保存失败
  原因与证据并停止，MUST NOT 发送任何业务或恢复动作。
- **FR-026**: 系统 MUST NOT 自动执行状态变更类的重置/清理动作来满足声明的前置条件；前置条件所需的
  初始状态 MUST 通过外部/人工确认或独立配置提供的证据来满足，而不是由系统自行构造。

**声明式已发送动作审计**

- **FR-027**: 测试用例或场景 profile MAY 通过通用 matcher（基于 `action_type`/目标/intent）为动作
  声明审计 tag/类别；核心框架 MUST NOT 硬编码任何固定的业务动作分类。
- **FR-028**: 按 tag 的发送次数统计 MUST 仅计入执行结果证明键鼠事件确实已发送的动作；被 RepeatGuard/
  一致性检查/坐标空间拒绝拦截、未产生真正发送的动作提案 MUST NOT 计入任何 tag 的发送次数，但 MUST
  在逐轮审计记录中保留其"被拦截"状态。

**向后兼容**

- **FR-029**: 系统 MUST 保持对不声明前置条件/tag/业务断言、仅含弱证据（如通用画面变化信号）的旧格式
  测试用例的加载与执行能力，MUST NOT 因本 feature 的改动导致其无法被加载。
- **FR-030**: 旧格式用例产生的弱断言判定与本 feature 声明式机制产生的确定性判定结果 MUST 在最终结果
  与报告中保持可清晰区分，MUST NOT 被本 feature 的改动混同或掩盖。

**恢复边界**

- **FR-031**: 本 feature 范围内的任何失败处理或恢复路径 MUST NOT 通过发送无依据的默认按键导航来
  降级鼠标点击。
- **FR-032**: 本 feature 范围内的任何失败处理或恢复路径 MUST NOT 执行任何不在该测试步骤已声明动作
  范围内、会改变被测应用状态的操作作为恢复手段。
- **FR-033**: 危险目标漂移（FR-014～016）与坐标空间拒绝（FR-021～022）触发的停止 MUST 遵循既有的
  失败分类与恢复框架及其共享重试预算门禁，MUST NOT 开辟脱离预算控制的独立重试通道。
- **FR-034**: 所有可能由本 feature 新增结果（`dangerous_drift`、`ambiguous_fail_safe`、坐标空间
  拒绝、前置条件失败）到达的恢复策略 MUST 分别显式声明：最大执行次数、冷却时间、是否消耗全局重试
  额度、是否允许改变动作路径、是否需要强模型、是否需要人工确认。任一字段缺失或非法时，配置加载
  MUST 失败；系统 MUST NOT 使用隐式默认值、无限重试或绕过共享预算继续运行。

**报告可审计性**

- **FR-035**: 每一轮动作迭代的报告记录 MUST 包含该轮计算得到的稳定动作身份摘要（含所属测试步骤与
  是否命中 `action_id` 强匹配）、安全冲突检查/一致性检查/危险漂移的判定结果与理由。
- **FR-036**: 涉及 Grounding 的报告记录 MUST 包含候选声明的 `coordinate_space`、换算前的原始候选
  坐标、以及换算后用于实际执行的原始像素坐标。
- **FR-037**: 每个测试步骤的报告记录 MUST 包含其最终业务结果断言的判定依据，使复核人员无需重新运行
  即可判断该步骤通过/失败/不确定的具体原因。
- **FR-038**: 每次运行的报告记录 MUST 包含前置条件评估记录（声明的 fact、观察到的证据、比较结果）
  与按声明 tag 分类的动作发送次数统计（FR-027/028），使复核人员无需重新运行或复核原始日志即可完成
  审计。

**测试与验证方式**

- **FR-039**: 本 feature 新增的自动化测试 MUST 基于固定截图、录制帧序列或其他可离线重放的证据数据
  运行，MUST NOT 在常规自动化测试执行过程中连接或操作真实/在线目标环境。
- **FR-040**: 任何声称提供本 feature 所述通用框架能力的变更，MUST 至少使用两个互不相关的离线场景
  （参见 US8 中的表单提交、图标菜单、弹窗/滚动微动作三个场景）验证，外加任意数量的单场景回归 fixture
  （如 POS 购物袋结算）；单一场景的回归 fixture MUST NOT 被视为足以证明该能力具备通用性的充分依据。
- **FR-041**: 涉及真实/在线环境的验证 MUST 作为独立于常规自动化测试运行的环节，仅在获得最终人工
  批准后执行，MUST NOT 被纳入常规自动化测试流水线中自动触发。

### Key Entities

- **稳定动作身份（Stable Action Identity）**：作用范围严格限定在单个测试步骤内的复合标识，由该
  测试步骤、`action_type`、（若连续迭代提供了相同且非空的）`action_id` 共同组成；`action_type` 与
  非空 `action_id` 同时相同即为"同一逻辑动作尝试"的强匹配证据，用于非幂等重复执行防护，可覆盖自由
  文本改写差异；不同测试步骤之间不共享同一身份；本身 MUST NOT 被当作新目标安全的证明。
- **目标安全冲突信号（Target Safety Conflict Signal）**：新一轮目标的角色、交互性质或空间证据与
  前一轮目标发生的实质冲突；无论稳定动作身份是否匹配、无论前一轮 `ActionEffect` 是否为 `no_effect`，
  该信号出现时都 MUST 触发步骤 intent 一致性检查。
- **步骤意图一致性检查（Step Intent Consistency Check）**：判断新提出的目标是否仍然符合该测试步骤
  已声明业务意图的验证过程；验证不通过或结果存在歧义时，MUST 按 fail-safe 规则处理。
- **合法步骤内微动作（Legitimate Step-Internal Micro-Action）**：具有独立声明交互目的（如关闭遮挡
  元素、滚动、重新聚焦、等待、重新观察）、通过步骤 intent 一致性检查、且不构成对同一非幂等动作延续
  的新目标；MAY 被执行，但 MUST NOT 被用于重新执行业务结果尚未确定的主要非幂等动作。
- **危险目标漂移判定（Dangerous Target Drift Classification）**：由声明交互目的、声明动作风险级别、
  与步骤 intent 一致性检查结果以 AND 语义共同决定的分类结果——三者必须同时满足（目的属于合法微动作、
  通过一致性检查、风险级别不超阈值）才允许直接执行，任一不满足即判定为漂移；MUST NOT 由单一信号
  （如 `action_type` 变化）直接决定，也 MUST NOT 由三者之一单独否决或单独放行；判定为漂移时在执行
  前阻止直接点击，风险级别导致的人工确认/强模型介入需求 MUST 通过 FR-034 的恢复策略契约路由。
- **坐标空间声明（Coordinate Space Declaration）**：Grounding 候选目标通过显式字段 `coordinate_space`
  声明的坐标空间类型（`pixel` / `normalized_1000`）；同一响应内的不同候选可各自独立声明不同类型。
- **转换后执行坐标（Resolved Execution Coordinates）**：坐标空间声明按当前实际截图分辨率换算得到的
  原始像素坐标；该换算对每个候选坐标有且仅发生一次；换算后的完整边界框四角与最终点击点均须落在当前
  截图分辨率范围内。
- **声明式运行前置条件（Declarative Run Precondition）**：测试用例/场景 profile 声明的一组通用命名
  fact（key + 期望值/matcher）；与独立观察证据自动比较，不一致时零输入停止；不得由系统自动重置/
  清理环境来满足。与既有业务结果断言（`verification_mode`）共享同一底层 fact/assertion 声明语法与
  校验器，仅触发时机不同（运行前一次性触发 vs 步骤后触发），不是独立的第二套断言接口。
- **声明式动作 Tag（Declarative Action Tag）**：测试用例/场景 profile 通过通用 matcher 声明的动作
  审计类别；核心框架不预置任何固定业务分类；仅"确实已发送"的动作计入 tag 计数。
- **恢复策略契约（Recovery Policy Contract）**：每条恢复策略必须显式声明的六个字段——最大次数、
  冷却时间、是否消耗全局重试额度、是否允许改变动作路径、是否需要强模型、是否需要人工确认；缺失任一
  字段视为配置错误。
- **实际发送动作清单（Executed Action Log）**：仅包含执行结果证明键盘或鼠标事件已经发送的动作；
  被安全组件拦截的动作提案保留在逐轮审计中，但不属于该清单、不计入 tag 发送次数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在"表单填写并提交"离线场景中，即使 Planner 在同一提交步骤的重试中对同一非幂等提交
  动作使用不同措辞或目标描述，提交动作被重复执行的次数仍为 0；判定依据 FR-001～011 定义的稳定动作
  身份、安全冲突检查与 fail-safe 规则。
- **SC-002**: 在"无文字图标打开菜单"离线场景中，系统在缺乏文字锚点的情况下仍能正确识别视觉目标身份，
  该目标的候选坐标按其声明的 `coordinate_space` 正确换算为原始像素坐标（且换算有且仅发生一次），
  点击动作严格执行 1 次。
- **SC-003**: 在覆盖非正方形、宽高比悬殊分辨率的坐标空间回归场景中，100% 的运行拒绝坐标空间缺失/
  矛盾/未知取值/换算后越界的候选，而不是猜测后仍然执行点击（猜测执行次数为 0）。
- **SC-004**: 在"弹窗关闭或滚动后再操作目标"离线场景中，合法的步骤内微动作（关闭弹窗、滚动、重新
  聚焦、等待、重新观察）100% 未被误判为危险目标漂移，且未被用于重新执行业务结果尚未确定的主要
  非幂等动作。
- **SC-005**: 在构造的真正危险漂移场景（可交互控件→非交互结果展示元素，或可交互控件→另一不相关
  可交互控件）中，100% 的漂移在执行前被拦截，不产生直接点击。
- **SC-006**: 在全部离线回归场景（含 US8 三个通用场景与 POS 附加场景）中，`dangerous_drift` 的
  判定 0 次由 `action_type` 变化单独触发——即每一次判定为漂移的情形，均能在报告中追溯到声明目的/
  风险级别/一致性检查结果这三者的联合依据，而非仅凭 `action_type` 变化。
- **SC-007**: 在全部离线回归场景中，当 `action_id` 相同（满足 FR-002 强匹配）但目标角色/交互性质/
  空间证据发生冲突时，100% 的运行仍运行了 FR-003 所要求的一致性/漂移检查，即使前一轮 `ActionEffect`
  为 `no_effect`，检查也未被跳过。
- **SC-008**: 在声明了运行前置条件的离线回归场景中，凡声明 fact 与观察证据不一致、证据不可读或
  相互冲突的运行，100% 在发送第一个输入事件之前停止，实际发送动作次数为 0，且报告明确标记前置条件
  失败及对应证据；两者完全一致的场景 100% 通过该前置门禁，且不产生任何框架自发起的重置类动作。
- **SC-009**: 在声明了动作审计 tag 的离线回归场景中，报告中按 tag 分类的发送次数与被拦截提案记录，
  均可直接从报告字段读出，无需复核原始日志或重新运行；被拦截的提案 100% 不计入任何 tag 的发送次数。
- **SC-010**: 本 feature 交付前既有的全部离线自动化测试，在应用本 feature 改动后重新运行时全部继续
  通过，不出现回归。
- **SC-011**: 本 feature 新增的全部场景均有对应的固定截图或 mock 驱动的离线回归测试覆盖，这些测试
  运行过程中发起真实/在线环境连接的次数为 0。
- **SC-012**: 本 feature 声称的每一项通用框架能力，均至少有两个互不相关离线场景（US8 三个通用场景
  中的任意两个及以上）的回归测试作为证据；仅由 POS 附加场景单独通过、而无法被至少一个其他不相关
  场景复现的能力，MUST 被视为未满足本条验收标准。
- **SC-013**: POS 购物袋结算离线回归 fixture 使用与其余通用场景完全相同的核心机制通过，不依赖任何
  仅为该场景编写的核心代码分支或固定字段；该 fixture 的通过结果单独MUST NOT 被视为任何 SC 的充分
  验收依据。

## Assumptions

- 本 feature 建立在既有的 `ActionEffect`、`StepVerificationResult`、`RepeatGuard`、
  `verification_mode` 等实体与流程之上，复用而不重新定义这些既有概念，只在"动作身份/目标安全判定"、
  "危险漂移分类"、"坐标空间处理"、"声明式前置条件与动作审计"这几个环节上做加固或新增声明式接口。
  非幂等动作的分类（`action_kind`）沿用既有的判定机制，不在本 feature 中重新定义。
- 目标是否可交互、是否为非交互结果展示元素的具体区分依据来自 Planner/Grounder 现有输出中的角色、
  文字、附近文字等信息，具体判别规则由实现阶段结合场景数据给出，不在本规格中固化算法细节；若这些
  信息本身不可靠，FR-014 覆盖的"可交互控件→另一个不符合 intent 的可交互控件"漂移方向可作为额外的
  安全网，不完全依赖"可交互/非交互"这一单一二元区分。
- 0–1000 归一化坐标采用视觉定位模型的常见约定，即 X、Y 两个坐标轴分别独立相对图像的宽度、高度
  归一化，而非共用同一条最长边。
- 本 feature 不改变既有的 Planner/Grounder/Executor/Verifier 职责分离、恢复与重试共享预算等既有
  原则；坐标空间协议与危险漂移检测均落在 Grounder 与 Executor 之间的既有边界内，不新增独立角色。
- 声明式前置条件与声明式动作 tag 是本 feature 新引入的通用接口；不声明这些字段的既有测试用例继续
  按既有的兼容加载与弱断言判定行为运行，不因本 feature 被动强制迁移。
- "场景 profile"在本 feature 范围内是完全可选的声明容器（把 facts/tags/matchers 打包成可跨测试用例
  复用的配置），MUST NOT 被理解为本 feature 新增的独立注册接口或公共 API；核心框架 MUST 在零 profile
  注册的情况下仅凭测试用例内联声明即可完整满足 FR-024～028。本 feature 不设计、不实现任何 profile
  专属的注册/发现机制。
- POS 购物袋结算场景（`vnc_agent/testcases/pos-buy-bag-checkout.yaml`）作为触发本次重新基线的历史
  背景与其中一个离线回归 fixture 保留，不在规格中固化其具体业务字段、坐标或流程分支之外的更多细节；
  不记录任何 API Key、密码或其他凭据。
- 本 feature 范围不包含对既有观察、稳定性等待、报告生成整体架构的重新设计，仅在动作身份/目标安全、
  漂移检测、坐标空间换算、声明式前置条件与动作审计这几个具体决策点上收紧或新增规则。
