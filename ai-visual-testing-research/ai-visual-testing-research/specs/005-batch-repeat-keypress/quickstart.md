# Quickstart: Validating Batch Repeat Key Press

This is a run/validation guide, not an implementation guide — see `data-model.md` and
`contracts/` for the field/interface specifics, and `tasks.md` (generated by `/speckit-tasks`) for the
implementation steps themselves.

## Prerequisites

- `vnc_agent` dev environment set up (`pip install -e ".[dev]"` from `vnc_agent/`), Python 3.12.
- No live VNC target is required for the scenarios below — they run entirely offline against
  `FakeVNC`/`StubPlanner` fixtures already used by the existing e2e suite
  (`vnc_agent/tests/e2e/conftest.py`).

## 1. Run the new/changed unit tests directly

```bash
cd vnc_agent
pytest tests/unit/test_batch_repeat_key_validation.py -v
pytest tests/unit/test_action_policy_priority.py -v
pytest tests/unit/test_execution_router_batch_repeat.py -v
pytest tests/unit/test_keyboard_executor_repeat.py -v
pytest tests/unit/test_testcase_validation.py -v
```

Expected: all pass. Together these prove — per file — model validation (bounds, key vocabulary,
modifier rejection), `ActionPolicy` routing, `ExecutionRouter` result population, and
`KeyboardExecutor` loop behavior (success + fail-fast partial failure).

## 2. Run the cross-scenario e2e proof

```bash
pytest tests/e2e/test_scenario_16_batch_repeat_key.py -v
```

Expected: pass, and demonstrates, using the generic fixture testcase
(`tests/fixtures/testcases/generic-batch-repeat-key-example.yaml`) and `FakeVNC`/`StubPlanner`:
- `stub_planner.plan_calls == 0` for the batch-repeat step's iteration(s) — no Planner call at all.
- `drv.keys` contains exactly `count` entries of the declared key, sent consecutively.
- The iteration's `execution_result.requested_count == execution_result.completed_count == count`.
- Exactly one post-action verification ran for the step (one entry in the step's iteration list for
  the successful attempt, not one per key send).

## 3. Confirm existing behavior is untouched (regression gate)

```bash
pytest tests/unit/ tests/e2e/ tests/integration/ -v
```

Expected: the full existing suite still passes, including (at minimum, spot-check if the full run is
slow):

```bash
pytest tests/e2e/test_scenario_02_keyboard_first.py -v
pytest tests/unit/test_action_policy_priority.py -v
```

These exercise the pre-existing `press_key`/`hotkey` paths this feature must not alter (FR-011,
FR-012, SC-005).

## 4. Validate the invalid-declaration rejection path

Author (or reuse a fixture) a malformed test case, e.g.:

```yaml
steps:
  - id: bad-step
    name: bad
    intent: invalid batch repeat
    batch_repeat_key:
      key: shift        # modifier — must be rejected
      count: 0           # below minimum — must be rejected
    expected: { operator: all, conditions: [{ type: screen_changed }] }
```

```python
from vnc_agent.domain.testcase import load_test_case, FieldValidationError

try:
    load_test_case("path/to/bad-case.yaml")
    raise AssertionError("expected FieldValidationError")
except FieldValidationError as e:
    print(e.errors)  # should name batch_repeat_key.key and batch_repeat_key.count
```

Expected: `load_test_case()` raises before anything resembling a run starts — no VNC connection, no
screenshot, no key ever sent (Story 2 acceptance scenarios).

## 5. Validate the ScannerSimulator scenario definition (offline read, no live VNC needed for this step)

```bash
python -c "from vnc_agent.domain.testcase import load_test_case; tc = load_test_case('testcases/pos-scan-magazine-checkout.yaml'); step = next(s for s in tc.steps if s.id == 'clear-barcode-with-backspace'); print(step.batch_repeat_key)"
```

Expected: prints a `BatchRepeatKeyDeclaration(key='backspace', count=20, interval_ms=None)` (or the
chosen count), confirming the testcase YAML now declares the batch instead of relying on
`max_retries`-driven per-key Backspace prose (FR-013, SC-006).

## 6. (Optional, requires a live Windows VNC target) Full ScannerSimulator run

```bash
VNC_AGENT_VNC_PASSWORD=*** vnc-agent run testcases/pos-scan-magazine-checkout.yaml --target win10-test-01
```

Expected: the Barcode field is cleared in the `clear-barcode-with-backspace` step using a single
`ActionIteration` (visible in the run's HTML/JSON report as one iteration for that step, versus the
multiple iterations it took before this feature), and the report's `execution_result` for that
iteration shows `requested_count`/`completed_count`.
