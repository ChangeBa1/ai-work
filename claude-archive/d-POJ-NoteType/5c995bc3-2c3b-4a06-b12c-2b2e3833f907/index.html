CRITICAL: Use Formulas, Not Hardcoded Values

Always use Excel formulas instead of calculating values in Python and hardcoding them. This ensures the spreadsheet remains dynamic and updateable.

❌ WRONG - Hardcoding Calculated Values

# Bad: Calculating in Python and hardcoding result
total = df['Sales'].sum()

# Bad: Computing growth rate in Python
growth = (df.iloc[-1]['Revenue'] - df.iloc[0]['Revenue']) / df.iloc[0]['Revenue']
sheet['C5'] = growth  # Hardcodes 0.15

# Bad: Python calculation for average
avg = sum(values) / len(values)
sheet['D20'] = avg  # Hardcodes 42.5

✅ CORRECT - Using Excel Formulas

# Good: Let Excel calculate the sum
sheet['B10'] = '=SUM(B2:B9)'

# Good: Growth rate as Excel formula
sheet['C5'] = '=(C4-C2)/C2'

# Good: Average using Excel function
sheet['D20'] = '=AVERAGE(D2:D19)'

This applies to ALL calculations - totals, percentages, ratios, differences, etc. The spreadsheet should be able to recalculate when source data changes.

Formula Verification Checklist

Quick checks to ensure formulas work correctly:

Essential Verification

  • [ ] Test 2-3 sample references: Verify they pull correct values before building full model
  • [ ] Column mapping: Confirm Excel columns match (e.g., column 64 = BL, not BK)
  • [ ] Row offset: Remember Excel rows are 1-indexed (DataFrame row 5 = Excel row 6)

Common Pitfalls

  • [ ] NaN handling: Check for null values with pd.notna()
  • [ ] Far-right columns: FY data often in columns 50+
  • [ ] Multiple matches: Search all occurrences, not just first
  • [ ] Division by zero: Check denominators before using / in formulas (#DIV/0!)
  • [ ] Wrong references: Verify all cell references point to intended cells (#REF!)
  • [ ] Cross-sheet references: Use correct format (Sheet1!A1) for linking sheets

Formula Testing Strategy

  • [ ] Start small: Test formulas on 2-3 cells before applying broadly
  • [ ] Verify dependencies: Check all cells referenced in formulas exist
  • [ ] Test edge cases: Include zero, negative, and very large values

1. 核心推理越界：「日志空白 ≠ 硬件层故障」

  • 报告说法：故障时点「完全无日志」⇒ 问题发生在「Windows 启动前（POST／主板・电源系硬件层）」。
  • 逻辑问题：Windows XP 的事件日志服务要到启动中段才启动。在此之前，MBR/引导扇区代码、NTLDR/ntdetect、ntoskrnl/HAL 早期初始化、BOOT_START/SYSTEM_START 驱动加载（包括磁盘控制器驱动本身）、硬盘起转、以及 pre-EventLog 蓝屏——全部都不会写一条事件日志。「无日志」只能把故障收敛到「事件日志服务启动之前」，这是一个比「硬件」大得多的空间。报告把「Windows 启动前」悄悄等同于「硬件」，是外推而非证据。
  • 影响：这是承重墙。它一旦松动，后面「电容老化、电源老化」的定向就失去了排他性。
  • 建议：改写为「无日志只能说明故障发生在事件日志服务启动之前——POST、引导扇区、NTLDR、内核/驱动早期初始化、或硬盘起转/无法读取引导文件」。要进一步收敛到「硬件」，必须靠蜂鸣码、硬盘检测、POST 进度等额外证据，而不是单凭日志空白。

2. 关键判别实验没做：长按电源键（软复位）vs 只有拔电源才能恢复

  • 报告说法：恢复手段是「只有拔掉 AC 电源线再接回」。
  • 逻辑问题：报告把机理解释（待机残压需完全放电 ⇒ PSU/主板常电域故障）建立在「只有拔电才管用」这个排他性上，但这个排他性从未被验证。下一次故障时，先长按电源键 5–10 秒强制关机再开机——

  • 影响：报告在一个从未实验过的变量上得出了机理结论。

  • 影响：这个假说可能比「电容老化」更贴合报告自己的事实，却根本没进入候选。

4. 最贴合的替代原因被「凭空排除」：硬盘冷启动起转、USB 外设

  • 逻辑问题：「首次冷启动（断电 15–19 小时后）黑屏、电源灯亮、无日志、断电再通电立即恢复、13 年老机（极可能还是原装机械盘）」——这是 HDD 主轴电机静摩擦（stiction）/ 冷态起转困难的教科书式画像，其经典现场对策正是一次 AC 断通。同样地，「只有拔 AC 才恢复」也同样符合 USB 外设反向馈电/拖累 +5VSB 的情形（拔 AC 会同时切掉 USB 待机电）。报告只点名「主板/电源电容」，却没用最便宜的测试排除这两类。
  • 建议：把 HDD、USB 外设电源时序作为一等假说。判别手段几乎免费：冷启动时拔掉全部 USB 设备；故障启动时听/测硬盘是否起转；用已知良好硬盘冷启动。

5. 触发条件（断电 15h+）从未复现，n=2 且无基线，置信度被高估

  • 报告说法：复现关键是「断电 15 小时以上的当日首次启动」。
  • 逻辑问题：
  • 验证只做到约 1 小时放置，且是当天恢复后做的——同时把「断电时长」和「恢复后状态」两个相关变量都压在安全侧。真正的特征事件复现次数 = 0；这种「未复现」对结论真假几乎没有判别力。
  • 结论建立在连续两天的 n=2 上，没有基线（之前多少次「当日首次启动」是成功的，未知）。这个模式可能是巧合、环境因素、或最近才引入的回归，而非老化。
  • 「当日首次启动」这个框定部分是循环的：既然恢复手段就是拔电再启动，那么当天剩下的启动当然都成功——任何「需断电复位才能启动」的故障都会呈现为「首次启动失败」。
  • 建议：把「最可能原因」降级为「候选假说」。至少做一次（最好多次）15–19 小时冷断电复现，并把「过夜插电」与「过夜拔电」作为两个独立单元格分别测。

6. CMOS 电池列为「高优先级」与报告自身的关键症状相矛盾

  • 报告说法：对策②换 CMOS 纽扣电池（高优先级、便宜易行）。
  • 逻辑问题：纽扣电池域故意设计成独立于 AC；而在 AC 插着过夜期间，是 +5VSB（不是纽扣电池）在维持 CMOS，所以故障区间内纽扣电池根本没被消耗。CMOS 电池耗尽的典型表现是「CMOS checksum bad / RTC 走时不准 / BIOS 恢复默认」（有可见的 POST 文字），而非无声的黑屏不开机；而且如果电池真没电，拔 AC 恢复时反而更容易破坏 CMOS，而不是干净地恢复启动。报告没有任何 CMOS 症状（无走时偏移、无 checksum 报错），却把换电池排第二优先。
  • 影响：报告最强的证据（只有拔 AC 才恢复、线常插过夜）指向远离纽扣电池，而非指向它。这是结论与对策之间的内部不一致。
  • 建议：把 CMOS 电池降为「老旧硬件的常规保养项」，并明确说明恢复机理并不支持它；要么先采集 CMOS 证据（过夜后 RTC 是否偏移、恢复启动是否出现 checksum/默认加载提示）再决定优先级。

🟡 中严重度（2 项）

7. 电容机理无任何电气测量；计划做的「目视检查」与该主板不匹配

  • 报告断言「电解电容老化导致电源时序异常」，却没有 ESR 测试、没有纹波/示波器、没有 PWR_OK 捕获。而 2012–2013 年的 Ivy Bridge/ChiefRiver 板，CPU VRM 和 bulk 滤波大量使用固态聚合物电容——聚合物电容不会鼓包漏液，所以「开箱看鼓包/漏液」可能结构性地查不出所假设的缺陷。结果「目视干净」会被误读成「主板没问题」，却并不能为主板洗清嫌疑。
  • 老旧电解电容典型是在负载/发热下失效（起转、运行中），而非「轻载待机浸泡 15 小时后立即恢复」——与观察到的时间特征吻合度偏低。

8. 「长时间断电」与温度/时段/+5VSB 待机浸泡相混杂；15h+ 阈值未测

  • 一段长夜间间隔同时改变了：断电时长、环境温度（早晨冷机）、湿度、以及约 15 小时的 +5VSB 连续带电。报告挑了「断电时长/电容放电」，却没有一个测试能把「断电时长」与「温度/机械状态」分开。冷焊点/热胀冷缩断路、HDD 冷态粘连同样能拟合这两个数据点，指向的却是重焊/换盘，而非电容/电源。
  • 由于「线常插过夜」，断电时长与 +5VSB 待机浸泡在两次事件里不可分离，报告却单挑了断电时长当关键。建议把阈值如实表述为「介于 1h 与 15h 之间、未知」，并用「15h 断电+暖机 vs 15h 断电+冷机」「过夜插电 vs 过夜拔电」两组单元格去混杂。

🟢 低严重度（2 项有效）

  • POST 蜂鸣码从未观察/记录。AMI BIOS 上蜂鸣码是免费的内置判别器（能区分内存/显卡/CPU 与 pre-CPU 的供电停滞），连「是否有蜂鸣器」都没说明。在没用它的情况下断言「POST 层硬件故障」，定位的特异性偏弱。
  • 「电源灯亮」被过度解读为「略可放心」。电源灯只证明前面板 +5V（多由 +5VSB 派生）在场、且按键被 Super-I/O 登记；它对 CPU 是否执行、内存训练、POST 进度几乎不携带信息，HDD 起转卡住同样会是灯亮。应作为中性观察，不从中读出「安心」或因果。

综合阶段还产生了一条被判定为无效（strawman）的批评——「ping 不通不能说明机器没启动」——已过滤。报告把黑屏+无 ping+无 RDP+无日志四者合用来排除「Windows 已启动只是显示坏了」，这一推断是成立的。

✅ 报告做对的地方（为求平衡）

  • 边界推断部分正确：「无日志 + 无 ping + 无 RDP + 黑屏」确实排除了「Windows 已启动、仅是显示故障」，把故障锁定在「未到达可联网的 Windows 状态」——这一步是站得住的，问题只在于它过头到了「硬件」。
  • 诚实：明确承认 15h+ 冷启动复现未做、列为今后课题，没有谎称已复现。
  • 时间算术正确：约 19h、约 15.5h 断电，以及「两次都是长时间断电后的当日首次冷启动」的关联观察准确。
  • 控制变量到位：向上长确认是手动按键启动（排除 WoL/自动启动）、两天操作者不同（排除特定操作者）。
  • NetBT 4307 / Server 2511 判为良性——确实是常规网络事件，判断正确。
  • 长期对策合理：13 年老机建议更新、并把「拔电再启动」准确定位为应急对策而非修复，是稳妥的。

建议的下一步（按性价比排序的判别实验）

  1. 下次故障时：先长按电源键 5–10s 软复位再开机 → 不行再按前面板 reset → 还不行才断 AC。记录到底是哪一步恢复的（直接区分 +5VSB 域 vs 锁存状态）。
  2. 冷启动时拔掉全部 USB 外设再试（几乎免费的 USB 假说判别）。
  3. 故障启动时听/测硬盘是否起转；用已知良好硬盘冷启动（HDD 冷态粘连假说）。
  4. 把 zzwdt/MEI 当线索：抓一次正常启动的日志与恢复启动日志做 diff；查这块 ChiefRiver 板的 BIOS/ME 固件有无冷启动 errata，尝试 ME 完全复位或 BIOS 载入默认+刷新。
  5. 做真正的 15–19h 冷断电复现，过夜插电 vs 过夜拔电分两格测，看哪个变量真正预测故障。
  6. 把「最可能原因」改为「候选假说清单」，并先采集 CMOS 证据（过夜 RTC 偏移、checksum 提示）再决定要不要换纽扣电池。

一句话：报告的「定位到启动早期」是对的，但「定位到硬件/电容」是越界；真正能区分原因的两三个廉价实验还没做，而报告自己手里的 +5VSB/ME 线索反而被搁置了。
