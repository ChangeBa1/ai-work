什么时候读文件 / 用 grep 是合理的

  • 确认某个非常局部、不涉及调用关系的事实（比如一个常量的具体值、一行配置）。

要避免的模式：在还没查图谱的情况下，凭直觉 Glob / Grep 一堆文件、然后逐个 Read 去回答"X 在哪定义"或"谁调用了 X"——这正是图谱已经替你做完的事，手工做既慢又容易漏。

Best Practices

Library Selection

  • pandas: Best for data analysis, bulk operations, and simple data export
  • openpyxl: Best for complex formatting, formulas, and Excel-specific features

Working with openpyxl

  • Cell indices are 1-based (row=1, column=1 refers to cell A1)
  • Use data_only=True to read calculated values: load_workbook('file.xlsx', data_only=True)
  • Warning: If opened with data_only=True and saved, formulas are replaced with values and permanently lost
  • For large files: Use read_only=True for reading or write_only=True for writing
  • Formulas are preserved but not evaluated - use scripts/recalc.py to update values

Working with pandas

  • Specify data types to avoid inference issues: pd.read_excel('file.xlsx', dtype={'id': str})
  • For large files, read specific columns: pd.read_excel('file.xlsx', usecols=['A', 'C', 'E'])
  • Handle dates properly: pd.read_excel('file.xlsx', parse_dates=['date_column'])

## 原因メカニズム

1. 登録機が会計機へ中間取引を送信。状態 `SalesTran_SendMTransaction` となり、UI 側でバックグラウンドポーリング（`while` ＋ `Thread.Sleep(500ms)`）が起動する。

3. 店員が「再実行」ボタンを押下。状態が `SalesTran_WaitingReInquiryCanAcceptMTransaction` へ遷移する。
4. ⚠ このとき UI ポーリングのバックグラウンドスレッドは停止しておらず、`_isFinished` もリセットされないまま継続する。
5. 会計機が取引を取得（`OperationState == 2`）。ポーリングがこれを検知し `Sales_NotifyCustomer` を発行する。

7. 同時に `_isFinished = true` が設定されポーリングスレッドが自滅。以降 `Sales_NotifyCustomer` を発行する経路がなくなり、画面は「再送信中」のまま固定される。

用大白话从头讲一遍：

一、出了什么问题（现象）

店员用的收银机（注册机），有时候需要把一笔交易转交给旁边的会计机去处理（比如顾客要到会计机那台机器付款）。这个"转交"动作正常几秒就完成了。

但偶尔会出这种情况： - 会计机那边慢了（比如它正在恢复、重启），超过 10 秒还没接住这笔交易； - 注册机画面上提示超时，店员按了"再执行"想重发一遍； - 结果画面就卡在"正在重发"不动了，店员怎么点都没反应，最后只能强行关掉程序重开。

实机里很少碰到（因为会计机通常很快），但在会计机慢的环境（虚拟机、旧机器）下会冒出来——这也是它拖了很久没解决的原因。

二、为什么会卡（原因）

注册机画面背后有个"自动监视"功能，不停偷偷看"会计机接到没有"，一看到接到了，就喊一声"好了，转过去了"，交易就往下走。

卡死的根子是这个自动监视和"操作规则"对不上，出了三个毛病：

  1. 自动监视不分时机：它只管"会计机接到就喊"，不管现在该不该喊。
  2. 按"再执行"时没把它叫停：店员按了"再执行"、交易进入"重新确认"阶段后，自动监视还在继续跑。
  3. 规则上"重新确认"阶段不让喊"转过去了"：所以自动监视这时候喊的那一声，被规则挡掉了、白喊。

最要命的是：自动监视喊完那一声被挡掉后，它以为自己任务完成了、就停工了。于是后面真正需要喊"转过去了"的时候，反而没人喊了——交易就僵在中间，画面卡死。

一句话：盯梢的人在不该喊的时候喊了一声、被无视后以为自己完事了走了，结果该喊的时候没人喊了。

三、四个办法

案1（老办法）——管好自动监视的开关时机 让自动监视在"会计机开始接→开盯、进入重发→停、收到完成通知→停、按了再执行→重新开盯"。 ❌ 当年漏了一步：按"再执行"时只关了定时器，没把盯梢的人真正叫回来、也没让他重新打起精神，所以单独用堵不住。

案2（老办法）——放宽规则，让"重新确认"阶段也允许喊"转过去了" 直接改规则表，让那个阶段也能执行"转过去了"。 ❌ 规则表里这个阶段和另外两个正常阶段写在同一行，一改就把那两个正常阶段也一起放宽了，导致正常流程也被干扰（提前/重复喊"转过去了"），而且画面上"几号会计机接的"也显示不出来。

案3（新办法）——让自动监视学聪明 + 按再执行时把它叫停（只改程序，不动规则） 让自动监视喊之前先看一眼"现在是不是该喊的时候"，不该喊就不喊、也别以为自己干完了；按"再执行"时把它真正叫停、重新待命。 ✅ 只改一个程序文件，影响最小，所有机型自动生效。 ❌ 之后要靠会计机那边发通知来"叫醒"它重新喊，通知要是没送到还是会卡。

案4（新办法·推荐）——把规则表拆开，单独给"重新确认"开个口子（改规则） 把那一行拆成几行，只对"重新确认"这一项允许喊"转过去了"，并把画面上"几号会计机接的"也补上显示；双人收银那份规则表也照样拆一遍。 ✅ 不靠通知、根治；也不会误伤别的正常流程。 ❌ 动了规则表，要回归测试；而且有人收银和双人收银是两份规则表，别只改一份（漏改双人那份，双人侧还会卡）。

交易转交时，送信画面（SendMTransactionDialog）背后有一个「自动监视」功能——后台循环检查会计机有没有接住这笔交易。一旦查到会计机接住，就发一个「确定」通知（Sales_NotifyCustomer），交易推进到下一步（Fixed），画面正常离开。
