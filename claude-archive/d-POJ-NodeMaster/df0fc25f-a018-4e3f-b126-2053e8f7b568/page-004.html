根据 3 个案件（272279/293020/295405）的日志分析和源码调查，总结如下：

问题现象

POS4U 在运行 5~24 小时后崩溃，报错 COMException 0x80070008（没有足够的存储空间）。崩溃堆栈 3 次完全一致，均指向 WPF 文本渲染过程中底层调用 GetDesignGlyphMetrics 失败。

分析结论：高度怀疑 GDI 句柄泄漏，但未能在测试环境复现

支持这一判断的证据（logs）

证据 说明
🎯 崩溃码 = 0x80070008 这是 GDI 资源耗尽 的典型错误码，不同于托管堆 OOM
🎯 32bit 进程（WOW64） GDI 对象上限 10,000/进程，长时间运行易触顶
🎯 崩溃统一在 WPF 字体渲染 GetDesignGlyphMetrics 底层依赖 GDI，GDI 耗尽后首当其冲
🎯 3 台设备 3 个版本均崩溃 原因不在 POS4U 代码变更，而在 OS/驱动/COM 层
🎯 崩溃前均有 CashChanger 通信问题 CashChangerStatusRead（内部调用 DirectIO）反复失败，ActiveX COM 互操作为泄漏嫌疑入口
🎯 运行时长符合缓慢泄漏模型 最短 5h40m，最长 23h32m 后崩溃，与每笔交易泄漏少量 GDI → 逐步积累相符

未能复现的原因

在测试环境进行了代码级排查和压力测试准备，但缺乏触发泄漏的关键条件：

  1. 测试环境没有 Glory RAD300 实体设备 + OPOS 驱动 — 泄漏很可能发生在 OPOS ActiveX 控件（OPOSCashChanger.ocx / CHANGE~1.DLL）的 COM 互操作层，模拟器可能不会复现相同的内存分配行为
  2. 缺少崩溃时的 Full Memory Dump — 无法直接分析崩溃时刻哪种资源耗尽
  3. 生产环境的运行时间窗口过长（5~24h） — 短时间压力测试难以模拟泄漏积累过程
  4. 代码内部未植入 GDI 计数日志 — 无法在崩溃前观测到 GDI 数是否逼近 10,000 上限
