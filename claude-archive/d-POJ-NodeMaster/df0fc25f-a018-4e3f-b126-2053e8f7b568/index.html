结论：根本原因分析

COMException (0x80070008) 是 WPF 渲染引擎在文本/字体测量时 GDI 资源分配失败引起的崩溃。

原因排查方向（优先级从高到低）：

  1. GDI 对象泄漏 — OPOS 设备驱动(COM/OCX)在反复调用中泄漏 GDI 对象（笔、画刷、字体等）。32bit 进程默认 GDI 对象上限为 10,000，达到后新建字体/画笔等GDI对象会返回 ERROR_NOT_ENOUGH_MEMORY。可以通过 Process Explorer 监控 GDI Object 计数确认。

  2. 桌面堆(Desktop Heap)耗尽 — 长时间运行的 POS 终端，尤其 Windows Server 2016 (OS build 14393) 默认桌面堆较小（约 512KB~1MB）。OPOS 驱动的窗口消息、自定义控件渲染色消耗桌面堆，最终字体渲染无法分配。

  3. 32bit 进程地址空间碎片化 — POS4U.exe 是 32bit (WOW64) 进程，用户空间上限 2GB（不启用 /3GB）。虽然托管 Heap 未满（非 OOM），但原生 GDI 连续内存块无法分配。

建议的下一步

  1. 增加 GDI 对象计数日志（与内存日志并行输出），确认崩溃前是否逼近 10,000 上限
  2. 使用 Process Explorer / GDIView 在现场验证 GDI 对象数的随时间变化趋势
  3. 验证桌面堆大小：检查 HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Session Manager\SubSystems\Windows 的 SharedSection 参数
  4. 代码层：在 OPOS 设备调用的关键路径（CashChangerStatusRead、FixDeposit 等）确认是否及时释放 IDisposable 的 GDI 资源
  5. 临时规避：如果 GDI 对象数确实接近上限，可以修改注册表提高 GDI Process Handle Limit，或定期重启 POS 进程

什么是GDI

GDI = Graphics Device Interface（图形设备接口），是 Windows 的一个核心子系统，负责管理屏幕绘制、字体渲染、窗口显示等所有"画东西"的操作。

为什么 GDI 和这个崩溃有关？

每个 Windows 进程能创建的 GDI 对象 是有限的： - 32bit 进程（POS4U 就是这个）：上限 10,000 个 - 64bit 进程：上限 100,000 个

GDI 对象包括： - 设备上下文（HDC）— 画图用的"画布" - 画笔/画刷（HPen/HBrush）— 画线的颜色和形状 - 字体（HFont）— 文字怎么显示 - 位图（HBITMAP） - 区域（HRGN）

崩溃链路

OPOS CashChanger.DirectIO() 每次调用 → COM 互操作层分配 GDI 对象
         ↓ 但没有释放（泄漏）
GDI 对象数从 ~500 缓慢增长 → 接近 10,000
         ↓
WPF 要画文字 → 调用 GetDesignGlyphMetrics → 申请 GDI 字体对象
         ↓
GDI 配额耗尽 → 返回错误 0x80070008（"没有足够存储空间"）
         ↓
COMException → 应用崩溃

类比

GDI 对象就像停车位。停车位总共 10,000 个。你每次开车去办事（调用 OPOS），车就停那里。但每次办完事车没开走（GDI 泄漏），车位越来越少。15-24 小时后车位全满，你再想开车去办事（WPF 画文字），只能原地打转 — 崩溃。

关键点

  • 不是内存不足 — 物理内存/虚拟内存都还有，是 GDI 这个"停车位"用完了
  • 和 .NET GC 无关 — GDI 对象是 Windows 内核对象，不受 C# 垃圾回收管理
  • WPF "躺着中枪" — POS4U 自己的业务代码没问题，是底层 OPOS 驱动/C++ COM 组件泄漏了 GDI，WPF 在需要新 GDI 对象时第一个撞上枪口

两种植入方式，推荐第一种。

方式 1：在 TimerPutCashChangerStatus 中植入（推荐）

优点：每 10 秒自动执行一次，获得 GDI 数的时间序列，能观察到增长趋势。

在 TimerPutCashChangerStatus.cs 中：

using System.Runtime.InteropServices; // ← 新增
using System.Diagnostics;              // ← 检查是否已有

public class TimerPutCashChangerStatus : TimerSchedulerPluginBase
{
    // 新增：P/Invoke 声明
    [DllImport("user32.dll", SetLastError = true)]
    private static extern int GetGuiResources(IntPtr hProcess, int uiFlags);

    private const int GR_GDIOBJECTS = 0;
    private const int GR_USEROBJECTS = 1;

    // 新增：上次日志记录的 GDI 数，用于计算增量
    private int _lastGdiCount = 0;
    // 新增：计数间隔（每 N 次 OnTimerElapsed 输出一次，避免日志太多）
    private int _logCounter = 0;
    private const int GdiLogInterval = 6; // 每 6 次 ≈ 每分钟一次（10s × 6 = 60s）

然后在 OnTimerElapsed() 方法中，在 try 块末尾或开头加上：

protected override void OnTimerElapsed(object sender, ElapsedEventArgs e)
{
    try
    {
        // 原有的处理...

        // ===== 新增 GDI 计数日志 =====
        this._logCounter++;
        if (this._logCounter >= GdiLogInterval)
        {
            this._logCounter = 0;
            try
            {
                var hProcess = Process.GetCurrentProcess().Handle;
                int gdiCount = GetGuiResources(hProcess, GR_GDIOBJECTS);
                int userCount = GetGuiResources(hProcess, GR_USEROBJECTS);
                int delta = gdiCount - this._lastGdiCount;
                Logger.Info($"[GDIMon] GDI={gdiCount}, USER={userCount}, Delta={delta}, "
                    + $"HandleCount={Process.GetCurrentProcess().HandleCount}");
                this._lastGdiCount = gdiCount;
            }
            catch (Exception ex)
            {
                Logger.Error($"[GDIMon] Failed to get GDI resources: {ex.Message}");
            }
        }
        // ===== 结束 =====

        // 原有的送信检查...
    }
    // ...
}
