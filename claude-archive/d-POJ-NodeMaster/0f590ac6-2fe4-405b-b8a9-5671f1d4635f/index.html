代码调查规则

本项目（D:/POJ/NodeMaster）是一个大型 C# POS 系统，已经用 codebase-memory-mcp 构建了知识图谱：13 万+ 节点、32 万+ 边。图谱里已经编码好了函数定义、调用关系（CALLS）、数据流（DATA_FLOWS）、类继承、跨服务 HTTP/异步调用等结构信息——这些正是调查代码时最常需要的东西。

为什么优先用图谱，而不是 grep / 逐文件读

这个仓库太大。grep 一个常见名字会返回成百上千条噪音命中（注释、字符串、同名变量），逐文件 Read 会迅速吃掉上下文还看不到整体关系。图谱工具是针对"定位 + 关系"专门优化过的：一次查询就拿到去重后的函数、它的调用方/被调用方、参数数据流，比手工翻文件快几个数量级而且更准。所以调查代码的默认入口是图谱，不是 grep。

工具选择：按目的选工具

你的目的 用这个工具 为什么用它而不是 grep/读文件
定位函数 / 类 / 变量定义 search_graph BM25 + 语义检索 + 结构加权，命中真正的定义而不是注释或字符串里的同名词
理解调用关系（谁调用了 X / X 调用了谁） trace_path 直接沿 CALLS 边遍历，一次拿到多跳调用链，不用手动逐个追
追踪数据如何流动 trace_path（mode=data_flow） 沿 DATA_FLOWS 边传播，看参数在不同函数之间怎么传
评估一次改动的波及范围 detect_changes 基于 diff 算出受影响的下游节点
复杂 / 多跳关系查询 query_graph（Cypher） 任意图模式，例如"找所有调用 A 且被 B 调用的函数"
看整体架构、模块边界 get_architecture 高层包/服务/依赖 + Leiden 社区聚类，一眼看清真实的模块划分
看某段函数的具体源码 get_code_snippet 已经定位到具体符号后，再读它的实现细节

调查流程

  1. 确认索引：先 list_projects，确认 D-POJ-NodeMaster 已索引。如果没索引，提醒用户先 index_repository，不要在没图谱的情况下退回 grep。
  2. 不确定图里有什么时：get_graph_schema 看节点标签和边类型，避免写出查不到东西的查询。
  3. 定位目标：search_graph 找到具体的函数/类，拿到 qualified_name。
  4. 展开关系：用拿到的 qualified_name 调 trace_path 追踪调用链 / 数据流。
  5. 需要源码细节时：才用 get_code_snippet 读具体实现。

分工原则：图谱负责"定位 + 关系"，源码负责"细节"。不要用图谱去看一段函数怎么写的，也不要用读文件去找一个函数在哪定义。

什么时候读文件 / 用 grep 是合理的

读源码本身是必要的，关键是顺序：先用图谱定位，再按需读细节。以下情况直接读文件没问题：

  • get_code_snippet 已告诉你函数在哪个文件，但你需要看它的完整上下文（周围的字段定义、相邻方法、整个类的结构）。
  • 改动非代码文件：配置、.bat、.xml、.txt、文档——图谱只索引代码，这些必须直接读。
  • 确认某个非常局部、不涉及调用关系的事实（比如一个常量的具体值、一行配置）。

要避免的模式：在还没查图谱的情况下，凭直觉 Glob / Grep 一堆文件、然后逐个 Read 去回答"X 在哪定义"或"谁调用了 X"——这正是图谱已经替你做完的事，手工做既慢又容易漏。

一个示例

用户问："BuildOrderSortTool 这个工具是谁在调用？我想知道改它会影响哪里。"

❌ 错误做法：grep BuildOrderSortTool → 几十个文件命中 → 逐个 Read 排查调用点。

✅ 正确做法： 1. search_graph（query="BuildOrderSortTool"）→ 拿到该工具节点和 qualified_name。 2. trace_path（function_name=..., direction=inbound）→ 拿到全部调用方。 3. 评估改动影响：detect_changes。 4. 只在需要确认某处调用的具体写法时，才 get_code_snippet 读那一段。
