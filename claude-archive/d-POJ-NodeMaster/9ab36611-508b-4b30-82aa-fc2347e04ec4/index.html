文件：Source/POS4U/Settings/StateEventWinPOS.xml

1. 文件定位

该文件是 POS4U 系统的状态-事件驱动的命令编排配置。它定义了一组事务类型（TranType）下，当进入某个业务状态（State）时应自动执行的命令（Command）序列。不包含任何业务逻辑实现，纯粹以声明式 XML 描述状态机的事件响应行为。

属于 config 模块，被运行时状态机引擎读取，用于在状态切换时自动插入 Before 和 After 动作。

2. 对外暴露内容

该文件不暴露 class / function / export，它暴露的是一组状态机事件绑定规则，以下逐一列出顶级元素：

3. 关键逻辑 walkthrough

整体设计模式：

运行时，状态机引擎会读取本文件，在进入某个 TranType + State 组合时，执行该 State 下定义的所有 Command 元素。每个 Command 的 Before 属性指定进入状态前要调用的函数名，After 属性指定进入状态后要调用的函数名。

TranType 级别的 Command（不与特定 State 绑定）：

某些 TranType 在根（State 外）直接包含 Command 元素。例如 Sales（L22–L27）:

<TranType Id="Sales">
  <Command Before="Common_Clear" After="Sales_Clear" />
  <Command Before="Common_Total" After="Sales_Total" />
  ...

这意味着无论当前处于 Sales 的什么 State，当进入 Sales 事务时这些全局命令都会被触发。这是跨状态的默认行为。

State 级别的 Command：

当进入特定 State 时，执行更精细的命令。例如 L28–L31:

<State Id="SalesTran_Paying">
  <Command Before="Sales_ChangeQuantity" After="Sales_ChangeQuantityPaymentTicket" />
</State>

这意味着当常规销售进入"支付中"状态时，先调用 Sales_ChangeQuantity（二维码支付后修改数量），然后调用 Sales_ChangeQuantityPaymentTicket（修改支付票证数量）。

运行时的语义推测：

从 Before / After 属性命名推测，命令引擎的工作方式是： 1. 检测到状态切换到某个 <State Id="..."> 2. 遍历该 State 下所有 <Command> 元素 3. 对每个 Command，先执行 Before 函数（可能是进入状态前的清理或检查组），然后执行 After 函数（进入状态的业务逻辑）

事务级 vs 状态级的优先级：

需要结合其他文件确认：当同一个 TranType 同时存在事务级 Command 和状态级 Command 时，引擎是先执行事务级再执行状态级，还是反之。

重复定义问题：

  • CashIn 出现两次（L150 和 L164），L150 只定义了 Common_Total → CashInOut_Total，L164 只定义了 Common_CancelReason → MainMenu_ChangeDisplayBack 和 Common_FixReason → CashInOut_SetReason
  • CashOut 同理出现两次（L154 和 L170），内容和 CashIn 完全对称
  • EMoneyChargeVoid 出现两次（L198 和 L202），L198 是事务级的 ScanReceiptBarcode 映射，L202 是状态级的 EMoneyChargeVoidTran_Fixed 下的显示切换

这表明 XML 引擎支持对同一个 TranType Id 的分布式定义（multi-declaration）——运行时引擎会将所有同 Id 的 <TranType> 合并为一个事务类型的完整配置。否则重复定义会导致覆盖或加载错误。

状态 Id 的命名约定：

State Id 的命名分层清晰：{TranType缩写}{业务阶段}_{子阶段}。例如： - SalesTran_ItemReference（L32）——销售交易中的单品参照 - ItemReference_WaitingISBN（L36）——单品参照下的 ISBN 等待子状态 - ItemReference_WaitingCCodeAndPrice（L40）——单品参照下的条码+价格等待子状态

这是一种层次化状态嵌套（隐式通过命名前缀表达），而非 XML 层级嵌套。

SelfSales vs Sales 的关系：

SelfSales（L3）和 Sales（L21）共享很多同名 State（如 SalesTran_ItemReference），但行为不同： - SelfSales 的 SalesTran_ItemReference 执行 Common_SignInAttendant + SelfSales_ChangePriceBttonEnable - Sales 的 SalesTran_ItemReference 执行 Sales_ItemReference + Common_Barcode 即自助和人工结账在同一状态走不同逻辑。

商品取消的多路径设计（L47–L64, L73–L90, L109–L126）：

在 SalesTran_ItemCancel 状态中，定义了 8 个不同的 Command，每个对应不同的商品查找方式（标准查价、杂志查价、非查价、非 PLU 食品、书籍查价、ISBN 查价、CCode+Price 查价、降价商品）。取消方式也分两类：普通商品用 CancelSpecifiedLineByItem，特殊商品/书籍用 CancelSpecifiedLineBySpecialItem。

Return（L73–L90）和 ReSales（L109–L126）的 SalesTran_ItemCancel 配置与 Sales 完全相同，说明三种事务在取消商品时行为一致。

关于 L179 的逗号分隔语法：

<State Id="EvidenceReceiptTran_Fixed,EvidenceReceiptTran_Canceled">

这是一个特别设计：Id 属性包含逗号，表示该 Command 绑定到多个状态。这里表示当凭证收据处于"已确认固定"或"已取消"状态时，清除操作都跳转到显示切换。这与文件 2 的 Ids 属性（复数，逗号分隔列表）功能相同但属性名不同，需要结合引擎代码确认两者是否等价。

文件：Source/POS4U/Settings/StateWinPOSReSales.xml

1. 文件定位

该文件是 POS4U 系统的状态-可用命令映射配置，专门定义「再销售（ReSales）」和「取消（Void）」两类事务下，每个业务状态允许执行哪些用户命令。

与 StateEventWinPOS.xml 的区别： - StateEventWinPOS.xml：定义状态进入时自动触发的 Before/After 命令（事件驱动） - StateWinPOSReSales.xml：定义在某个状态下用户可以操作哪些命令（操作权限映射）

后者可以被理解为「UI 菜单/按钮可用性配置」——在特定状态下，显示哪些操作按钮给用户。

3. 关键逻辑 walkthrough

整体设计模式：

运行时，UI/按钮控制器会在状态切换时加载本文件，查询当前 TranType + State 下有哪些可用的命令（Command Id），然后据此渲染 UI（启用/禁用按钮或显示/隐藏菜单项）。

数据结构的差异——Ids 复数属性：

与文件 1 使用 State Id="..." 不同，本文件大量使用 State Ids="..."（复数）。Ids 的值通常为逗号分隔的列表。例如 L21:

<State Ids="SalesTran_Fixed,SalesTran_Canceled">

这表示当处于这两个状态之一时，都可执行 Sales_ChangeDisplay 和 MainMenu_ChangeDisplay 命令。

Ids 是复数形式，等同于文件 1 的 Id="A,B" 逗号分隔写法（L179），但属性名不同。需要结合引擎代码确认两者语义是否等价。

状态覆盖范围——从初始到补偿全链路：

ReSales（L3–L113）定义了 17 个状态，覆盖了从扫码重建交易（ReSalesTran_Neutral）→ 录入商品（SalesTran_EnteringItem）→ 支付（SalesTran_Paying）→ 完成/取消（SalesTran_Fixed,SalesTran_Canceled）的全生命周期，还包括错误恢复（ReSalesTran_RestoreMemberError、ReSalesTran_RestoreFatalError）和特殊状态（FaceMe 人脸识别、ValueCard 离线、PaymentService 连接中等）。

可用命令数的差异反映业务复杂度：

  • SalesTran_EnteringItem（L30–L50）：16 个命令——商品录入状态最复杂，需要增删改查、数量价格修改、会员操作、税务组变更等
  • SalesTran_Paying（L56–L79）：18 个命令——支付状态功能最多，支持现金、储值卡、应收账款、支付服务等多种支付方式
  • 错误状态（ReSalesTran_RestoreFatalError L14–L16）：仅 1 个命令——致命错误只允许强制取消
  • 简单状态（VoidTran_SelectReason L119–L122）：2 个命令——选择原因只有设置原因和取消确认

CAFIS Arch LAN 支付的特殊处理（L143–L148）：

Void 下的 Payment_CAFISArchLAN_WaitingPayment 状态有 4 个命令，是 Void 中最多的。CAFIS 是日本的信用卡支付网络（Credit And Finance Information System），ArchLAN 是其一种通信架构。该状态提供重试（Device_CAFISArchLANTotal）、未完成处理（Device_CAFISArchLANEMoneyUnFinished）、呼叫店员（Common_CAFISArchLANCallAttendant）和取消（Payment_CancelCAFISArchLAN）四个操作，说明 CAFIS 支付在取消事务中是一个需要特殊处理的异步流程。

关于 FaceMe 生物识别（L101–L108）：

两个 FaceMe 相关状态说明系统集成了人脸识别功能： - SalesTran_WaitingFaceMe（L101）：等待人脸识别完成，支持取消识别或确认识别完成 - SalesTran_FaceMeSecondCheckPinInput（L105）：人脸识别二次认证需输入 PIN，支持取消或进行二次检查

PaymentService（支付服务）的通用连接处理（L109–L112 和 L139–L142）：

PaymentService_ConnectService 状态同时出现在 ReSales 和 Void 中，且命令完全相同（PaymentService_Total + PaymentService_NotifyError）。这表明支付服务连接是一个跨事务复用的状态，当连接建立时执行合计查询，连接异常时通知错误。PaymentService_NotifyError 是唯一同时出现在该状态的命令，说明连接失败时用户只能收到错误通知而无法做其他操作。

4. 关键元素说明

4.1 <State Ids="..."> 多状态绑定

  • 位置: L4, L10, L14, L17, L21, L25, L30, L51, L56, L80, L84, L88, L92, L97, L101, L105, L109, L115, L119, L123, L127, L131, L135, L139, L143
